# MonkeyScrimManager2

작성일: 2026-10-28

## 1. 프로젝트 개요

MonkeyScrimManager2(이하 `MSM2`)는 [MonkeyScrimManager](https://github.com/Longcat2957/MonkeyScrimManager)(이하 `MSM1`)의 리그 오브 레전드 내전 운영 비즈니스 로직을 참고하여, 프로젝트 구조와 사용자 경험을 처음부터 다시 설계하고 구현하는 프로젝트이다.

`MonkeyScrimManager2`와 `MSM2`는 내부 프로젝트명이며, 사용자에게 노출하는 서비스명은 **`Monkeybot`**이다.
화면·브라우저 제목·메타데이터·봇 메시지에는 정확히 `Monkeybot`을 사용한다.

MSM2는 기존 코드를 점진적으로 개선하는 일반적인 리팩터링이 아닌, 기존 프로젝트를 참고 자료로 활용하는 **전면 재구축(Clean-Slate Rewrite)** 프로젝트이다.

기존 기능을 모두 계승할 필요는 없으며, 불필요한 기능은 제거하고 필요한 기능은 개선하거나 새롭게 구현한다.

## 2. 재구축 배경

MSM1은 개발 과정에서 기능과 코드가 누적되면서 전체적인 구조가 지나치게 복잡해졌다.

주요 문제점은 다음과 같다.

- 불필요하게 분리된 백엔드 및 외부 API 처리 구조
- 하나의 파일에 과도하게 많은 코드와 책임이 집중된 구조
- 모듈 간 역할과 책임이 불명확한 설계
- 구성요소 사이의 높은 결합도
- 새로운 기능의 추가와 기존 기능의 수정이 어려운 구조
- 전반적인 코드 가독성과 유지보수성 저하

이러한 문제는 부분적인 리팩터링으로 해결하기 어렵다고 판단하였다.

따라서 MSM2에서는 기존 코드와 아키텍처를 계승하지 않고, 유지보수성과 확장성을 중심으로 새로운 시스템을 구축한다.

## 3. 기술 스택 및 아키텍처

MSM2의 기술 스택과 배포 환경은 다음과 같이 확정한다.

- **웹 애플리케이션:** SvelteKit 기반 풀스택
- **봇 애플리케이션:** discord.js 기반 Discord 봇
- **디자인 프레임워크:** [STDF](https://stdf.dev/) (Svelte 5 및 Tailwind CSS 4 기반)
- **데이터베이스:** PostgreSQL
- **배포 환경:** VPS

MSM1에서 사용하던 Rust-Axum 기반의 별도 웹 백엔드와 분리된 Riot API 처리 구조는 제거한다.

웹 애플리케이션의 프런트엔드와 서버 측 기능을 SvelteKit으로 통합하여 불필요한 서비스 분리를 최소화한다.

단, 애플리케이션을 통합한다는 것이 모든 코드를 하나의 모듈에 집중시킨다는 의미는 아니다. 각 기능의 책임과 의존 관계는 명확하게 구분한다.

PostgreSQL은 유지하지만 기존 데이터베이스 스키마는 전면 재설계한다.

기존 배포 환경인 VPS도 유지하되, 배포 구성과 운영 방식은 새로운 아키텍처에 맞게 재정비한다.

## 4. 기능 재정립

MSM1의 모든 기능을 유지하는 것을 목표로 하지 않는다.

기존 기능을 분석하여 유지, 개선, 제거 여부를 결정하고, MSM2에 필요한 기능을 새롭게 정의한다.

기존 프로젝트의 동작과 구현은 참고 자료일 뿐이며, MSM2의 기능 범위는 별도의 요구사항 문서에서 관리한다.

## 5. 사용자 경험 개선

### 5.1. ROFL 기반 전적 등록

MSM1에서는 내전 종료 후 사용자가 경기 결과를 직접 입력해야 한다.

MSM2에서는 리그 오브 레전드 리플레이 파일(`*.rofl`, 이하 `ROFL 파일`)을 업로드하여 경기 결과를 등록하는 방식을 핵심 기능으로 제공한다.

이를 통해 다음을 목표로 한다.

- 수동 입력 과정 제거
- 전적 등록 절차 간소화
- 사용자 입력 오류 감소
- 전적 데이터의 정확성과 일관성 향상

기존의 수동 전적 입력을 위한 컴포넌트와 처리 흐름은 제거한다.

단, 파일 분석 오류와 데이터 누락에 대한 검증 및 예외 처리 방안은 별도로 마련한다.

### 5.2. 상세 경기 정보 제공

MSM1에서 제공하지 못했던 다양한 경기 정보를 추가한다.

예상되는 정보는 다음과 같다.

- 경기 진행 시간
- 플레이어별 CS 및 KDA
- 플레이어별 상세 경기 통계
- 팀별 경기 결과와 성과
- 누적 전적을 활용한 통계 및 분석

실제 제공 가능한 정보의 범위는 ROFL 파일의 분석 및 기술적 검증을 통해 확정한다.

### 5.3. 화면 내 중복 방지

한 페이지에서 하나의 기능은 하나의 조작 지점으로 제공하고, 하나의 설명은 필요한 위치에서 한 번만 제공한다.
공통 헤더·본문·푸터와 열린 메뉴·대화상자를 포함해 화면 전체를 기준으로 판단한다.
빈 공간을 채우기 위한 구성요소나 같은 의미를 바꿔 쓴 안내는 추가하지 않는다.
구체적인 작성·완료 검토 기준은 [AGENTS.md의 Web UI and Content Rules](../AGENTS.md#web-ui-and-content-rules)를 따른다.

## 6. 데이터 보존 원칙

ROFL 파일에서 수집한 데이터는 향후 새로운 기능과 통계 분석에 활용할 수 있도록 최대한 보존한다.

다음 원칙을 따른다.

- 업로드한 ROFL 원본 파일 보존
- 추출 가능한 원본 메타데이터 보존
- 주요 경기 정보의 구조화 및 PostgreSQL 저장
- 게임 버전과 파서 버전에 따른 데이터 형식 차이 고려
- 새로운 데이터 추출 기능이 추가될 경우 기존 원본을 재분석할 수 있는 구조 마련

원본 파일과 분석 결과를 구분하여 관리하며, 구체적인 데이터베이스 스키마와 저장 구조는 별도로 설계한다.

## 7. 코드 품질 및 설계 원칙

MSM2에서는 코드의 유지보수성과 가독성을 핵심적인 품질 목표로 설정한다.

다음 원칙을 지향한다.

1. **단일 책임:** 각 모듈과 컴포넌트는 명확한 책임을 가진다.
2. **관심사 분리:** UI, 비즈니스 로직, 데이터 접근 및 외부 API 처리를 적절히 구분한다.
3. **적절한 모듈화:** 지나치게 비대한 파일과 불필요한 추상화를 방지한다.
4. **낮은 결합도:** 특정 기능의 변경이 다른 기능에 미치는 영향을 최소화한다.
5. **테스트 용이성:** 주요 비즈니스 로직을 독립적으로 검증할 수 있도록 설계한다.
6. **단순성 우선:** 명확한 필요성이 없는 복잡한 패턴과 계층의 도입을 지양한다.

단순히 파일을 작게 나누거나 코드의 줄 수를 줄이는 것 자체가 목적은 아니다.

각 구성요소의 책임이 명확하고, 새로운 개발자가 쉽게 이해하고 수정할 수 있는 구조를 목표로 한다.

## 8. 기존 프로젝트 활용 원칙

MSM1은 다음 사항을 파악하기 위한 참고 자료로 활용한다.

- 기존 내전 운영 비즈니스 로직
- 사용자 및 관리자 워크플로
- 기존 기능의 목적과 동작
- 데이터 간 관계 및 처리 흐름
- 기존 아키텍처의 문제점

반면 기존 프로젝트의 기능 전체, 코드 구조, 데이터베이스 스키마 및 구현 패턴은 계승 대상으로 간주하지 않는다.

MSM2의 설계는 기존 코드를 얼마나 재사용할 수 있는지가 아니라, **새로운 요구사항을 얼마나 단순하고 명확하게 구현할 수 있는지**를 기준으로 결정한다.

## 9. 최종 목표

MSM2는 MSM1의 기능을 단순히 재구현하는 프로젝트가 아니다.

내전 운영에 실질적으로 필요한 기능을 중심으로 시스템을 재정립하고, ROFL 기반의 편리한 전적 관리 경험을 제공하며, 장기적으로 유지보수하고 확장하기 쉬운 코드베이스를 구축하는 것이 궁극적인 목표이다.
