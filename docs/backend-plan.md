# 백엔드 구현 계획

작성일: 2026-11-03. 전체 코드 대조일: 2026-11-05. 기준: 현재 작업 트리의 프론트엔드·서버 코드와 DB 스키마.

**SvelteKit의 기존 화면과 form action을 유지하면서, 기능별 서버 함수에 인증·업무 규칙·DB 저장을 연결한다.**
읽기는 `queries.ts`, 쓰기는 `service.ts`에 모으고 Drizzle을 직접 사용한다. CRUD의 생성·조회·수정·삭제 책임을 명확히 나누되,
취소·철회처럼 기록을 남겨야 하는 동작은 상태 수정으로 처리한다. 별도 API 서버나 테이블마다 반복되는 CRUD 계층은 만들지 않는다.

이 문서는 구현한 기반과 남은 작업의 설계·완료 기준을 함께 기록한다. 현재 화면별 구현 현황은 [웹 문서](web/README.md),
서비스 원칙은 [프로젝트 목적](purpose.md), 저장 계약은 [DB ERD](database-erd.md)·[ROFL 적재 모델](rofl-import.md)·[MMR](mmr.md)을 따른다.
아래에서 **제안**으로 표시한 정책은 아직 서비스 요구사항으로 확정되지 않았다.

보존할 업무 데이터가 없다는 사용자 확인에 따라 **35개 테이블·76개 외래키의 초기 생성 기준을 재작성했다.** 이후 `0001`~`0004`를 추가한 현재 스키마는 **40개 테이블·88개 외래키**다.
`0000_initial_schema.sql`부터 Drizzle journal 순서로 적용한다. 이미 적용한 SQL은 보존하고 이후 변경은 새 migration으로 관리한다.

Discord OAuth·DB 세션·공개 조회/관리 guard, 서버별 Riot 계정 연결, Discord 설정, 모집·신청·수동 편성·대진·진행 상태를
실제 서버 함수와 DB에 연결했다. 경매·경기·개인 전적·통계·홈 순위 조회와 내부 MMR 반영·역분개 서비스도 구현했다.
모집·개인 신청·팀 구성 게시와 Gateway 동기화·게시 복구도 연결했다. ROFL 영구 등록·MMR 동시 반영·시리즈 종료·승자 진출·최종 결과 게시와 운영자 요청 참가 안내 DM도 연결했다.
실제 Discord/Riot 자격 증명으로 전체 흐름을 검증했다는 뜻은 아니다. 아래 완료 기준은 후속 검증에도 적용한다.

## 2. 코드 구조와 책임

다음은 현재 기능별 책임 구조다. 모든 폴더에 같은 파일 구성을 강제하지 않고 필요한 조회·쓰기 모듈만 둔다.

```text
apps/web/src/
  hooks.server.ts                  세션 복원, 요청 식별자
  routes/**/+page.server.ts         load와 form action 어댑터
  routes/**/+server.ts              실제 HTTP 소비자가 있는 인터페이스
  lib/features/**                  화면 DTO, 공유 enum·순수 계산
  lib/server/
    auth/                          OAuth, 세션, 권한 검사
    guild/                         길드·멤버·Discord 설정·홈 조회
    accounts/                      Riot 계정 연결·대표 지정·해제
    scrims/                        내전 설정·신청·상태 전환
      manual.ts                    수동 편성
      auction.ts                   경매
      bracket.ts                   대진 초안·확정·승자 진출
    matches/                       경기·Game 조회, 검증된 결과 등록
    rofl/                          기존 파서·적재 모델, 참가자 연결
    mmr/                           계산, 원자적 반영·안전한 역분개
    records/                       현재 시즌 개인 전적·통계 조회
    discord/                       봇 통신, 동기화·게시 작업
    riot/                          기존 Riot 클라이언트
    ddragon/                       기존 카탈로그·에셋 조회
    db/                            Drizzle 연결·스키마
    errors.ts                      예상 가능한 업무 오류
    status.ts                      기존 상태 조회
apps/bot/src/                      Gateway, Discord interaction·메시지
apps/web/drizzle/                  초기 생성 SQL·Drizzle 이력, 운영 이후 변경 migration
```

- 각 기능은 필요할 때 `queries.ts`와 `service.ts`를 둔다. 입력 검증이나 변환이 반복될 때만 별도 파일로 분리한다. 파일마다 동일한 틀을 강요하지 않는다.
- **라우트:** 요청 파싱 → 세션 문맥 전달 → 서버 함수 호출 → 기존 반환형·`fail`·`redirect` 변환. SQL과 업무 상태 전환을 직접 작성하지 않는다.
- **조회 함수:** 권한과 길드 범위를 확인하고 필요한 자료를 조회해 화면 DTO를 반환한다. 팀·대진 초안 등을 조회 중 생성하지 않는다.
- **쓰기 함수:** 입력 허용 목록, 권한, 현재 상태, 연관 데이터 검증과 트랜잭션을 소유한다. `RequestEvent`·`FormData`·SvelteKit `fail`에 의존하지 않는다.
- **DB 접근:** 해당 기능 안에서 Drizzle을 직접 사용한다. 재사용되는 복잡한 쿼리만 추출한다. `BaseRepository`, `BaseService`, 범용 CRUD 생성기, DI 프레임워크는 도입하지 않는다.
- **기능 간 호출:** 최상위 업무 함수가 트랜잭션 하나를 열고 하위 함수에 `tx`를 전달한다. 하위 함수가 독립 커밋해 일부만 저장되는 구조를 피한다.
- **공유 규칙:** 화면의 `can.*`와 서버 쓰기 검증이 같은 상태·권한 판정을 사용한다. 순수 규칙은 재사용하되, 클라이언트가 보낸 권한·점수·잔액은 신뢰하지 않는다.
- **봇:** 웹이 DB와 업무 규칙을 소유하고 봇은 Discord 입출력을 담당한다. 봇에 동일한 모집·편성 규칙을 다시 작성하지 않는다.

## 3. CRUD와 요청 계약

### 3.1 CRUD의 의미

| 구분 | 서버 함수 명명 | 처리 원칙 | HTTP API가 필요한 경우 |
| --- | --- | --- | --- |
| C 생성 | `createScrim`, `createRegistration`, `createGameFromRofl` | 서버가 ID·시각·초기 상태 생성. 같은 성공 요청 재시도에 중복 효과 방지 | `POST /resources`, 생성 시 `201` |
| R 조회 | `getScrim`, `listMatches`, `getPlayerRecord` | 부수 효과 없이 조회. 단건 없음과 빈 목록 구분 | `GET /resources`, `GET /resources/:id` |
| U 수정 | `updateScrimSettings`, `updateRegistration`, `updateAuctionSetup` | 허용 필드만 수정. 상태 전환은 명시적 함수로 사전 조건 검증 | 일부 수정 `PATCH`, 전체 자원 교체가 필요한 경우만 `PUT` |
| D 삭제 | `deleteSession`, `deleteAccountLink`, `deleteDraftBracket` | 세션·연결·이력이 없는 대진 초안처럼 실제 제거 대상만 삭제 | `DELETE /resources/:id`, 본문 없으면 `204` |

`withdrawRegistration`, `cancelScrim`, `endScrimEarly`, `voidAcquisition`은 **U**다.
계정 연결 삭제는 `guild_riot_accounts`의 해당 서버 연결을 지우는 DELETE다. `riot_accounts` 식별 행과 과거 출전은 보존한다.
수동 편성·대진 배정 해제는 기존 참가자·슬롯의 필드를 비우는 U이며 참가자·팀 삭제가 아니다.
기록이 있는 Scrim·Match·Game·신청 이력·MMR 원장에 화면 소비자가 없는 자유 삭제 API를 만들지 않는다.
상태 전환을 `updateScrim({ status: arbitraryValue })`로 개방하지 않고 `startScrim`, `closeRecruitment`처럼 조건이 분명한 함수로 제공한다.

웹의 기존 `?/register`, `?/move`, `?/unlink` 등은 유지한다. SvelteKit form action의 전송은 POST이지만
내부 서비스는 위 CRUD 책임으로 나눈다. 같은 기능을 JSON REST API와 form action에 이중 구현하지 않는다.
독립 HTTP 소비자가 있을 때만 오른쪽 열의 메서드 규칙을 적용한다.
[SvelteKit form actions 공식 문서](https://svelte.dev/docs/kit/form-actions).

### 3.2 공통 계약

- 실행자 ID는 세션 또는 인증한 봇 interaction에서 얻는다. 모든 조회·수정에서 `guildId → scrimId → matchId/participantId`의 소속 관계를 서버가 확인한다.
- Discord ID는 문자열, 서비스 내부 ID는 UUID로 검증한다. enum·정수 범위·문자열 길이·목록 크기·실제 달력 날짜를 검사한다. 일정은 Asia/Seoul 입력을 UTC로 저장한다.
- 기존 성공·실패 모양을 유지한다. 생성의 이동 경로, 업로드의 `{ order }`, `message`, `errors`, `positionsError`, `riotIdError`, `lookup`을 해당 화면에 맞춰 반환한다.
- 업무 오류는 코드·사용자 문구·필드 오류를 갖는다. 라우트가 `400` 입력 오류, `401` 인증 필요, `403` 권한 없음, `404` 범위 내 대상 없음, `409` 충돌, `413` 크기 초과, `429` 호출 제한, `503` 외부 의존 장애로 변환한다. 예상하지 못한 오류는 `500`으로 전달한다. 요청 식별자는 생성하지만 오류 로그·응답과의 연결은 아직 구현하지 않았다.
- 기존 Riot·Data Dragon의 `502` 상위 응답/통신 오류, `504` timeout, `503` 설정/가용성 오류와 `Retry-After` 계약은 유지한다.
- SQL 오류·토큰·원본 ROFL을 응답이나 로그에 노출하지 않는다. 교차 길드의 존재 여부를 드러내지 않는 오류 정책을 통일한다.
- 초기 범위에서 목록·필터·페이지 크기는 기존 프론트 계약을 유지하고 정렬에 고유 ID를 보조 키로 넣는다. 모든 목록 요청에 상한을 둔다.
- `load`는 필요한 DB 자료를 일관된 단위로 읽고, 연관 행은 묶어서 조회한다. 참가자마다 Riot API나 개별 SQL을 호출하는 방식은 사용하지 않는다.

### 3.3 동시 변경과 재시도

내전 쓰기는 **Scrim 행 잠금 → 최신 권한·상태 확인 → 해당 자원 변경 → revision 증가**를 기본으로 한다.
운영자의 설정·편성·경매·대진 변경에는 `expectedRevision`을 추가하고 값이 다르면 `409`와 재조회로 처리한다.
일반 참가 신청은 최신 정원을 잠금 안에서 다시 계산하므로 다른 사람의 신청만으로 불필요한 충돌을 만들지 않는다.
[PostgreSQL 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

경매의 현재 후보 처리에는 `lotId`도 필수다. 사용자가 보고 있던 후보와 서버의 후보가 다르면 낙찰하지 않는다.
편성 드래그 요청은 클라이언트에서 순차 처리하며, 실패하면 서버 상태로 복구한다.
서버 함수는 외부 API 호출·ROFL 파싱을 잠금 밖에서 수행하고, 저장 직전에 바뀔 수 있는 조건을 다시 검사한다.
기본 잠금 순서는 내전 → 경기 → 관련 행의 고정 ID 순서로 통일한다.
계정 연결/해제와 신청/신청 계정 변경은 관련 사용자·Riot 계정을 고정 순서로 먼저 잠근 뒤 서버별 연결·내전을 잠근다.
같은 트랜잭션 안에서 해당 서버의 연결 소유자와 활성 사용 여부를 다시 확인하여 해제와 신청의 경쟁을 막는다.
사용자 잠금은 외래키 KEY SHARE 검사와 충돌하지 않는 `FOR NO KEY UPDATE`를 사용한다.
MMR 반영·정정·시즌 변경은 시즌 → 내전 → 경기 → Game → 점수 행 순서를 공유한다.

고유 제약은 마지막 방어선으로 사용한다. 내전 생성은 요청 ID, 신청은 현재 신청의 고유성, 봇은 interaction ID,
ROFL은 검증된 파일·경기 식별 근거로 재요청을 구분한다. 응답 유실 후 재시도가 다른 사람을 처리하거나 데이터를 두 번 만들면 안 된다.

## 5. 기능별 구현 규칙

### 5.1 인증과 접근 권한

1. `/auth/discord` → `/auth/discord/callback`의 Authorization Code + PKCE를 구현했다. 일회성 `state`, 고정 callback, 내부 경로만 허용하는 복귀 주소를 검증한다. OAuth는 `identify`만 요청하고 길드 후보·소속은 Bot REST로 확인한다. [Discord OAuth2](https://docs.discord.com/developers/topics/oauth2).
2. 세션은 DB에 난수 토큰의 해시·사용자·만료 시각을 저장한다. 쿠키에 원본 난수를 넣고 `HttpOnly`, 운영 `Secure`, `SameSite=Lax`, 경로·만료를 명시한다. 로그인 시 새 세션을 발급하고 `/auth/logout` POST에서 삭제한다.
3. `hooks`는 세션을 `App.Locals`에 복원한다. 일반 서버 조회는 `requireGuildView`로 활성 길드의 공개 열람을 허용한다. 조작은 `requireUser`, `requireGuildMember`, `requireGuildAdmin`, `requireServiceAdmin`으로 용도에 맞게 검사한다. 관리 화면·본인 계정·백오피스는 각각의 전용 권한을 유지한다. 레이아웃 통과나 숨겨진 버튼은 권한 검사를 대신하지 않는다. [SvelteKit hooks](https://svelte.dev/docs/kit/hooks#Server-hooks-handle-locals).
4. 세션 사용자와 길드 권한을 분리한다. 소속·실효 서버 관리 권한·운영자 역할은 봇 동기화와 요청 시 확인으로 갱신한다. 서비스 운영자에게 모든 길드 조작 권한을 자동 부여하지 않는다.
5. 봇은 `Guilds`와 `GuildMembers` intent를 사용하며 Developer Portal의 Server Members Intent 설정이 필요하다. 역할·탈퇴 이벤트를 처리하고 봇 재시작·이벤트 누락 후 알려진 서비스 멤버를 재확인한다. 권한 갱신 실패를 권한 있음으로 처리하지 않는다. [Discord Gateway intents](https://docs.discord.com/developers/events/gateway#gateway-intents).
6. 헤더의 로그인·POST 로그아웃을 연결했다. 일반 열람은 비로그인·비소속자에게 공개하며 본인 신청은 소속 멤버, 운영 조작은 길드 관리자로 제한한다. ROFL은 관리자 또는 확정된 경기 출전자에게 허용하고 실제 등록에서도 현재 권한을 재검증한다.

로그인 시 필요한 조회 후 OAuth 토큰은 폐기한다. 지속 갱신을 소비하는 기능이 생길 때만 암호화 저장을 추가한다.
웹 쓰기는 SvelteKit의 origin 검사와 쿠키 정책을 유지하며, 브라우저가 봇 내부 인증을 대신 사용할 수 없게 한다.

### 5.2 서버 관리와 계정 연결

- 로그인·검증된 봇 참가 시 사용자와 멤버 연결을 생성·갱신한다. 멤버 관리 목록은 현재 화면대로 서비스에 연결된 멤버를 대상으로 한다.
- Riot 조회는 기존 `server/riot` 함수를 직접 호출한다. PUUID는 Riot API 식별자, `platform`은 LoL 플랫폼, ACCOUNT 지역은 라우팅 값으로 구분한다.
- `link`는 관리자·대상 멤버·실제 조회 결과를 확인한 후 사용자와 계정을 잠그고 해당 서버에 연결한다. 같은 서버의 다른 사용자 연결을 탈취하지 않으며 첫 연결을 대표로 지정한다.
- `primary`는 해당 서버에서 대상 사용자에게 연결된 계정인지 확인하고 기존 대표 해제와 새 대표 지정을 함께 커밋한다. `unlink`는 **해당 서버**의 활성 내전 사용 여부를 검사한 뒤 연결 행만 삭제한다. 대표 해제 시 남은 `linked_at → riot_account_id` 순으로 재선택한다.
- Riot 식별 행은 PUUID로 재사용하지만 연결·대표 여부·변경 권한은 서버별이다. 다른 서버의 연결·활성 신청은 변경하지 않는다. `/me`는 본인 연결을 서버별로 묶으며, 과거 Game·MMR의 사용자 귀속은 당시 출전 기록을 따른다.
- Discord 설정은 알려진 역할·채널 ID만 받는다. 운영자 역할 변경 뒤에도 실행자가 관리 권한을 유지하는 현재 조건을 지킨다. 역할 삭제·채널 삭제·봇 권한 회수를 반영한다.
- 계정 연결 행에는 연결 실행자·시각이 저장되지만 계정 해제·대표 변경·권한 설정 변경의 별도 감사 원장은 없다. 감사 기록 보강은 후속이며 세션·토큰·원본 파일은 기록 대상이 아니다.

### 5.3 모집과 단계 전환

- 팀 수 2~4, 팀당 5명, 추가 모집 0~10명을 서버에서 검증한다. 선발은 `팀 수 × 5`, 활성 신청은 `선발 정원 + 추가 정원` 이하다.
- 동일 내전에서 사용자·Riot 계정 중복을 생성과 수정 모두 검사한다. 해당 서버에서 본인에게 연결된 계정만 선택할 수 있다. 희망 포지션은 중복 없는 유효 목록이다.
- 신청 이력은 유지한다. 철회·제외는 기존 신청을 닫고 재신청은 새 행을 만든다. 선발자 이탈 시 가장 이른 대기자부터 승급하며 동시 신청·철회에도 정원을 지킨다.
- 신청 상태 조작에는 신청 ID, 편성·경매·출전에는 영속 참가자 ID를 사용한다. 재신청해도 기존 참가자 식별자는 유지한다.
- 정원 축소는 선발 수와 전체 활성 신청 수를 모두 검사한다. 자동 제외로 맞추지 않는다. 수동 대기 전환 후 자동 재승급 정책은 9절에서 확정한다.
- 모집 마감은 선발 정원이 정확히 찼을 때 허용한다. 방식 미선택 상태로도 마감할 수 있다. 팀 기본 이름·표시 순서는 서버에서 생성한다.
- `recruit → preparing → ready → in_progress → completed`, `cancelled`, `ended_early`를 명시적 전환표로 구현한다. 정상 결과 등록에서 BO 승자와 결승 승자를 자동 판정해 내전을 종료한다. 정상 ROFL 등록은 마지막 대진 완료 시 자동 종료한다. 현재 요약의 내전 종료 조작도 남아 있으며 모든 대진이 완료된 경우에만 허용한다.
- 방식 변경·되돌리기는 현재 단계와 진행 이력을 검사한다. 편성·대진 초안은 정리하고 경매 이력은 무효화하며 신청 이력은 유지한다. 기록된 Game이 있으면 모집·편성·대진 준비로 돌아가지 않는다.
- 현재 중도 종료는 진행 Match를 `ended_early`, 미진행 Match를 `cancelled`로 만들고 완료 Game·점수·MMR을 보존한다. MSM1의 현재 점수 우세 팀 판정과 동점 승자 없음, 종료 가능한 단계 확대는 결과·후속 대진 처리와 함께 연결할 차이다.

| 기존 되돌리기 | DB 처리 |
| --- | --- |
| `preparing → recruit` | 방식·신청 유지, 미확정 편성 초기화. 이력이 참조하는 팀·경매 행은 보존 |
| `ready → preparing` | 대진 초안 정리, 편성 잠금 해제 |
| `in_progress → ready` | Game이 없을 때만 허용. 무결과 Match와 노드 연결을 정리하고 재시작 때 변경된 대진·BO로 재생성 |
| `completed → in_progress` | 완료 Game·Match 유지, 내전 종료 상태만 복귀 |
| `ended_early → in_progress` | 완료 기록 유지, 해당 중도 종료가 멈춘 Match만 이전 상태로 복원 |
| `cancelled` | 복귀하지 않음 |

실제 Game 존재를 검사하며 `Match.status=in_progress`라는 이유만으로 무결과 되돌리기를 막지 않는다.
반대로 업로드와 되돌리기가 동시에 실행되어 이미 저장된 Game을 삭제하지 않도록 같은 잠금을 사용한다.

### 5.4 수동 편성과 경매

수동 편성은 선발 참가자만 배정하며 팀·포지션 슬롯마다 한 명, 참가자마다 한 슬롯을 보장한다.
이동·교환을 한 트랜잭션으로 처리하고, 전원 배정과 팀별 다섯 포지션이 완성될 때 확정한다.
직접 action 요청에서도 `formationMethod=manual`과 허용 단계를 확인한다.

경매는 다음 불변식을 서비스와 DB 제약으로 지킨다.

- 경매 시작 전 팀장 중복·선발 여부·팀 수·초기 포인트를 검사한다. 설정 중 일부 팀장만 선택한 저장도 지원한다.
- 시작 포인트는 1 이상, 낙찰가는 0 이상이며 PostgreSQL `integer` 범위 안의 정수로 제한한다.
- 참가자는 팀장·영입 완료·현재 후보·대기·유찰 중 정확히 한 상태에 속한다. 현재 열린 lot는 하나다.
- 낙찰 가격은 정수·허용 범위·잔액·팀 정원을 검증하고 서버가 잔액을 계산한다. 수동 영입은 가격 0 낙찰과 구분해 `method=manual`, `price=null`로 남긴다.
- `draw/shuffle/restore`의 순서는 DB에 저장한다. 프로세스 메모리나 매 조회 무작위 추첨으로 복원하지 않는다.
- `revert/reset/reopenSetup`은 영입 이력을 삭제하지 않고 무효화하며 포인트·팀 배정·lot·대기열을 함께 복원한다. 복구 후보가 현재 후보와 대기열에 중복되지 않게 한다.
- 모든 action에서 `formationMethod=auction`, 내전 단계, 경매 단계, 현재 lot를 확인한다. 완료된 팀 편성은 ready로 전환하고 대진 초안을 만든다.
- 첫 연결에서는 기존 새로고침 흐름과 저장 후 재조회를 사용한다. 실시간 공동 경매가 별도 요구되면 폴링부터 평가하고, 필요 없이 WebSocket 서버를 추가하지 않는다.

현재 10초 타이머·입찰가 입력은 운영자의 로컬 안내다. 입찰 저장·자동 낙찰·서버 타이머를 새 기능으로 추가하지 않는다.

### 5.5 대진과 Match 생성

- 현재 2팀 결승, 3팀 준결승+결승 직행 시드, 4팀 준결승 2개+결승 템플릿을 유지한다. 기본 BO와 허용값은 `features/scrims/bracket.ts`를 기준으로 한다.
- 편성 확정 때 라운드·노드·슬롯 초안을 생성한다. 확정 전에는 직접 팀 배치·이동·해제와 라운드 BO를 수정할 수 있다. 배치 이동은 도착 팀을 풀로 돌려보내며 수동 편성의 자리 교환과 구분한다.
- 확정은 대진 배치의 잠금이다. 내전 시작 때 **양 팀이 확정된 노드만** 실제 Match를 생성한다. 미정 결승을 가짜 팀 ID나 빈 팀 Match로 만들지 않는다.
- Match 생성 시 라운드 BO·내전 피어리스 설정을 복사한다. 생성 이후 설정 변경을 기존 Match에 소급하지 않는다.
- 마지막 승리 Game 등록 시 점수·승자를 확정하고 승자 참조 슬롯을 해석한다. 다음 노드의 두 팀이 모두 정해지면 해당 Match를 같은 트랜잭션에서 한 번만 생성한다.
- 결승 직행은 시드 관계로 표현한다. 존재하지 않은 Game·승리 점수·MMR을 만들지 않는다. 별도 수동 승패 입력·밴픽·게임 중 진행 상태 API는 추가하지 않는다.

### 5.6 ROFL 등록과 MMR

**ROFL은 최종 결과 입력 어댑터다.** 경기 ID·다음 세트 번호·확정 출전 라인업은 MSM1처럼 서비스가 관리한다.
`matchId + expectedRevision + expectedGameNumber`를 현재 상태와 대조하고, 확정 Game 수+1인 슬롯만 신규 등록한다.
실제 경기 시각은 확인되지 않으면 null로 보관한다. ROFL에 절대시각이나 포지션이 없다는 이유만으로
서비스의 등록 슬롯·확정 라인업·MMR 처리 순서를 미정으로 취급하지 않는다.

별도 검증이 필요한 경계는 **파일 참가자와 연결된 계정·확정 라인업의 대응, 파일의 팀·진영, 같은 경기의 중복 등록**이다.
ROFL 원시 PUUID를 Riot API PUUID와 같다고 가정하지 않는다. 서비스 팀 A/B는 기존 서버 계정 연결로 기준을 잡고 확정 팀·포지션과 대조한다. 미연결 부계정은 일치한 참가자의 해당 전적에만 귀속하며 서버별 계정 소유권을 자동 변경하지 않는다. 양 팀의 기준이 없거나 기존 소유자와 충돌하면 거부한다.
블루·레드는 업로드 화면에서 선택한 서비스 팀과 검증된 참가자 매핑을 사용한다. 파일명·홀짝 순번으로 진영을 만들지 않는다.
SHA-256은 동일 바이트 중복의 근거이고 서로 다른 파일의 동일 경기를 식별하는 키는 아니다.
이 차이를 명시적으로 검증하며, 외부 경기 ID가 필수인 새로운 운영 절차를 임의로 요구하지 않는다.

새 파일의 최초 등록 순서:

1. 사용자·길드·경기·업로드 권한과 요청 크기를 확인한다. 업로드는 파일당 64MiB로 제한한다. 공통 파서는 파일 128MiB·메타데이터 2MiB 상한을 두며, 별도 파싱 timeout·전체 업로드 동시성 제한은 없다.
2. 잠금 밖에서 `projectRoflGame`·`prepareRoflImport`로 결과·통계·파일 지문을 준비한다. 클라이언트의 계정·팀 매핑을 그대로 채택하지 않는다.
3. **사용자 → Riot 계정 → 서버별 계정 연결 → 시즌 → 내전 → 경기 → Game·점수 행** 순으로 잠근다. 전역 Riot 식별자는 갱신하지 않으므로 `KEY SHARE`를 사용한다. 이미 성공한 요청은 기존 결과를 반환하고, 신규 요청은 현재 세트·revision·라인업·BO를 재검증한다. 시즌 잠금은 내전·경기 잠금보다 먼저 획득한다.
4. ROFL 선별 행·Game·당시 실출전·동포지션 MMR 원장·현재 점수를 같은 트랜잭션에서 저장한다. 정상 경로의 DB 오류는 전체를 롤백하며 MMR만 나중에 재시도하는 성공으로 숨기지 않는다.
5. 시리즈 점수와 BO 승자를 계산하고 다음 대진·Match·라인업 전파를 처리한다. 결승 승자가 정해지면 MSM1처럼 내전도 자동 종료한다. 피어리스는 안내이며 결과 등록 실패 조건이 아니다.
6. 커밋 후 Discord 게시 등 외부 부수 효과를 처리한다. 결과·MMR 트랜잭션과 외부 메시지 전송은 구분한다.

같은 파일의 취소 결과 복구는 신규 파싱·Riot 조회 전에 분기한다. 현재 권한·슬롯을 검사하고 경기 잠금 뒤 기존 선별 자료·출전자·계정 귀속을 재검증하여 새 Game·출전·MMR·게시 이력을 저장한다. 이전 취소 Game과 역분개는 유지한다.

원본 ROFL·전체 메타데이터·패킷·파일 보관 경로는 저장하지 않는다. 재분석에는 재업로드가 필요하다.
연결 실패·승패 충돌은 예외이며 정상 결과마다 사람의 승인을 추가하지 않는다.

**라인업은 사전에 확정한다.** 경매의 희망 포지션을 실제 포지션으로 복사하지 않고 MSM1의 경기별 라인업 확정 흐름을 연결한다.
그 라인업과 파일 참가자의 대응을 검증한 값을 `gameParticipants.position`에 보존한다.
사용자·시즌·라인업 자체가 미확정인 예외 자료의 보존은 정상 자동 등록과 분리하며 정상 경로를 항상 MMR 보류로 설계하지 않는다.

[MMR](mmr.md)은 초기 1500, K=32, 동포지션 상대, Game별 반영을 준용한다. 시즌은 내전에 고정하고
외부 시각 대신 서비스의 등록 순서·점수 revision으로 반영을 직렬화한다. 실제 경기 시각을 생성하거나 변경하지 않는다.

정정은 **마지막 확정 Game**의 안전한 역분개로 처리한다. 현재 점수가 대상 원장의 after와 일치하고 revision이 최신 원장과 연속되며,
아직 유효한 후속 경기 반영·관리 보정·후속 대진 작업이 없어야 한다. 이미 역분개한 후속 변경은 이력으로 남긴다. 조건이 맞지 않으면 409이며 후속 전체 자동 재계산은 기본 범위에 넣지 않는다.
원장·이전 ROFL 근거를 보존하고 점수 복원과 Game·시리즈·대진 정정을 같은 트랜잭션에서 처리한다.

### 5.7 전적과 통계

- 개인 전적·서버 통계는 기본 현재 활성 시즌의 채택 Game과 당시 출전 기록을 조회하고 취소된 부모 기록을 제외한다. 경기 상세는 선택한 경기의 기록을 보존해 조회한다. 순위는 활성 멤버의 현재 시즌·포지션 유효 반영 1게임 이상만 포함한다.
- 전적의 사용자 귀속은 당시 참가 기록으로 고정한다. 현재 계정 소유자나 현재 길드 멤버십으로 과거 기록을 재해석하지 않는다.
- 프론트 DTO의 `kills/deaths/assists`, 다중 킬, 점수, `playedAt`, `position` 등 실제로 누락 가능한 필드를 nullable로 보완한다. 미확인값을 0·업로드 시각·희망 포지션으로 채우지 않는다.
- 평균·KDA·CS/분·팀 합계는 지표별 유효 표본과 분모를 정의한다. 0분 경기·일부 누락·날짜 미확인을 처리한다. 경기 수는 사용자 행 수를 10으로 나누지 않고 서로 다른 Game을 센다.
- 날짜 미확인 기록의 표시·정렬과 연승 등 순서 의존 지표의 제외 조건을 정한다. 데이터 없는 상태와 조회 실패를 구분한다.
- 처음에는 SQL 집계와 기존 순수 계산 함수를 사용한다. 캐시·집계 테이블은 실제 실행 계획과 응답 시간으로 필요가 확인된 뒤 추가한다.
- 편성·경매에서 보여 주는 후보 전적·MMR·시너지·챔피언 정보도 같은 조회 원천을 사용한다. 근거가 없는 목 수치를 유지하려고 미합의 Riot API나 선호 챔피언 편집 기능을 추가하지 않는다.

### 5.8 Discord 봇과 외부 API

권한·설정 동기화는 현재 웹 서버의 Bot REST 직접 조회로 연결했다. 별도 봇 RPC 없이 소속·실효 권한을 검증하고,
목록에는 30초 캐시·동시 요청 합치기·4개 서버 동시 조회 제한을 적용한다. 쓰기 guard는 캐시된 권한으로 승인하지 않는다.
모집·엔트리 게시와 참가 interaction을 기존 업무 서비스에 연결했다. 상세 구현과 실행은 [봇 문서](bot.md), 후속 의존 범위는 [봇 계획](bot-plan.md)을 따른다. 최종 결과 게시는 ROFL 저장 트랜잭션에서 예약하고 커밋 뒤 봇이 전송한다.
웹과 봇 사이에는 서버 간 인증과 외부 라우팅 차단을 적용하고, 각 요청의 실행자·길드·내전 관계를 다시 검증한다.

| 내부 인터페이스의 소비자 | 필요한 자원·동작 |
| --- | --- |
| 웹 권한 검사 | 현재 Discord Bot REST로 직접 조회. 별도 내부 HTTP 경로를 만들지 않음 |
| 봇 Gateway 동기화 | 길드·멤버·역할·채널 스냅샷 생성/갱신/소속 제거 |
| 봇 모집 interaction | 기존 신청 서비스의 C/U, interaction ID로 중복 요청 방지 |
| 봇 게시 처리 | 대기 게시 작업 조회·처리 점유·성공/실패 갱신 |

내부 인터페이스는 실제 소비 기능에 필요한 `/internal/bot/` 경로만 제공한다. 웹은 봇의 상태 확인처럼 보호된 내부 주소를 사용하며,
봇은 웹의 내부 HTTP 어댑터를 통해 같은 업무 함수를 호출한다. 봇에 DB 직접 수정 권한을 주지 않는다.

내전 저장과 Discord 전송 성공을 묶지 않는다. 필요한 게시 작업을 업무 트랜잭션에 기록하고 봇이 처리한다.
PostgreSQL의 작은 작업 기록에 대상·종류·상태·재시도 시각·점유 만료를 두어 재시작 후 복구한다.
모집·엔트리·경기 라인업·세트 결과와 참가 DM 메시지 ID를 저장한다. 종류와 대상 ID를 함께 사용해 다른 경기·수신자의 글을 바꾸지 않는다. Discord가 수신한 직후 응답이 유실된 경우도 대조·복구하며 정확히 한 번 전송됐다고 가정하지 않는다.
429 대기, 채널 삭제, 권한 회수, 임의 멘션 방지, 최종 실패 추적을 포함한다. 별도 메시지 브로커는 도입하지 않는다.

기존 Riot 프록시는 소비자를 다시 확인해 관리자 조회 등에 인증·호출 제한을 연결하거나 내부 호출만 남긴다.
Data Dragon은 실제 화면 소비와 기존 캐시를 유지한다. 서비스 기능에 필요 없는 Riot·Discord 범용 프록시를 추가하지 않는다.

## 6. DB 스키마를 먼저 정리

기존 32개에서 세션·서버별 계정 연결·경매 후보 순서를 추가해 35개 테이블의 초기 기준을 만들었다. 2026-11-05에는 게시 작업·interaction 기록을 `0001_discord_bot.sql`로 추가하고, `0003_match_results.sql`에 경기별 라인업·ROFL 등록 이력과 게시 대상 확장을 추가해 40개 테이블이 됐다.
세션·길드 신선도·revision·대진 확정·팀 순서·Match 복원·주요 업무 제약은 반영했다. 아래 표의 ROFL 예외 처리,
MMR·Discord 게시의 현재 구현과 추가 검토할 감사 이력을 구분한다. 테이블마다 CRUD API를 만들지 않는다.

| 보완 대상 | 소비 기능·결정할 저장 방식 |
| --- | --- |
| 초기 생성 기준 | 정리한 스키마 전체와 `is_service_admin`을 포함하는 초기 SQL·snapshot·journal 재생성. 기존 업무 데이터 변환 migration은 생략 |
| 세션 | `sessions`: 토큰 해시, 사용자 FK, 생성·만료. 로그아웃·만료 시 폐기 |
| 서버별 계정 연결 | `guild_riot_accounts`: 서버·계정 PK, 사용자·대표·지정자·지정 시각. Riot 식별 행과 분리 |
| 길드 활성·권한 신선도 | 봇 퇴장·사용자 탈퇴·권한 회수 판정에 필요한 활성/동기화 정보. 과거 기록과 소속 분리 |
| 동시 수정·생성 재시도 | Scrim revision, 생성 요청 식별자와 실행자 기준 고유성 |
| 편성·대진·재개 | 팀 표시 순서·활성 구분, 대진 확정 시각/실행자, 중도 종료가 변경한 Match의 복원 근거를 저장 |
| 경매 | 지속 가능한 후보 대기열 순서·상태, 유찰 등 lot 무효화 근거. `auction_teams.captain_participant_id`의 NOT NULL을 부분 설정 저장과 맞춤 |
| 업무 제약 | 팀 수·추가 정원·포인트 범위, 참가자·팀·포지션·대진 연결, 같은 내전의 직접 시드 중복, 생성 요청·lot·영입·Game 중복 방지 |
| ROFL | 같은 파일의 버전별 중복 채택과 동일 경기 식별 제약. 연결 실패를 보존·재처리한다면 선별 자료와 경기 문맥·실패 사유를 연결할 최소 구조 |
| 경기 라인업 | Match별 팀 A/B·5포지션·참가자 배치, 경기 내 사용자 중복 금지, 확정 시각·실행자·revision. 현재 팀 배정과 당시 Game 출전은 별도로 보존 |
| MMR | 기존 application·ledger·revision 제약으로 원자적 반영과 안전한 마지막 Game 역분개를 처리. 정상 경로에 별도 처리 큐·재계산 상태를 추가하지 않음 |
| Discord 게시 | 기존 내전당 모집 글 하나의 구조를 종류별 글 식별로 확장, 게시 재시도 기록 추가 |
| 감사·정정 | 계정/권한 변경 이력. 결과 정정 제공 시 채택 전후 근거·실행자·사유 추가. MMR 원장으로 모든 변경 이력을 대신하지 않음 |

경매 대기열은 조회 시 복원 가능한 단일 저장 원천을 정하고 lot 이력과 서로 다른 현재 상태를 중복 관리하지 않는다.
모집을 재개해 팀 수가 줄어도 과거 경매 이력이 참조하는 팀은 삭제하지 않는다. 현재 팀 구성과 과거 팀의 표시·활성 범위를 구분한다.
스키마 파일 분할은 관계와 책임이 안정된 뒤 필요할 때 한다. 테이블마다 별도 저장소 클래스를 만들지 않는다.

진행 순서는 **프론트 계약에 맞는 모델·제약 수정 → 초기 생성 파일 재생성 → 빈 MSM2 DB 적용 → 제약 검증**이다.
이번 초기 재작성에서는 과거 users-only migration을 보존하기 위한 단계별 ALTER 이력을 쌓지 않았다.
실행 시 대상이 업무 데이터 없는 MSM2 전용 DB인지 확인하고 해당 스키마와 Drizzle 적용 이력을 함께 초기화한다.
같은 PostgreSQL 인스턴스의 다른 프로젝트 DB·볼륨은 대상이 아니다.

모든 미확정 후속 기능의 테이블을 먼저 만들지는 않는다. 현재 프론트에 필요한 확정된 구조부터 정리하고,
ROFL 검증 결과·정책 결정에 의존하는 필드는 근거가 정해질 때 추가한다. 실제 목록·출전·시즌 순위 쿼리로 인덱스를 검토한다.
개발 seed는 별도 명령으로 실행하며 운영 코드의 자동 seed를 금지한다.
업무 데이터를 저장하기 시작한 이후의 스키마 변경부터는 데이터를 보존하는 변경 migration을 작성한다.

## 7. 프론트엔드 연결 상태와 확인된 제한

| 영역 | 현재 구현·제한 |
| --- | --- |
| 운영 데이터·인증 | 실제 서버 ID는 DB와 세션을 사용한다. 명시적 개발 샘플만 목 데이터이며 조회 실패를 목으로 대체하지 않는다 |
| 오래된 화면·동시 조작 | `expectedRevision`·현재 경매 `lotId`, 409 뒤 재조회, 수동 편성 요청 순차 처리를 구현했다 |
| 권한 표시 | 공개 조회는 60초 이내 멤버십만 관리자 힌트로 쓴다. 서버 화면 GET hook에서 만료 소속을 먼저 갱신하고 서버·내전 layout은 내부 경로 변경에도 권한을 다시 계산한다. 연동 장애 시 공개 열람은 유지하며 오래된 권한은 사용하지 않는다 |
| 경기 라인업 | 수동 확정 엔트리 자동 적용·경매 Match별 1회 확정·모든 세트 재사용·승자 포지션 전파 구현 |
| ROFL 팝업 | 실제 등록은 파일 하나·세트 블루 팀 선택. 파일별 성공/오류와 선택 해제 표시, 모든 닫기 경로에서 저장 결과 재조회 |
| 공통 확인창 | 루트 STDF Dialog 호스트와 공통 overlay로 dialog 의미·초기 포커스·최상위 Tab/Escape·중첩 배경 차단·포커스 복귀를 처리한다. 화면 이동은 대기 중 확인을 취소한다 |
| 편성 참고 자료 | 실제 MMR은 연결됐다. 시너지·상대 전적은 빈 자료이며 경매 후보 상세는 실제 서버에서 미제공 |
| 경매 수동 배치 | 현재 후보·유찰자 모두 후보 목록의 팀별 배치 버튼을 제공하며 드래그만 가능한 동작은 아님 |
| 편성의 진영 표시 | 수동 편성은 팀 이름·포지션만 표시하며 팀 순서를 진영으로 해석하지 않는다. 실제 진영은 세트 업로드에서 지정한다 |

UI 변경은 [디자인 시스템](web/design-system.md)·[패턴](web/patterns.md)에 따라 모바일·키보드·상태별 화면을 확인하고,
중복 조작·설명을 만들지 않으며 `pnpm check:branding`을 포함해 검사한다.

## 8. 최초 구현 순서와 검증 기준

아래 표는 최초 연결 작업의 순서와 검증 기준이며, 각 행 전체의 완료를 뜻하지 않는다. 현재 상태와 남은 범위는 0·1·7·9절을 따른다.
각 단계는 **저장 계약 → 서버 함수 → 라우트 연결 → 실제 화면 검증** 순서로 끝낸다.
아래 단계 번호는 의존 순서이며 기간 추정이 아니다. ROFL 식별 근거 검증은 초기에 병행해 자동 등록의 가능 범위를 먼저 확정한다.

| 단계 | 작업 | 완료 기준·다음 단계 의존 |
| --- | --- | --- |
| 0. DB 정리·계약 검증 | 프론트와 스키마의 확정된 차이 수정, 초기 SQL·Drizzle 기준 재생성·빈 DB 적용. 선행 정책과 ROFL 식별 fixture 검증 병행 | 현재 화면의 상태·이력·ID·제약을 DB로 표현. ROFL 조사 결과는 7단계 출시 조건이며 DB 정리 전체를 막지 않음 |
| 1. 인증 기반 | 세션, OAuth, guard, 봇 소속·권한 조회/동기화, 공통 오류 | 정리된 DB에서 실제 로그인·로그아웃, 권한 회수·교차 길드 차단 |
| 2. 서버·계정 관리 | `/me`, 서버별 Riot 조회·연결·대표·해제, Discord 설정 | 재시작 후 보존, 서버 간 연결 격리·동시 연결·권한 변경 검증 |
| 3. 모집·신청 | 내전 생성·목록·상세, 신청·선발·대기·철회, 설정·마감·취소 | 마지막 자리 동시 신청에도 정원 준수, 신청 이력 보존, 봇과 공유할 서비스 준비 |
| 4. 수동 편성 | 배정·교환·초기화·확정, 방식 변경·복귀 | 드래그 저장·재조회·충돌 복구, 전원 배정 검증, ready와 대진 초안 연결 |
| 5. 경매 | 팀장·포인트·대기열·lot·낙찰·유찰·수동 영입·되돌리기 | 중복 후보·초과 지출 방지, 재시작 복원, 완료·복귀와 이력 보존 |
| 6. 대진·경기 | 배치·BO·확정·해제·시작, 실제 Match·조회·종료 | 2/3/4팀 구조, 미정 결승 지연 생성, 시작 후 잠금, 중도 종료 기록 보존 |
| 7. ROFL 영구 저장 | 기존 파서·적재 모델 연결, 검증·멱등성·점수·승자 진출 | 동시 업로드·응답 유실에 중복 없음, 다음 Match 생성까지 원자성. 확정 경기·세트·라인업 및 파일 연결 검증 필수 |
| 8. MMR·전적 | 시즌 고정, 자동 반영·안전한 역분개, 전적·통계·순위, nullable DTO | 하나의 Game이 모든 화면에서 같은 결과, 원장·현재값 일치, 경기별 라인업 확정과 파일 참가자 대응 검증 |
| 9. 봇 업무·운영 | 참가 interaction, 게시·재시도, 예외 재처리 절차, 배포·관측 | 웹/봇 동일 규칙, 재시작·외부 장애 복구, 운영 모드 전체 흐름 확인 |

2~6단계의 읽기 화면은 각 쓰기 기능과 함께 연결한다. 8단계에서 개인/서버 집계와 순위를 완성한다.
봇 모집 연동은 3단계 완료 후, 엔트리 게시와 결과 게시도 각각의 의존 기능 완료 후 병행할 수 있다.
시즌 생성·전환, 서비스 운영자 최초 지정, 보류·정정 처리는 첫 릴리스에서 인증·감사 가능한 운영 명령으로 제공하는 안을 우선한다.
현재 UI에 없는 운영 대시보드·시즌 설정·수동 MMR 편집 화면을 미리 만들지 않는다.

## 10. 검증과 운영 전환

### 10.1 반드시 검증할 시나리오

API 테스트는 [lite/hard 구조](testing.md)로 재작성했다. lite는 단순 규칙·고정 응답 계약, hard는 격리 PostgreSQL의 실제 서비스와 SvelteKit HTTP 요청을 검증한다.
기존 프론트·ROFL 회귀 테스트는 별도로 보존한다. 2026-11-03 실제 실행에서 lite 324개와 DB·HTTP hard 199개가 모두 통과했다.
아래 표는 구현 범위의 검증 기준이며 최신 실행 결과는 [테스트 문서](testing.md)를 따른다.

| 영역 | 핵심 검증 |
| --- | --- |
| 인증·권한 | 세션 만료·폐기, OAuth state 재사용, 비소속/다른 길드 ID, 권한 회수 후 직접 action 호출 |
| 계정·설정 | 같은 서버의 동시 연결·대표 지정, 다른 서버의 독립 연결, 해제와 신청의 경쟁, 해당 서버 활성 신청 계정 해제 차단, 역할/채널 삭제, 설정 변경 후 실행자 권한 |

최종 흐름은 실제 로그인한 두 사용자 이상으로 **모집 → 신청 → 수동/경매 편성 → 드래그 대진 배치 → 시작 → ROFL 업로드 → 승자 진출 → 종료**를 각각 수행한다.
동일 Game이 경기 상세·대진·홈·개인 전적·통계·MMR에 일관되게 나타나고 프로세스 재시작 후에도 유지되어야 한다.
모바일·키보드·실패 후 재시도·브라우저 두 개의 동시 조작도 확인한다.

### 10.2 배포와 완료 조건

아래는 출시를 위한 후속 기준이다. 현재 저장소의 배포 구성은 nginx 내부 경로 차단 예제와 수동 실행 안내이며, 프로세스 관리·HTTPS 전체 구성·CI·DB 백업/복구 구성은 제공하지 않는다.

- 구현 단계마다 타입·브랜딩 검사, 관련 단위/DB 통합 테스트를 통과시킨다. 최종 연결에서는 `pnpm check`, `pnpm --filter @msm2/web test`, `pnpm build`와 브라우저 흐름을 확인한다.
- `deploy/`에 VPS 실행·역방향 프록시·HTTPS·웹/봇 재시작·내부 주소 차단·요청 크기/시간 제한을 정리한다. 개발 바로가기와 목 데이터가 운영 자료를 만들지 않게 한다.
- 초기 스키마 적용과 새 환경 재현을 확인한다. 운영 데이터 생성 이후에는 DB 백업·복구와 변경 migration 적용·실패 복구 절차를 검증한다. 앱 기동 시 자동 스키마 초기화를 하지 않는다.
- DB statement/query timeout과 외부 요청 timeout을 맞추고, 업로드 처리 수·DB 풀·게시 재시도를 제한한다. 상태 화면에서 반환만 끝내고 실제 작업이 무한히 남지 않게 한다.
- 요청 ID·업무 오류 코드·처리 시간·보류/재시도 수를 기록한다. 원본 ROFL·세션·OAuth/Riot/봇 토큰은 수집하지 않는다. 게시 실패는 운영자가 찾아 복구할 수 있어야 한다. 정상 ROFL은 MMR까지 원자적으로 저장하며 별도 MMR 보류 큐를 운영하지 않는다.
- 완료한 기능의 목 의존을 제거하고 [웹 문서](web/README.md)·[DB ERD](database-erd.md)·환경 변수 예제를 실제 코드에 맞춘다. 미구현 계획을 현재 기능처럼 표시하지 않는다.

**전체 완료 기준:** 기존 프론트엔드의 모든 실제 조회·form action과 MSM1 준용에 필요한 경기 라인업·정정 기능이 권한 검증·영속 저장·오류 처리로 연결되고,
ROFL 자동 결과 등록과 대진·전적·MMR·Discord 후속 처리가 검증 가능한 근거로 작동하며,
동시 요청·재시작·외부 장애가 중복 기록이나 기록 손실을 만들지 않는 상태다.

| 6 | 수정된 동작을 문서에 다시 반영하고 전체 회귀 검증. 새 migration을 격리 DB에서 먼저 검증한 뒤 개발 DB에 적용 | 기본/lite·hard·타입·브랜딩·포맷·웹/봇 빌드, 주요 뷰포트·상호작용, 테스트 schema/프로세스 정리 확인 | 완료 |

스키마 변경은 1단계에서 `0004`로 추가한다. ROFL 메타데이터는 파일의 선별 근거이고, Game별 제출 이력은 별도 행으로 관리한다.
취소된 근거를 다른 경기나 다음 세트에 재사용하지 않으며, 같은 세트라도 최신 운영 문맥이 아닌 과거 요청으로 결과를 되살리지 않는다.
각 단계는 관련 회귀 검증을 통과한 뒤 다음 단계로 진행하고, 문서에 적힌 미해결 제한은 해당 수정이 확인된 시점에 갱신한다.

최종 검증은 기본 웹 414개·봇 63개, DB·HTTP hard 312개가 모두 통과했다. 타입·브랜딩·포맷·웹/봇 빌드와 주요 브라우저 동작도 확인했다. 개발 DB는 `0004`까지 적용 후 40개 테이블·88개 FK·업무 행 0개이며, 테스트 schema·연결·HTTP 프로세스는 남지 않았다. 세부 범위와 실행 기록은 [API 테스트 문서](testing.md)를 따른다.

### 11.2 별도 기능 보완 순서

다음은 위 재현 결함과 구분되는 미완성 기능이다. 현재 완료 상태로 표시하지 않는다.

1. **MSM1 예외 운영:** `d60df685`의 실제 행위 기록을 기준으로 경매 추첨·유찰 복귀·수동 배치까지 마지막 행위 취소를 구현한다. 내전 취소 복구와 중도 종료의 단계·현재 우세 팀 처리는 결과/MMR/다음 대진을 함께 보존·역분개하는 경계로 설계한다. 현재 중도 종료 복귀는 이미 구현됐다.
2. **시즌 운영:** 최초 시즌 준비와 별개로 종료·다음 시즌 생성·기본 조회 시즌 선택을 추가한다. 기존 내전에 고정한 시즌과 과거 MMR 원장을 바꾸지 않고, 중복 전환·진행 중 내전·동시 결과 등록 조건을 먼저 정한다.
3. **편성 참고 정보:** 현재 시즌의 유효 ROFL 실출전에서 팀 시너지·상대 전적·경매 후보 상세를 조회한다. 데이터 없음과 조회 실패를 구분하고 목 수치나 미정 평점을 합성하지 않는다.
4. **출시 준비:** 프로세스 관리·HTTPS·CI·DB 백업/복구 구성을 저장소에서 재현 가능하게 준비하고 지정 환경에서 검증한다. 약관·개인정보 처리방침의 확정 본문과 문의 경로는 운영 정보를 받아 작성한다. 실제 Discord 검증은 현재 제외 지시가 해제된 뒤 수행한다.
