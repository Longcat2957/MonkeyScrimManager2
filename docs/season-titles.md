# 칭호 확정 명세: 시즌 15종 · 한 세트 10종 · Bo3 2종

**상태: 총 27종 명칭·조건 확정, 운영 미구현.** 시즌 칭호는 같은 서버·시즌의 1위 기록이며 새 결과나 정정으로 보유자가 바뀐다. 한 세트·Bo3 칭호는 해당 경기에서 조건을 달성한 출전자에게 귀속되며 시즌 순위를 요구하지 않는다. MVP/ACE·종합 평점은 포함하지 않는다.

### 공통 판정

- 기본은 활성 시즌, 과거 시즌 선택 시 그 시즌만 사용한다. 귀속은 내전의 `mmrSeasonId` 기준이다. 업로드 시각·경기일·현재 Riot 계정 연결·모집 명단으로 추정하지 않는다.
- 표본 기준은 해당 칭호에서 **분자와 분모를 모두 계산할 수 있는** 세트/시리즈 수다. 누락을 0으로 채우지 않고, 실제 기록된 0은 보존한다. 분모가 0이거나 시간이 없으면 해당 비율에서만 제외한다. 분당 값은 세트별 분당 값의 평균이 아니다.
- 팀 지분과 킬 관여율의 팀 합계는 해당 세트 같은 진영의 실제 5명에게 필요한 값이 모두 있을 때만 계산한다. `가성비 킹`은 다섯 포지션별 순위이며 한 선수가 여러 포지션에서 보유할 수 있다. 예: 피해 지분 30%, 골드 지분 20%면 그 세트는 +10%p다.
- 원래 값으로 비교하고 표시할 때만 반올림한다. 공동 1위는 모두 보유자이며 표본 수·이름·조회 순서로 승자를 가르지 않는다. `원챔`에서 한 선수의 최다승 챔피언이 여럿이어도 같은 칭호를 중복 부여하지 않는다. 자격자가 없으면 해당 칭호에는 보유자가 없다.
- 시즌·서버가 같으면 어느 화면에서도 보유자가 같다. 통계의 포지션·최소 게임·최근 10게임, 개인 전적의 포지션·쪽 번호는 시즌 칭호 계산을 바꾸지 않는다.

## Bo3 칭호 2종

| 번호 | 표시 이름 | 정상 종료 Bo3 획득 조건 |
| --- | --- | --- |
| 17 | 삼꽉의 악마 | 1세트 패배 후 2·3세트를 모두 이긴 팀의 출전자 5명. 승패승은 해당 없음 |

기존 후보 19·20번은 제외한다. 한 세트 판정은 채택된 유효 ROFL과 확정 출전 포지션으로 비교한다. 필요한 수치가 누락되면 해당 칭호만 판정하지 않는다. Bo3는 유효 세트를 번호순으로 읽고 진영이 바뀌어도 고정 팀을 기준으로 비교한다. 결과 취소·재등록 후 무효가 된 달성 기록은 표시하지 않는다.

## 전체 구현 순서

1. 세 범위에 서로 다른 고정 ID를 부여한다. 시즌 결과의 식별 단위는 `(시즌, 칭호, 비교 포지션, 선수)`, 단발 달성은 `(세트 또는 시리즈, 칭호, 선수)`다. 한 세트에서 여러 칭호를 동시에 획득할 수 있다. 같은 펜타킬 칭호를 다른 세트에서 다시 얻는 것도 별도 기록이다. 표의 번호나 표시 이름은 키로 사용하지 않는다.
2. 기존 읽기 권한 안에서 서버·내전·경기·채택된 ROFL을 제한하는 SQL 조건을 공유한다. 시즌 순위용 조회와 단발 달성용 조회는 분리한다. 경기 하나를 열 때 시즌 전체를 집계하지 않는다. 별도 배지 발급 테이블이나 업로드 후처리 없이 유효 기록에서 파생한다.
3. 시즌 순위 SQL, 세트 판정 SQL, 정상 종료 Bo3 판정 SQL을 각각 구현하고 DB fixture로 검증한다. 칭호별 27회 조회 대신 각 조회가 해당 범위의 모든 조건을 평가한다. 칭호명과 단위는 고정 ID에 대응시키고 TypeScript에서 재판정하지 않는다.
4. 홈·통계·개인 전적에는 시즌 보유자를, 경기 상세에는 세트·시리즈 달성자를 연결한다. 숫자와 공개 신원을 분리하고 기존 명부·점수판과 같은 읽기 권한을 적용한다. 세 범위의 프로파일링과 정정 시나리오가 모두 통과한 뒤 운영에 반영한다.

### 한 세트 10종: 선택한 세트의 달성자

- `(서버, 경기, 세트)`로 좁힌 뒤 `gameParticipants`와 채택 ROFL의 참가자 통계를 조인한다. 양쪽 실제 포지션을 짝지어 `TOP DIFF`의 총 CS와 `협곡의 진공청소기`의 정글 몬스터 CS를 구분한다. 상대 포지션이 없으면 그 비교만 제외한다.
- 한 번 읽은 세트에서 진영별 팀 킬·챔피언 피해 합, 양 팀 개인 딜 최댓값과 해당 값의 인원 수를 계산한다. 팀 합계에는 해당 팀 5명의 입력이, 양 팀 비교에는 양쪽 입력이 모두 있어야 한다. `오만이횽이야`는 패배한 **단독** 1위만, `하지만 이겼죠?`는 최종 킬 차가 조건을 만족한 승리 팀 **5명 모두**에게 준다. 중간에 몇 킬 뒤졌었는지는 추정하지 않는다.
- 나머지는 표의 승패·포지션·시간·K/D/A·팀 지분 조건을 적용한다. `Last Man Standing`은 `pentaKills >= 1`이며 승패나 마지막 생존 여부를 보지 않는다. 시간·비율 경계는 표시용 반올림 없이 원값으로 비교한다. 결과는 달성한 `(gameId, 칭호 ID, 선수, 근거 수치)`만 반환한다.

### Bo3 2종: 정상 종료한 한 시리즈의 달성자

- 선택한 `matchId`의 유효 세트만 순서대로 읽어 세트별 진영을 고정 팀 A/B로 환산한다. 정상 종료·확정 승자·선승 점수가 일치하는 Bo3만 평가한다. 절대 경기 시각은 필요 없다.
- `삼꽉의 악마`: 시리즈 승리 팀 관점에서 순서가 정확히 패·승·승이면 그 팀 출전자 5명에게 준다. 승·패·승이나 단순 2:1은 해당하지 않는다.
- `공무원`: 2:0 승리 팀의 바텀·서포터를 확정 포지션으로 찾는다. 두 세트 모두 양쪽 듀오의 데스 4개가 유효해야 한다. 세트별로 승리 팀 듀오 합계가 엄격히 작은지 검사한다. 한 세트라도 같거나 크면 탈락이다. 통과하면 승리 듀오 2명에게만 준다.
- [경기 상세](../apps/web/src/lib/server/matches/queries.ts)의 같은 읽기 시점에 선택 세트 점수판에는 해당 세트 칭호를, 시리즈 결과에는 Bo3 칭호를 한 번만 표시한다. 시리즈 진행 중에도 정상 등록된 세트 칭호는 보인다. 정상 종료 전에는 Bo3 수상자를 만들지 않는다. 취소·재등록 후에는 원래 세트의 달성이 사라지고 새 결과만 남는다.

### 시즌 15종: 선택한 시즌의 보유자

1. **유효 기록을 PostgreSQL에서 먼저 좁힌다.** [전적 조회](../apps/web/src/lib/server/records/queries.ts)와 같은 조건으로 서버·선택 시즌·미취소 내전과 경기·완료 세트를 고른다. `gameId`와 채택된 `roflMetadataId`가 모두 일치하는 실제 출전자만 조인한다. 중도 종료 전 정상 등록 세트는 1~13번에 남긴다. 시즌 전체 `PlayerGame[]`나 ROFL JSONB를 칭호 계산용으로 앱에 전송하지 않는다. SQL 안에서 [ROFL V1 저장 필드](../apps/web/src/lib/server/rofl/import-model.ts) 중 필요한 숫자만 읽는다. 원본 재파싱·재업로드는 필요 없다.
2. **시리즈는 세트와 따로 센다.** 조회가 이미 조인하는 `matches`에서 BO 형식·상태·고정 팀·승자를 가져온다. [경기 기록](../apps/web/src/lib/server/matches/queries.ts)의 정상 종료 판정(확정 승자와 유효 세트 점수 일치)을 재사용한다. 14·15번만 `bestOf = 3`으로 제한한다. `matchId`로 묶고 취소되지 않은 `gameNumber`로 순서와 1:1을 확인한다. 블루/레드가 아니라 서비스 팀으로 각 세트 승자를 맞춘다. 14번은 3세트 승리 실출전자에게, 15번은 실제 출전한 사용자마다 `(matchId, 사용자)`당 한 번만 승패를 반영한다. 부전승·몰수처럼 유효 ROFL 점수로 완결되지 않은 경기는 포함하지 않는다.
3. **SQL에서 보유자까지 결정한다.** 유효 세트·출전자 → 세트/진영별 5인 합계 → 선수별 집계와 선수/포지션·선수/챔피언별 집계 → 칭호별 후보 → 순위 순으로 구성한다. 시리즈 집계는 세트 집계와 분리해 5인 조인으로 승수가 늘어나지 않게 한다. `FILTER`, `COUNT`, `NULLIF`로 칭호별 유효 표본·분모를 계산한다. 평균·비율은 `numeric`으로 비교하고 화면용으로 반올림한 값으로 정렬하지 않는다. `RANK() OVER (PARTITION BY 칭호, 비교 포지션 ORDER BY 점수 DESC)`로 공동 1위를 보존한다. 개인 필터·상위 순위 제한은 순위 결정 뒤에만 적용한다. 시즌마다 15번 조회하지 않고 한 번의 매개변수화된 집계에서 실제로 필요한 순위 행만 반환한다. TypeScript는 권한 확인·공개 표시 변환·단위 포맷을 맡고 [임시 랭커](../apps/web/src/lib/features/players/achievements.ts)로 재계산하지 않는다.
4. **세 화면을 같은 결과로 전환한다.** [통계 스냅샷](../apps/web/src/lib/server/stats/snapshot.ts)의 `scoped` 리더보드와 분리하고 최초 SSR·기존 `stats/live`가 같은 순위를 반환하게 한다. 응답 타입과 클라이언트 검증기도 함께 바꾼다. [서버 홈](../apps/web/src/routes/g/%5BguildId%5D/+page.server.ts)은 선택 시즌의 보유자를 읽되 다음 내전·현황에는 시즌 필터를 적용하지 않는다. [개인 전적](../apps/web/src/routes/g/%5BguildId%5D/players/%5BuserId%5D/+page.server.ts)은 같은 순위에서 해당 선수 배지만 꺼낸다. 백분위의 기존 4게임 기준은 유지한다. 개발 미리보기에는 같은 결과 계약의 샘플만 사용하고 운영에서 샘플로 대체하거나 별도의 TypeScript 점수 공식을 유지하지 않는다.
5. **기존 카드·순위창·배지의 단독 1위 전제를 제거한다.** 카드와 순위창에는 공동 1위 여부·값·표본 단위(세트/시리즈)를 전달한다. `가성비 킹`은 포지션을 구분하고, 공통 ‘최소 4게임’ 안내와 최근 10게임 업적 필터는 제거한다. 통계 리더보드 필터는 유지한다. 빈 시즌/자격자 없음은 오류와 구분하고, 조회 실패를 샘플 데이터로 대체하지 않는다. 서버 내부에서만 실출전자별로 집계한 뒤 기존 `readPublicIdentities`와 공개 표시 이름·링크 정책을 적용한다. 비공개·탈퇴자의 Discord ID, 실명성 표시 이름, Riot ID가 공개 응답에 새지 않게 한다.

6. **최적화 순서는 SQL, 인덱스, 결과 캐시다.** 캐시가 비었을 때도 목표 응답 시간을 만족하는 SQL을 먼저 만든다. 별도 수상 테이블·주기적 전체 재계산·Redis는 기본 구성에 넣지 않는다. 아래 측정에서 반복 조회 비용이 목표를 넘을 때만 결과 캐시를 추가한다.

### SQL 작성·실행 경계

칭호 집계 본문은 Drizzle 쿼리 빌더로 조립하지 않는다. 서버 전용 조회 모듈에 PostgreSQL의 `WITH`, `JOIN`, `GROUP BY`, 윈도 함수가 보이는 **순수 SQL 문장**을 작성하고, [기존 실행 방식](../apps/web/src/lib/server/accounts/lifecycle.ts)처럼 Drizzle의 `sql` 태그와 `tx.execute(...)`로 감싼다. 길다는 이유만으로 별도 SQL 파일 로더나 저장 프로시저를 도입하지 않는다. 이 결정은 칭호 집계에만 적용하며 기존 접근 검사·일반 조회를 일괄 재작성하지 않는다.

- 서버 ID·선택 시즌 ID 등은 `sql` 템플릿의 바인드 값으로 전달한다. 요청값을 문자열에 이어 붙이거나 `sql.raw`에 넣지 않는다. SQL은 고정된 결과 열과 단위를 반환하고 TypeScript는 드라이버의 `numeric`·`bigint` 표현을 안전하게 읽는다. 순위를 JS 숫자로 다시 비교하지 않는다.
- 프로파일링은 별도 복사본이 아니라 **서비스가 실행할 동일 SQL과 바인드 값**에 `EXPLAIN`을 붙여 실행한다. 실행 계획과 반환 행을 같은 커밋의 쿼리에 연결해 기록한다.

## SQL 프로파일링과 인덱스 채택 기준

- **비교 조건 고정:** 배포와 같은 PostgreSQL 주 버전·설정의 격리 DB에서 빈 시즌, 일반 시즌, 예상 최대 시즌을 준비한다. 다른 서버·시즌의 기록, 취소 이력과 동점자도 함께 넣는다. fixture 크기(시즌·세트·참가 행 수), 설정, `ANALYZE` 시점, 측정 횟수·동시 요청 수를 결과에 기록한다. 측정 전 SQL별 p95와 30초 갱신 동시 부하의 허용 시간을 정한다.
- **각 SQL을 따로 측정:** 화면별 실제 바인드 값으로 권한/시즌 조회, 칭호 집계, 공개 신원 일괄 조회, 도입 시 캐시 버전 조회까지 SQL별 `EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT JSON)`을 보관한다. 추정/실제 행 수, `loops`, shared hit/read, temp read/write, 정렬·해시 spill, 계획·실행 시간을 본다. CTE 재스캔, 범위를 좁히기 전 JSONB 추출, 조인 행 증폭이 있으면 먼저 쿼리를 고친다. 작은 시즌의 순차 스캔 자체는 결함이 아니다.
- **요청 전체도 측정:** 실행 계획과 별도로 반복 실요청의 p50/p95, DB 왕복 수, DB 반환 행·바이트, 최종 응답 크기를 기록한다. SSR과 `stats/live`의 기존 리더보드 조회까지 포함해 시즌 원장 중복 읽기가 새 병목인지 확인한다. 차가운 DB 버퍼와 반복 실행을 구분하고, OS 페이지 캐시까지 통제하지 않았다면 디스크 콜드 측정이라고 쓰지 않는다. 운영 캐시는 비우지 않는다.
- **인덱스는 가설별 A/B:** [현재 스키마](../apps/web/src/lib/server/db/schema.ts)에 `scrims_guild_id_idx`, `scrims_mmr_season_id_idx`, `(scrim_id, id)`·`(game_id, side, position)` 유일 제약 등이 있다. 이들이 실제 조인을 지원하는지 먼저 확인한다. 예컨대 시즌 진입에서 불필요한 행을 많이 읽을 때만 `scrims(guild_id, mmr_season_id)` 후보를 비교한다. 완료 세트 선택이 병목이면 해당 조인 키의 부분 인덱스를 별도로 시험한다. JSONB 숫자를 합산한다는 이유만으로 GIN이나 지표별 인덱스를 추가하지 않는다.
- **배포 게이트:** 같은 데이터·부하에서 변경 전후 결과 행의 일치, SQL별 계획, p95·버퍼 읽기·임시 쓰기, 인덱스 크기와 ROFL 등록/정정 쓰기 지연을 한 표에 남긴다. 읽기 개선이 없거나 쓰기 예산을 초과하면 후보를 버린다. 채택한 인덱스만 마이그레이션으로 만들고, 운영 크기에서 생성 시 잠금·소요 시간과 제거 절차까지 검증한다. 근거 없는 인덱스나 측정하지 않은 SQL은 운영에 반영하지 않는다.

## 캐시: 같은 시즌의 재사용과 정정 직후 정확성

- **두 종류의 적중을 분리한다.** PostgreSQL의 shared buffer hit는 페이지 재사용이지 집계 생략이 아니다. 결과 캐시의 hit는 **그 요청에서 칭호 집계 SQL을 실행하지 않은 것**으로 센다. 시즌을 보는 세 화면과 30초 폴링이 같은 결과를 재사용하는 게 목표다.
- **캐시 단위:** 결과 캐시가 필요하면 `(서버 ID, 해석된 시즌 ID, 집계 규칙 버전, 결과 revision)`별 상위 순위와 모든 공동 1위의 내부 숫자 결과만 저장한다. 페이지·포지션·최소 게임·최근 필터·사용자별로 같은 집계를 쪼개지 않는다. 한도 밖의 공동 1위도 자르지 않는다. 이름·아바타·공개 링크·권한은 캐시하지 않고 매 요청 접근 검사 뒤 반환할 사람만 일괄 변환한다. `stats/live`의 `private, no-store`는 유지한다.
- **정확성:** 캐시를 도입할 때만 서버·시즌별 revision을 둔다. ROFL 등록·취소·재등록과 집계 자격을 바꾸는 내전/시리즈 상태 변경은 같은 DB 트랜잭션에서 해당 시즌 revision을 갱신한다. 롤백은 올리지 않는다. 활성 시즌 전환은 먼저 실제 시즌 ID를 다시 해석한다. 버전과 집계는 일치하는 DB 스냅샷에서 읽고, 이전 계산이 늦게 끝나도 새 버전 키를 덮지 못하게 한다. TTL이나 최신 업로드 시각만으로 정정을 판별하지 않는다.
- **적중과 비용:** 프로세스 내 용량 제한 캐시부터 검토한다. 동일 키 동시 miss는 프로세스당 한 계산을 공유하고, 실패는 저장하지 않는다. 이전 버전은 용량·TTL로 회수한다. 여러 인스턴스는 DB revision을 확인해 오래된 값을 반환하지 않되 각자 처음 한 번은 miss일 수 있다. 공유 캐시 도입 여부는 그 중복 비용을 측정해 판단한다.
- **배포 전 시나리오:** 결과가 안 바뀐 시즌에서 홈 → 통계 → 개인 → 자동 갱신을 반복해 SQL 실행 횟수, hit/miss 및 적중률, hit/miss별 p95, DB revision 조회 비용, 캐시 메모리·퇴출 수를 기록한다. 필터 변경은 hit, 시즌/서버 변경은 별도 키, 정정 커밋 후 첫 조회는 새 보유자, 그다음은 hit여야 한다. 동시 miss, 계산 중 정정, 프로필 비공개 전환, 두 인스턴스에서도 같은 기준을 검사한다. 높은 적중률만으로 통과시키지 않는다.

경기 상세는 시즌 순위 캐시를 읽지 않는다. 한 세트 10명·Bo3 최대 3세트의 직접 조회를 기준선으로 삼는다. 반복 조회가 실제 병목일 때만 `(범위, 서버, 경기, 선택 세트 또는 시리즈, 규칙 버전, 유효 결과 버전)`으로 캐시한다. 경기·내전 취소와 정정까지 포함한 버전을 보장할 수 없으면 캐시하지 않는다. 정정 트랜잭션이 시즌 순위와 단발 달성 양쪽에 반영되는지 검사한다.
