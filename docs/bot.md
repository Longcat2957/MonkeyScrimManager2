# Discord 봇

구현 범위: 모집 생성·개인 신청·모집/팀 구성/경기 라인업/ROFL 결과 게시·운영자 요청 참가 안내 DM·Gateway 동기화·게시 복구.
업무 규칙과 DB는 SvelteKit 서버가 소유한다. 역할과 저장 구조는 [봇 계획](bot-plan.md)을 따른다.

## 설정과 실행

`apps/bot/.env.example`을 `apps/bot/.env`로 복사한다. `.env`는 Git에서 제외한다.

| 변수 | 설정 |
| --- | --- |
| `DISCORD_TOKEN` | 웹 `DISCORD_BOT_TOKEN`과 같은 봇 계정의 토큰 |
| `DISCORD_APPLICATION_ID` | 해당 Discord 애플리케이션 ID. 명령 등록에 필요 |
| `DISCORD_TEST_GUILD_ID` | 명령을 등록할 테스트 서버 ID |
| `BOT_INTERNAL_TOKEN` | 32자 이상의 난수 키. 웹의 같은 변수와 동일하게 설정 |
| `BOT_API_URL` | SvelteKit 내부 주소. 기본 `http://127.0.0.1:3000`; 웹 개발 서버를 쓸 때는 포트를 5173으로 변경 |
| `WEB_ORIGIN` | 사용자가 열 웹 주소. 운영에서는 실제 HTTPS origin |
| `BOT_STATUS_PORT` | 선택 사항. 같은 호스트의 웹이 상태를 조회할 로컬 포트 |

Developer Portal에서 Server Members Intent를 활성화한다. 봇은 `Guilds`, `GuildMembers`로 이벤트를 받고 일반 메시지 본문은 읽지 않는다.
앱은 서버 설치로 초대하며 명령과 봇을 사용할 수 있어야 한다. 게시 채널에서는 보기·메시지 전송·메시지 기록 읽기 권한이 필요하다.
웹에서도 같은 채널의 실제 게시 권한을 확인한다. 모집은 모집 채널, 팀 구성과 확정 출전 명단은 엔트리 채널, ROFL 결과는 결과 채널을 사용한다.

```sh
pnpm dev
pnpm dev:bot
```

두 명령은 별도 터미널에서 실행한다. 운영에서는 웹을 먼저 준비하고 봇을 실행한다.

```sh
pnpm build
pnpm start
pnpm start:bot
```

웹 운영 프로세스는 `HOST=127.0.0.1`로 열고 프록시에서 `/internal/`을 차단한다.
[nginx 설정 예제](../deploy/nginx-internal.conf.example)를 실제 HTTPS server 블록에 포함한다.
앱의 프록시 프로토콜 인식 설정은 실제 배포 환경에 맞춘다. 내부 인증 키를 클라이언트 환경 변수나 URL에 넣지 않는다.

## 명령 등록과 동작

명령 등록은 실제 Discord 상태를 변경한다. 봇 기동 시 자동으로 등록하지 않는다.
테스트 서버를 확인한 뒤 아래 명령을 명시적으로 실행한다.

```sh
pnpm bot:register
```

운영 전역 명령 등록은 `pnpm bot:register --global`로 구분한다. 다른 앱의 ID와 토큰을 섞어 사용할 수 없게 검증한다.

| 명령 | 동작 |
| --- | --- |
| `/초기설정` | 현재 서버 관리자 확인 후 최초 `시즌 1`을 준비하고 웹 관리 링크 표시. 활성 시즌은 재사용하며 종료된 시즌을 임의로 재개하지 않음 |
| `/내전모집` | 제목·한국 시각 일정·팀 수·추가 대기 정원·하드 피어리스로 생성. 편성 방식은 웹에서 선택 |
| `/내전목록` | 현재 서버의 웹 내전 목록으로 이동 |
| `/게시복구` | 관리자가 실패 작업을 제목으로 선택해 재시도. 불명 전송은 기존 메시지 ID 또는 해당 글이 없다는 명시적 확인 필요 |

채널·운영자 역할·Riot 계정 연결은 웹 서버 관리에서 설정한다. 관리자 권한은 현재 Discord 권한/운영자 역할로 다시 확인한다.
봇 참가에는 웹 로그인 세션을 만들지 않는다. Discord interaction의 사용자와 실제 서버 소속을 사용하며 서버별 계정 연결을 검사한다.

공개 모집 글의 `내 신청`은 본인에게만 입력 화면을 연다. 계정이 여러 개면 선택하고 희망 포지션은 하나 이상 고른다.
선택만 바꾸면 저장되지 않으며 제출 후 선발/대기 상태를 확인한다. 같은 화면에서 수정·철회할 수 있고 마감 후에는 조회만 제공한다.
개인 입력 화면은 10분 또는 봇 재시작 후 만료될 수 있다. 공개 글의 버튼으로 다시 열면 된다.
웹에서 바꾼 신청·선발·설정·모집 단계도 같은 게시 글에 반영된다.

## 게시와 복구

게시 작업은 업무 저장과 같은 트랜잭션에 기록하고 봇이 한 개씩 처리한다. 채널 미설정/전송 실패가 업무 저장을 취소하지 않는다.
수동 편성 확정 또는 경매 완료 후 팀 구성 카드를 게시한다. 되돌리기/취소 시 이전 확정 글도 제거하거나 갱신한다.
일반 내전의 경기 라인업은 확정된 수동 편성에서 자동 준비되고, 경매 내전은 경기별로 한 번 확정한다. 같은 Match의 BO 전체에서 재사용하며 매 세트 다시 확정하지 않는다.
경기 라인업 카드는 확정된 팀별 출전자·포지션만 표시한다. 팀의 색이나 희망 포지션으로 실제 경기 진영/출전 포지션을 추측하지 않는다.

ROFL 결과 저장과 MMR·대진 처리가 성공하면 Game별 결과 카드를 예약한다. 실제 세트 번호·진영·승자·챔피언·KDA·시리즈 점수를 표시한다.
기존 글의 점수는 같은 메시지에 갱신한다. 결과 정정으로 취소된 Game의 글을 삭제한 뒤 새 결과를 게시하며, 이전 글이 전달 불명이면 대조가 끝날 때까지 새 결과는 대기한다.
게시 형식은 Discord 네이티브 Components V2 카드다. 별도 결과 이미지를 생성하지 않는다.

참가 안내 DM은 웹 내전의 운영 메뉴에서 `참가 안내 보내기`를 실행했을 때만 예약한다. 모집 마감 후 준비·진행 중인 내전에서 현재 선발된 Discord 사용자만 대상이다.
같은 내전의 같은 사용자에게 반복 요청해도 새 DM을 만들지 않는다. 이후 새 선발자가 생기면 다음 요청에서 그 사람만 추가한다.
작업 점유 시 선발 상태와 내전 단계를 다시 검사하고, 발송 전에는 실제 서버 멤버와 DM 채널 수신자를 확인한다. 대기·철회자에게 자동 안내하지 않는다.
웹은 대기·발송 완료·실패·전달 불명 건수를 보여 준다. 예약 성공은 실제 수신 완료를 뜻하지 않는다.

429·일시 장애는 다음 시도를 예약한다. 권한 회수·채널 삭제 등은 `blocked`, 신규 글이 전송됐는지 알 수 없으면 `uncertain`으로 남는다.
`/게시복구`에서 작업과 대상 채널을 확인한다. 이미 게시된 글이 있으면 메시지 ID를 전달하고, 없음을 확인했을 때만 새 게시를 허용한다.
메시지 ID를 받으면 웹 서버가 해당 채널·봇 작성자·내전 링크를 대조한다. 경기 라인업·결과·DM은 링크의 게시 작업 식별자도 일치해야 한다.
복구 요청 역시 interaction ID로 중복 효과를 방지한다. DM 수신 차단은 실패로 남으며 반복 발송하지 않는다.
불명 DM의 글없음확인은 수신자에게 안내가 없음을 확인한 뒤 사용한다. 프로세스 중단으로 DM 채널 정보까지 유실됐다면 메시지 ID 대조를 사용할 수 없고 부재 확인이 필요하다.

채널 변경은 이전 글을 정리한 뒤 새 위치로 게시한다. 이전 글 접근 권한을 잃었다면 먼저 권한 또는 채널 상태를 정리한다.
기존 글이 삭제되어 편집이 404로 실패하면 `MESSAGE_MISSING`으로 보류한다. `/게시복구`에서 글없음확인을 전달해 기존 메시지 ID를 지운 뒤 새 작업으로 생성한다.
게시 작업의 점유 만료와 오래된 응답은 토큰·버전으로 검사한다. Discord 전달을 영구적으로 정확히 한 번 보장한다고 가정하지 않는다.

## 검증

```sh
pnpm test:bot
pnpm test:lite
pnpm test:hard
pnpm check:tests
pnpm check
```

봇 테스트는 node:test와 고정 API/Discord adapter를 사용한다. `test:lite`는 웹 lite와 봇 테스트를 함께 실행한다.
hard는 기존 전용 PostgreSQL과 실제 빌드한 SvelteKit 앱에서 내부 API·업무 저장·게시 상태를 검증한다.
테스트에서는 실제 Discord 로그인·명령 등록·메시지 발송을 수행하지 않는다. 이번 구현 검증에서도 실제 발송은 실행하지 않았다.
실제 서버의 권한·DM 수신 설정을 포함한 연동 검증은 지정한 테스트 서버와 발송 대상이 준비된 뒤 별도로 진행한다.
