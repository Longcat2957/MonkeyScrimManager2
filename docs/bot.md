# Discord 봇

구현 범위: 시즌 조회·전환·모집 생성·개인 신청·모집/팀 구성/경기 라인업/ROFL 결과 게시·운영자 요청 참가 안내 DM·Gateway 동기화·게시 복구.
웹 서버가 권한·업무 규칙·DB를 소유한다. 봇은 인증된 내부 API를 통해 변경을 요청하고 Discord에 전송한다. 게시 작업과 interaction 기록의 구조는 [DB ERD](database-erd.md#discord-작업과-요청-기록)를 따른다. 봇은 웹 로그인 세션을 만들지 않고, 비밀 interaction 토큰이나 요청 원문을 저장하거나 로그에 남기지 않는다.

## 설정과 실행

`apps/bot/.env.example`을 `apps/bot/.env`로 복사한다. `.env`는 Git에서 제외한다.

| 변수 | 설정 |
| --- | --- |
| `DISCORD_TOKEN` | 웹 `DISCORD_BOT_TOKEN`과 같은 봇 계정의 토큰 |
| `DISCORD_APPLICATION_ID` | 해당 Discord 애플리케이션 ID. 명령 등록에 필요 |
| `DISCORD_TEST_GUILD_ID` | 명령을 등록할 테스트 서버 ID |
| `BOT_INTERNAL_TOKEN` | 32자 이상의 난수 키. 웹의 같은 변수와 동일하게 설정 |
| `BOT_API_URL` | SvelteKit 내부 주소. 기본 `http://127.0.0.1:3000`; 웹 개발 서버를 쓸 때는 포트를 5173으로 변경 |
| `WEB_ORIGIN` | 사용자가 열 웹 주소. 운영에서는 실제 HTTPS origin |
| `BOT_STATUS_PORT` | 선택 사항. 같은 호스트의 웹이 상태를 조회할 로컬 포트 |

Developer Portal에서 Server Members Intent를 활성화한다. 봇은 `Guilds`, `GuildMembers`로 이벤트를 받고 일반 메시지 본문은 읽지 않는다.
앱은 서버 설치로 초대하며 명령과 봇을 사용할 수 있어야 한다. 게시 채널에서는 보기·메시지 전송·메시지 기록 읽기 권한이 필요하다.
웹에서도 같은 채널의 실제 게시 권한을 확인한다. 모집은 모집 채널, 팀 구성과 확정 출전 명단은 엔트리 채널, ROFL 결과는 결과 채널을 사용한다.

```sh
pnpm dev
pnpm dev:bot
```

두 명령은 별도 터미널에서 실행한다. 운영에서는 웹을 먼저 준비하고 봇을 실행한다.

```sh
pnpm build
pnpm start
pnpm start:bot
```

VPS에서는 웹·봇·Caddy를 같은 Docker Compose 프로젝트로 관리한다. 웹 포트는 호스트에 공개하지 않고 Caddy만 외부 HTTPS를 받는다. Caddy는 `/internal`·`/internal/`을 차단하며 웹은 `PROTOCOL_HEADER=x-forwarded-proto`를 읽는다. 내부 인증 키를 클라이언트 환경 변수나 URL에 넣지 않는다.
호스트에서 직접 실행할 때는 웹을 `HOST=127.0.0.1`로 열며 systemd·nginx 예제를 사용할 수 있다. Compose 배포·인증서 관리와 dev CI → main CD 절차는 [배포 문서](deployment.md)를 따른다.

## 명령 등록과 동작

명령 등록은 실제 Discord 상태를 변경한다. 봇 기동 시 자동으로 등록하지 않는다.
테스트 서버를 확인한 뒤 아래 명령을 명시적으로 실행한다.

```sh
pnpm bot:register
```

운영 전역 명령 등록은 `pnpm bot:register --global`로 구분한다. 다른 앱의 ID와 토큰을 섞어 사용할 수 없게 검증한다.

| 명령 | 동작 |
| --- | --- |
| `/초기설정` | 현재 서버 관리자 확인 후 봇을 제외한 전체 멤버를 등록·갱신하고 최초 `시즌 1` 준비. 처리한 일반 멤버 수와 내전 만들기·서버 관리 버튼 표시 |
| `/시즌` | 관리자가 현재·종료 시즌을 조회하고 새 시즌 시작 버튼 → 이름 입력창 → 전환 확인으로 진행 |
| `/내전모집` | 명령 실행 시 입력창을 연다. 제목·한국 시각 일정과 팀 수·추가 대기 정원·하드 피어리스를 입력·선택해 생성. 편성 방식은 웹에서 선택 |
| `/내전목록` | 현재 서버의 웹 내전 목록으로 이동 |
| `/게시복구` | 관리자 개인 화면에서 실패 작업을 선택하고 버튼으로 복구. 검색 입력창·기존 글 연결 입력창·글 없음 확인 제공 |

채널·운영자 역할·Riot 계정 연결은 웹 서버 관리에서 설정한다. 관리자 권한은 현재 Discord 권한/운영자 역할로 다시 확인한다.
봇 참가에는 웹 로그인 세션을 만들지 않는다. Discord interaction의 사용자와 실제 서버 소속을 사용하며 서버별 계정 연결을 검사한다.

`/초기설정`은 Discord 멤버 목록을 끝까지 조회한 뒤 일반 멤버의 내부 사용자·서버 멤버십·서버 별명을 저장한다. 재실행하면 기존 사용자와 활성 시즌을 재사용한다. 탈퇴한 서비스 계정은 자동 복원하지 않으며 웹 로그인 세션이나 내전 신청을 일괄 생성하지 않는다. 목록 조회 실패나 실행자의 관리 권한 회수는 부분 성공으로 처리하지 않는다.

참가자 이름은 해당 서버의 별명, Discord 전역 표시 이름, 사용자명 순으로 표시한다. 별명은 다른 서버에 적용하지 않으며 기존 비공개·탈퇴 표현도 유지한다.

공개 모집 글은 `참가하기`·`대기하기`·`참가 취소`를 독립 버튼으로 제공한다. `참가하기`는 버튼 한 번으로 신청한다. 웹 가입 이력이 없어도 실제 Discord 멤버를 검증한 뒤 내부 사용자·서버 멤버십·참가 기록을 생성한다. Riot 계정이 없어도 신청하며, 대표 계정이 있으면 기본 선택한다. 처음의 희망 포지션은 포지션 무관이고 재신청은 기존 희망 포지션을 재사용한다.
`대기하기`는 신규 대기 신청 또는 선발자의 대기 전환을 즉시 처리하고, `참가 취소`는 본인 신청을 확인 화면 없이 철회한다. 대기자가 `참가하기`를 누르면 빈 선발 자리로 복귀하며 자리가 없으면 대기를 유지한다. 실제 변경은 기존 신청 ID와 현재 모집 상태를 다시 검사한다. 대기 인원은 추가 대기 정원과 별개로 직접 대기자가 있을 수 있어 현재 인원만 표시한다.
선발자가 `참가하기`를 누르면 본인 신청 화면을 연다. 계정은 선택 사항이고 희망 포지션은 필요할 때 수정한다. 선택만 바꾸면 저장되지 않으며 수정 버튼으로 저장한다. 같은 화면에서 철회할 수 있고 마감 후에는 조회만 제공한다.
개인 입력 화면은 10분 또는 봇 재시작 후 만료될 수 있다. 공개 글의 버튼으로 다시 열면 된다.
웹에서 바꾼 신청·선발·설정·모집 단계도 같은 게시 글에 반영된다.

운영자는 모집 글의 `참가자 추가` 버튼을 누르고 개인 화면의 Discord 사용자 선택 메뉴에서 서버 멤버를 검색·선택해 대신 신청할 수 있다. 선택하면 즉시 추가하며 웹 가입·Riot 연결이 없는 대상도 실제 서버 소속을 확인해 내부 사용자와 참가 기록을 만든다. 봇은 제외하고 계정·희망 포지션·정원·대기·마감·중복 규칙은 본인 신청과 공유한다. 저장 결과를 확인하지 못하면 최초 대상과 요청 키로만 다시 확인하며, 권한은 화면 진입과 실제 등록 시 서버에서 다시 검사한다.

모든 명령은 옵션 없이 화면을 여는 진입점이다. 내전 생성 입력창은 제목·일정 입력과 팀 수·대기 인원·피어리스 선택 메뉴를 사용한다. 초기설정 화면의 내전 만들기 버튼으로도 같은 입력창을 연다. 오류 후에는 입력 수정 버튼으로 초안을 다시 연다. 작성자·서버·10분 만료를 확인하고 최초 요청의 멱등 키로 중복 생성을 막는다. 모집·팀 구성·경기 결과 메시지는 제목·요약·팀별 명단을 Discord 네이티브 구분선으로 나누고 상태 색상을 적용한다.

## 시즌 조회와 전환

`/시즌`의 조회·전환은 모두 웹 서버가 현재 실효 관리자 권한을 검사한다. 종료 시즌은 이름과 한국 시각의 기간으로 확인하며 응답은 실행자에게만 보인다. 시즌 UUID를 본문에 표시하지 않고, 긴 종료 이력은 페이지 이동 버튼으로 조회한다. 시즌이 없으면 기존 `/초기설정`을 안내한다.

전환하려면 새 시즌 시작 버튼을 누르고 이름(trim 후 1~100자)을 입력한다. 현재·새 시즌을 보여 주는 확인 화면에서 시즌 전환 버튼을 눌러야 저장한다. 돌아가기는 저장하지 않으며 과거 시즌을 전환 대상으로 제시하지 않는다. 화면은 작성자·서버·10분 만료를 확인하고 오래된 확인 버튼과 중복 전환을 막는다.

봇은 화면을 열 때의 `expectedCurrentSeasonId`와 실행자·최초 전환 확인 interaction ID를 `/internal/bot/guilds/[guildId]/seasons`의 POST로 보낸다. 같은 경로의 GET은 관리자 조회가 소비한다. 조회·전환은 기존 10초 제한을 사용한다. 권한 회수와 오래된 선택은 서버 오류를 안내하고, 새로운 현재 시즌으로 바꾸어 자동 재전송하지 않는다.

서버는 MSM1 pin의 [시즌 전환](https://github.com/Longcat2957/MonkeyScrimManager/blob/d60df685e48c180b236342eae81b389ae87e38bf/apps/api-python/src/monkeybot_api/services/guilds/seasons.py)처럼 이전 활성 시즌 종료·새 시즌 생성을 원자적으로 처리하고 receipt로 재전송의 중복 효과를 막는다. 진행 중인 내전은 원래 시즌과 MMR을 유지하고 새 모집부터 새 시즌을 사용한다. 이전 점수·원장을 복제하거나 기존 내전을 새 시즌으로 옮기지 않는다. 자세한 계약은 [MMR 시즌 전환](mmr.md#시즌-전환)을 따른다. 웹 전적·순위의 과거 시즌 선택과 서버 관리의 시즌 전환 UI도 제공한다. 웹과 봇은 같은 전환 서비스를 사용하며 웹은 현재 시즌 CAS로, 봇은 기존 interaction receipt까지 함께 적용한다.

## 게시와 복구

게시 작업은 업무 저장과 같은 트랜잭션에 기록하고 봇이 한 개씩 처리한다. 채널 미설정/전송 실패가 업무 저장을 취소하지 않는다.
수동 편성 확정 또는 경매 완료 후 팀 구성 카드를 게시한다. 되돌리기/취소 시 이전 확정 글도 제거하거나 갱신한다.
일반 내전의 경기 라인업은 확정된 수동 편성에서 자동 준비되고, 경매 내전은 경기별로 한 번 확정한다. 같은 Match의 BO 전체에서 재사용하며 매 세트 다시 확정하지 않는다.
경기 라인업 카드는 확정된 팀별 출전자·포지션만 표시한다. 팀의 색이나 희망 포지션으로 실제 경기 진영/출전 포지션을 추측하지 않는다.

ROFL 결과 저장과 MMR·대진 처리가 성공하면 Game별 결과 카드를 예약한다. 실제 세트 번호·진영·승자·챔피언·KDA·시리즈 점수를 표시한다.
기존 글의 점수는 같은 메시지에 갱신한다. 결과 정정으로 취소된 Game의 글을 삭제한 뒤 새 결과를 게시하며, 이전 글이 전달 불명이면 대조가 끝날 때까지 새 결과는 대기한다.
게시 형식은 Discord 네이티브 Components V2 카드다. 별도 결과 이미지를 생성하지 않는다.

참가 안내 DM은 웹 내전의 운영 메뉴에서 `참가 안내 보내기`를 실행했을 때만 예약한다. 모집 마감 후 준비·진행 중인 내전에서 현재 선발된 Discord 사용자만 대상이다.
같은 내전의 같은 사용자에게 반복 요청해도 새 DM을 만들지 않는다. 이후 새 선발자가 생기면 다음 요청에서 그 사람만 추가한다.
작업 점유 시 선발 상태와 내전 단계를 다시 검사하고, 발송 전에는 실제 서버 멤버와 DM 채널 수신자를 확인한다. 대기·철회자에게 자동 안내하지 않는다.
웹은 대기·발송 완료·실패·전달 불명 건수를 보여 준다. 예약 성공은 실제 수신 완료를 뜻하지 않는다.

429·일시 장애는 다음 시도를 예약한다. 권한 회수·채널 삭제 등은 `blocked`, 신규 글이 전송됐는지 알 수 없으면 `uncertain`으로 남는다.
`/게시복구`의 선택 메뉴에서 실패 작업을 고른다. 게시 실패는 다시 시도 버튼으로 복구하며, 이미 게시된 글이 있으면 기존 글 연결 입력창에 메시지 링크나 ID를 입력한다. 전달 불명은 기존 글 연결 또는 글 없음 확인으로만 진행한다. 글 없음 확인은 별도 확인 화면을 거쳐야 새 게시를 허용한다.
메시지 ID를 받으면 웹 서버가 해당 채널·봇 작성자·내전 링크와 링크의 게시 작업 식별자를 대조한다. 모집·팀 구성을 포함한 모든 종류에서 선택한 작업과 일치해야 한다.
복구 요청 역시 interaction ID로 중복 효과를 방지한다. DM 수신 차단은 실패로 남으며 반복 발송하지 않는다.
불명 DM의 글 없음 확인은 수신자에게 안내가 없음을 확인한 뒤 사용한다. 프로세스 중단으로 DM 채널 정보까지 유실됐다면 기존 글 연결은 비활성화되고 부재 확인이 필요하다.

게시 작업 식별자가 없는 이전 형식의 글도 메시지 ID가 이미 저장돼 있다면 다시 시도 버튼으로 같은 글을 갱신할 수 있다.
ID가 저장되지 않은 전달 불명 글은 종류나 내용으로 추정 연결하지 않는다. 해당 기존 글을 직접 삭제한 뒤 글 없음 확인으로 복구한다.

채널 변경은 이전 글을 정리한 뒤 새 위치로 게시한다. 이전 글 접근 권한을 잃었다면 먼저 권한 또는 채널 상태를 정리한다.
기존 글이 삭제되어 편집이 404로 실패하면 `MESSAGE_MISSING`으로 보류한다. `/게시복구`에서 글 없음 확인을 완료해 기존 메시지 ID를 지운 뒤 새 작업으로 생성한다.
게시 작업의 점유 만료와 오래된 응답은 토큰·버전으로 검사한다. Discord 전달을 영구적으로 정확히 한 번 보장한다고 가정하지 않는다.

복구 목록은 최근 갱신 순으로 최대 25개를 보여 준다. 작업 검색 버튼의 입력창에서 해당 서버의 전체 실패·전달 불명 작업을 내전 제목과 대상으로 검색하며 목록 새로고침도 제공한다. API 응답이 유실되면 같은 요청 다시 확인 버튼으로 최초 멱등 키와 요청 내용을 유지한다.
검색어는 앞뒤 공백을 제거하고 최대 100자를 허용하며 `%`·`_`·`\`도 일반 문자로 검색한다.
라인업은 경기 이름·양 팀, 결과는 세트 번호·경기 이름·양 팀, DM은 수신자를 표시한다. 취소된 Game은 `취소 결과`로 구분하여
같은 경기·세트의 새 결과와 혼동하지 않게 한다. 결과 정정으로 삭제된 후속 라인업의 게시 정리 작업은 `삭제된 라인업`과 원본 대상 ID로 구분한다.
봇의 100자 선택지 안에서는 종류·실패 상태·대상을 먼저 표시하고 내전 제목을 줄인다.
검색과 실제 재시도 모두 현재 관리자 권한과 서버 범위를 검사하며, 검색이 게시 재처리 조건을 완화하지 않는다.

## 검증

```sh
pnpm test:bot
pnpm test:lite
pnpm test:hard
pnpm check:tests
pnpm check
```

봇 테스트는 node:test와 고정 API/Discord adapter를 사용한다. `test:lite`는 웹 lite와 봇 테스트를 함께 실행한다.
hard는 기존 전용 PostgreSQL과 실제 빌드한 SvelteKit 앱에서 내부 API·업무 저장·게시 상태를 검증한다.
운영 VPS에서 확인한 Gateway 연결·전역 명령 등록과 실제 사용자 흐름 검증은 구분한다. 지정된 테스트 서버와 수신자를 준비한 뒤 실제 명령·권한 회수·Components V2 게시·DM 수신·재연결과 게시 복구를 확인한다.
