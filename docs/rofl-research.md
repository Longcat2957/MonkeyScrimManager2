# ROFL 데이터 추출 연구 노트

조사일: 2026-10-28. 실행 방법은 [ROFL 분석](rofl.md)을 참고한다.
연구 목표는 현재 용도를 정하지 않은 데이터까지 로컬에서 추출하고, 확인된 구조와 미확정 의미를 구분하는 자체 파서다.
현재 추출은 Linux에서 ROFL 파일만으로 수행하며, Riot API나 게임 클라이언트에 의존하지 않는다.
이 문서의 원본·전체 추출물 보관은 개발자가 명시적으로 실행한 연구에 한정한다.
서비스는 [P0~P2 적재 모델](rofl-import.md)에 따라 선별 데이터만 저장하며, 원본 파일을 보관하거나 자동 재분석하지 않는다.

## 확인 범위

서로 다른 두 경기의 ROFL2 파일을 조사했다. 각 빌드의 표본은 하나뿐이다.
이 문서에는 참가자 신원, 개별 통계 값, 원본 payload, 비공개 파일 식별자를 싣지 않는다.

| 관측 항목 | 로컬 표본 | 공개 비교 표본 |
| --- | --- | --- |
| 전체 게임 버전 | `16.21.829.8620` | `16.5.752.7101` |
| 참가자 수 | 10 | 10 |
| 참가자당 메타데이터 필드 | 313 | 339 |
| 참가자 필드의 JSON 값 타입 | 모두 문자열 | 모두 문자열 |
| 청크 descriptor 길이 | 18바이트 | 17바이트 |

두 표본의 공통 참가자 필드는 275개다. 나머지는 로컬 표본에만 38개, 공개 표본에만 64개 존재한다.
서로 다른 경기이므로 이 차이를 패치 변경만의 결과로 단정하지 않는다.
10명이라는 참가자 수, 필드 목록, 문자열 형태도 전체 ROFL의 불변 조건이 아니다.

집계 근거는 Git에서 제외되는 `samples/rofl-research/metadata-inventory.json`과
`samples/rofl-research/16.21-full/`의 `report.json`, `chunks.json`, `verification.json`이다.
공개 비교 파일의 출처는 [고정 커밋의 16.5 샘플](https://github.com/Danmoreng/league-replay-analyzer/blob/955974a68adc0d08b26cca7d4e9411d6219d786c/replays/EUW1-7779216102.rofl)이다.

## 원본 메타데이터

현재 요약 모델보다 원본 `statsJson`의 범위가 넓다.
전투·피해·회복·보호막·경제·아이템·룬·시야·목표물·핑·시전 횟수 외에 이벤트/미션 이름공간과 미분류 필드도 있다.
이 분류는 필드명에 따른 조사 편의용이며, 각 값의 의미와 단위를 검증했다는 뜻이 아니다.

- 원본 ROFL, `metadata.raw.json`의 원문 바이트, 원래의 `statsJson` 문자열과 알 수 없는 필드를 보존한다.
- 숫자처럼 생긴 문자열을 일괄 변환하지 않는다. 식별자·태그·범주 값도 숫자 형태일 수 있다.
- 누락, `null`, 빈 문자열, `0`, `false`를 합치지 않는다. `0`/`1`만 관측돼도 boolean으로 단정하지 않는다.
- 서비스용 숫자 필드는 출처와 단위를 확인한 명시적 매핑으로만 만든다.
- 이벤트 이름이 존재한다는 사실만으로 해당 게임 모드나 행동의 발생을 추론하지 않는다.

두 표본에서는 안전한 정수 범위를 벗어난 숫자 문자열이나 소수·지수 문자열을 관측하지 않았다.
향후 입력에도 없다고 가정하지 않으며, 원문 보존과 숫자 투영의 범위 검사는 별개로 유지한다.
`metadata.json`은 JS `JSON.parse`로 읽은 뷰이므로 실제 JSON 숫자의 정밀도까지 보존하지는 않는다.
큰 정수나 소수의 정확한 표기는 `metadata.raw.json`과 원본 파일에서 다시 읽는다.

## 청크 descriptor

청크 영역은 가변 길이 게임 버전 문자열 직후부터 메타데이터 앞 256바이트 서명 영역 직전까지다.
아래 오프셋은 청크 시작 기준이며, 다중 바이트 정수는 little-endian이다.

| 오프셋 | 크기 | 현재 읽는 값 |
| --- | --- | --- |
| `+0` | 4 | `id` |
| `+4` | 4 | `nextChunkId` 원시 값 |
| `+8` | 1 | `stream` |
| `+9` | 4 | `uncompressedSize` |
| `+13` | 4 | `compressedSize` |
| `+17` | 1, 18바이트 형식에만 존재 | 의미 미확정 확장 바이트 |

`compressedSize > 0`이면 Zstandard 본문이며, 0이면 `uncompressedSize` 길이의 원시 본문이다.
16.21 표본에서는 압축 청크 696개와 원시 청크 1개 모두 확장 바이트가 `0x04`였다.
따라서 이 바이트를 압축 여부나 특정 의미의 enum으로 선언하지 않는다.
`nextChunkId`는 저장하되 그 값으로 파일 오프셋을 계산하거나 체인을 강제로 복원하지 않는다.

17/18바이트 후보 각각에 대해 전체 청크 영역의 경계와 압축 프레임 시작을 확인한다.
서명 영역 직전까지 정확히 도달하는 후보가 하나일 때만 선택한다.
손상된 바이트를 건너뛰며 다음 magic을 찾는 방식은 사용하지 않는다.
이 결과는 두 형식의 실측 증거이며, 18바이트 형식의 최초 도입 패치를 확정한 것은 아니다.

공개 구현도 표기와 필드 분할이 서로 다르므로 문서 하나를 규격으로 취급하지 않는다.
[RoflLens 컨테이너 구현](https://github.com/ss26367098/rofllens/blob/62a475a8f05e7dfa94df5990758be2156c892496/src/rofllens/container.py)과
[ROFL-X 형식 조사](https://github.com/Toastaspiring/ROFL-X/blob/88954be66da506f188fbd134944fdfd8334ad846/docs/ROFL_FORMAT.md)는 비교 자료이며, 현재 표본의 바이트 경계 검증이 우선한다.

### Zstd 압축 프레임 검증

Node 22.20.0에서 잘린 Zstd 입력이 오류 없이 부분 출력으로 반환되는 경우를 재현했다.
빈 프레임의 일부뿐 아니라 정상 본문의 끝을 자른 경우도 해당하므로, 선언된 출력 크기와
소비한 입력 크기를 비교하는 것만으로 프레임 완결성을 보장하지 못한다.
[Node 구현](https://github.com/nodejs/node/blob/v22.20.0/src/node_zlib.cc#L1607)과
[Zstd API의 완료 반환값](https://github.com/facebook/zstd/blob/v1.5.7/lib/zstd.h#L927)을 대조했다.

현재 두 표본은 압축 청크마다 단일 Zstd 프레임을 가진다.
따라서 [Zstd 공식 형식](https://github.com/facebook/zstd/blob/v1.5.7/doc/zstd_compression_format.md)에 따라
프레임 헤더·블록 경계·마지막 블록·체크섬 영역이 끝까지 존재하는지 먼저 확인한다.
실제 압축 해제와 체크섬 검증은 Node 기본 모듈에 맡기며, 출력 길이·윈도 제한도 적용한다.
연결된 복수 프레임과 후행 데이터는 현재 지원 범위에서 거부한다. 원래 압축 바이트는 원본 파일에 보존된다.

## 패킷 framing

압축 해제한 청크마다 이전 시각·패킷 ID·`param` 상태를 0으로 초기화한다.
블록은 flags, 시각, payload 길이, 필요하면 패킷 ID, `param`, payload 순서다.

| flags 비트 | 설정된 경우 | 설정되지 않은 경우 |
| --- | --- | --- |
| `0x80` | 이전 시각에 `u8 / 1000`초 추가 | `f32` 절대 시각(초) |
| `0x10` | payload 길이 `u8` | payload 길이 `u32` |
| `0x40` | 이전 `u16` 패킷 ID 재사용 | 새 `u16` 패킷 ID |
| `0x20` | 이전 `param`에 **signed i8** 추가 | 새 `u32` `param` |

`param` 덧셈은 uint32 wrap을 적용한다. 16.21 표본에서는 음수 delta를 16,451회 관측했다.
unsigned delta로 읽으면 바이트 경계는 맞아도 값이 틀릴 수 있다.
flags 전체와 본문을 보존하며 위 표 이외 비트에 새 의미를 부여하지 않는다.
절대 시각은 float32, delta 누적은 JavaScript 배정밀도로 기록하므로 원본 바이트도 함께 남긴다.

`packetId`는 패킷 종류를 나타내는 숫자이고 `param`은 별도 문맥 값이다.
일부 패킷에서 `param`이 엔티티 식별자일 수 있으나, 모든 값이 참가자·팀·챔피언을 뜻한다고 보지 않는다.
payload를 끝까지 분리한 사실만으로 킬·이동·피해·아이템 이벤트를 해석했다고 표현하지 않는다.

| 스트림 원시 값 | 청크 | 분리한 패킷 | 압축 해제 바이트 | 공개 연구의 통상적 구분 |
| --- | ---: | ---: | ---: | --- |

| 2 | 34 | 391,601 | 7,454,760 | 키프레임 상태 복구 데이터 |

숫자와 경계는 로컬 실측이며, 오른쪽 명칭은 공개 연구에서 사용하는 구분이다.
초기 상태·제어 payload의 내부 레코드까지 이해했다는 뜻은 아니다.
키프레임의 상태 복구 기록을 게임 진행 스트림과 합산하면 같은 상태나 행동을 중복 계산할 수 있다.

서로 다른 패킷 ID는 265개, payload 합계는 30,648,163바이트다.
실패 청크와 framing 밖에 남은 압축 해제 바이트는 모두 0이며, **검증된 본문 의미 디코더도 0개**다.
독립 Python 검사에서 697개 청크와 1,795,343개 인덱스를 전수 대조하고 원본·메타데이터 보존을 확인했다.
이는 구조 검증이다. 서명의 진위, 업로드 권한, 경기 결과의 정당성이나 게임 이벤트 의미를 인증하지 않는다.

## 로컬 연구 자료 보관 방식

개발자가 `rofl:research`를 실행한 추출 디렉터리는 원본 파일, 전체 메타데이터, 압축 해제 청크,
청크 목록, 압축된 패킷 인덱스와 보고서를 보관한다.
인덱스의 오프셋은 압축 해제 청크 기준이며 payload를 잘라 다시 읽을 수 있다.
원본에는 헤더의 미확정 바이트, 서명, 압축된 표현까지 남으므로 JSON 변환에서 빠진 정보도 재조사할 수 있다.
청크별 해시와 전체 버전, 출력 schemaVersion을 기록하며 해석 실패를 데이터 삭제로 처리하지 않는다.
집계용 메모리의 항목 수를 제한하되 통계 생략 여부를 보고하고, 전체 패킷 인덱스 기록은 계속한다.
원본과 파생 결과는 모두 `/samples/` 아래에서 Git 제외를 유지한다.

## 다음 연구와 보류 기준

ROFL-X는 16.19 파일 20개에서 종료 통계와 패킷 분포를 대조해 시야·사망 일부와 거친 위치를 복원했다.
위치는 약 512 게임 좌표 단위 수준이며 정확한 이동 경로는 미해결이다. [방법과 한계](https://github.com/Toastaspiring/ROFL-X/blob/88954be66da506f188fbd134944fdfd8334ad846/docs/EXPLORE.md)
이는 ROFL만으로 진행할 수 있는 연구의 예이며, 해당 패킷 ID·변환표·참가자 순서 가정을 16.21에 이식하지 않는다.

1. 같은 전체 빌드의 파일을 추가로 비교해 청크 형식, 확장 바이트, 스트림·패킷·문맥 값의 분포를 확인한다.
2. 게임 진행 스트림의 패킷별 빈도·길이·시각·`param`을 집계하고, 종료 통계와 대응할 후보만 만든다.
3. 후보를 만든 경기와 검증할 경기를 분리한다. 사망·레벨·KDA 같은 소수의 명시적 가설부터 반례를 찾는다.
4. 후보의 의미·단위·계정 연결은 독립 근거가 확인될 때만 추가한다. 원본 값과 관측 출처는 유지한다.

단일 파일의 수치 일치, 전부 0인 열, 비슷한 필드명, 동일한 payload 길이만으로 의미를 확정하지 않는다.
동률·복수 후보·표본 부족·검증 경기의 불일치·패치 변경이 있으면 후보 상태로 남기거나 해석을 보류한다.
재접속·리메이크·항복·특수 모드·다른 참가자 수를 아직 검증하지 않았으므로 일반 지원을 선언하지 않는다.
수치상 구조 coverage와 의미 coverage를 계속 별도로 보고하며, 미해석 데이터 추출은 의미 연구와 독립적으로 유지한다.
