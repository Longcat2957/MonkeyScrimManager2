# QA 계획: ROFL 등록 확인, 모집 일정, 통계 백분율

구현 기준과 QA 접수 당시의 현황을 기록한 문서다. 적용된 동작은 [경기·통계](web/pages/records.md)와 [모집 설정](web/pages/scrims.md)을 따른다.

## 1. ROFL 실제 등록값 미리보기

- **현황:** [업로드 팝업](../apps/web/src/lib/components/matches/RoflUploadDialog.svelte)은 파일·블루 팀을 선택하고 진영을 확인하면 곧바로 등록을 요청한다. 실제 파싱 결과를 저장 전에 보는 화면은 없다.
- **안전장치:** 같은 모달에 `등록값 미리보기` 단계를 추가한다. 대상 경기·세트와 파일명을 표시하고, 실제로 기록될 **블루·레드 팀명과 승패**, 양 팀 5명씩의 **출전자 ↔ ROFL Riot 계정, 포지션, 챔피언, K/D/A**를 보여 준다. 첫 연결은 새로 연결될 계정을 구별한다. 단순 파일 요약이나 “등록할까요?” 확인창으로 대체하지 않는다.
- **동작:** `미리보기`는 기존 서버의 권한 검사·파싱·라인업 대조 로직으로 등록 후보를 계산하되 결과·계정 연결·MMR·Discord 게시를 반영하지 않는다. `수정`은 선택을 보존하고 파일이나 진영이 바뀌면 다시 계산한다. `이대로 등록`만 쓰기를 요청한다. 원본 파일을 보관하거나 별도 승인자를 두지 않는다.
- **서버 검증과 한계:** [결과 저장](../apps/web/src/lib/server/matches/results.ts)의 권한·라인업·세트 번호·revision·중복 검증과 세트 단위 트랜잭션은 유지한다. 최종 저장 시 서버가 다시 계산한 값이 미리보기와 다르면 쓰지 않고 재확인을 요구한다. 연결 근거가 충돌하면 오류를 표시한다. 전원 미연결인 첫 경기는 선택한 진영에 따라 귀속되므로 양 팀 명단을 대조하는 것이 특히 중요하다.
- **완료 기준:** 미리보기·뒤로 가기·취소만으로는 경기 결과나 부수 효과가 생기지 않는다. 실제 ROFL로 미리보기의 양 팀·승자·선수별 값과 등록 후 상세가 일치하는지 검증한다. 진영 수정, 다른 운영자의 선등록, 더블 클릭, 응답 유실을 기존 [DB](../apps/web/tests/api/hard/db/match-results.test.ts)·[HTTP](../apps/web/tests/api/hard/http/match-results.test.ts) 검증과 함께 확인한다. 운영의 세트별 등록과 개발 샘플의 다중 파일 동작을 구분하고 모바일·키보드에서도 확인 후 등록할 수 있어야 한다.

## 2. 새 모집 일정 기본값 통일

- **현황:** [웹 모집 만들기](../apps/web/src/routes/g/%5BguildId%5D/scrims/+page.svelte)는 팝업을 여는 시각보다 30분 뒤를 채운다. [Discord 모집 초안](../apps/bot/src/interactions/create-scrim.ts)은 `scheduledAt`을 빈 문자열로 시작한다. 입력 없이 제출하면 두 경로의 결과가 다르다.
- **변경:** Discord도 새 초안을 열 때 한 번만 30분 뒤를 계산해 한국 시각으로 미리 채운다. 웹과 같은 시각을 저장하는지 확인한다. 오류 후 다시 열 때, 기존 모집을 수정할 때는 기본값으로 덮어쓰지 않는다. 날짜와 시간을 명시적으로 모두 지우면 기존 ‘미정’ 동작을 유지한다.
- **기존 데이터:** 예정 시각이 DB에 있는데 화면이나 모집 공지만 ‘미정’이면 조회·전달 경로를 고친다. 근거 없는 과거 `null`은 소급 보정하지 않는다. 모집 예정 시각은 ROFL 실제 경기 시각과 별개다.
- **완료 기준:** 웹과 Discord 모두 한국 시각 23:45에 새 모집을 열면 다음 날 00:15가 표시된다. 기본값 제출·직접 수정·명시적으로 비우기·오류 후 재열기 각각에서 웹 목록·상세와 Discord 공지가 같은 일정을 가리킨다.

## 3. 통계 백분율을 1%p 단위로 확인

- **현황:** [표시 함수](../apps/web/src/lib/features/players/format.ts)는 비율에 100을 곱한 뒤 정수로 반올림한다. [개인 지표의 상위 비율](../apps/web/src/lib/features/players/stats.ts)은 유효 비교 인원과 공동 순위로 계산한다. 비교자가 정확히 10명이면 순위가 바뀔 때 10%p씩 달라지는 것이 정상이다. 이 두 경로에는 10%p로 강제 반올림하는 코드가 없다.
- **변경 범위:** QA가 본 시즌·포지션·항목에서 분자와 분모, 서버 응답, 화면 값을 차례로 비교한다. 승률·킬 관여율처럼 실제 비율이 10%p로 잘리는 경로가 있으면 최초 손실 지점만 수정한다. 원래 비율로 집계·정렬하고 최종 표시에만 반올림한다. 순위 표본 크기 때문에 생긴 간격이라면 통계식을 바꾸지 않는다.
- **완료 기준:** 7승 12경기는 `58%`, 17명 중 공동 3위는 기존 백분위 규칙대로 `상위 18%`다. 10명 중 3위는 `상위 30%`로 유지한다. 실제 0은 `0%`, 계산할 수 없는 값은 `—`로 구분한다. 소수점 표시나 인위적인 순위 보간은 범위 밖이다.

## 로컬 검증 결과

- 격리 PostgreSQL에서 미리보기 전후에 전적·계정 연결·MMR이 바뀌지 않았고, 등록 후 열 명의 저장값이 미리보기와 일치했다. 파일·계정 연결·진영 변경, 동시 제출, 마지막 세트 취소·복구도 확인했다.
- Chromium 390px·1440px에서 미리보기와 등록 후 상세를 대조했다. 미리보기 응답 유실은 저장 없이 재시도하고, 등록 응답 유실은 중복 기록 없이 실제 경기 상태를 다시 조회했다.
- 모집을 한국 시각 23:45에 열면 다음 날 00:15로 표시·저장됐다. 웹 목록·상세와 Discord 공지 데이터가 일치했다. 수동 수정과 명시적으로 비운 값도 유지됐다.
- 통계는 `7/12 = 58%`, `24/70 = 34%`, `7위/25명 = 상위 28%`를 확인했다. QA가 본 운영 표본은 특정하지 못했다. 운영 DB나 과거 일정을 변경하지 않았다.
