# Discord 봇 구현 계획

작성일: 2026-11-05. MSM1 `d60df685`의 실제 모집·웹 편성·운영자 요청 DM 코드를 참고하며 현재 MSM2 구현을 기준으로 갱신한다.

## 역할과 사용자 흐름

MSM1의 모집·참가와 웹 편성 연결을 참고한다. 명령 개수·분리된 일반/경매 모델·메시지 모양을 그대로 이식하지 않는다.
Discord에서는 모집을 알리고 본인 신청을 관리한다. 선발·수동 편성·경매·대진 운영은 기존 웹을 사용한다.
웹이 DB·권한·업무 규칙을 소유하고 봇은 Gateway·interaction·메시지 입출력을 담당한다.

공개 모집 글에는 제목·일정·선발/대기 인원·참가자·희망 포지션을 표시하고 `내 신청`, `내전 열기`를 제공한다.
`내 신청`은 본인에게만 계정·희망 포지션·현재 신청 상태를 보여 준다. 선택만으로 저장하지 않고 제출로 신청/수정을 확정하며 철회는 확인을 거친다.
수동/경매의 신청 흐름은 같고, 선발 정원이 차도 추가 대기 정원이 남으면 신청을 허용한다.
개인 입력창은 만료할 수 있지만 공개 모집 글의 버튼은 봇 재시작 후에도 새 입력창을 연다.

## 구현 범위

1. 직접 관리하는 코드와 설정의 들여쓰기를 공백 4칸으로 통일한다. EditorConfig·Prettier와 검사 명령으로 유지하며 잠금 파일·생성 SQL은 생성 도구 형식을 따른다.
2. 공유 JSON 타입과 인증된 `/internal/bot` HTTP 어댑터를 추가한다. SvelteKit을 계속 사용하고 봇에 DB 접근 권한을 주지 않는다.
3. 초기 설정에서 최초 시즌을 준비하고, 모집 생성·개인 신청을 기존 업무 서비스에 연결한다. 운영자의 서버별 계정 연결 정책을 유지한다.
4. 웹과 봇의 변경 트랜잭션에 게시 작업을 함께 기록한다. 모집 게시/수정/취소와 확정된 팀 구성 게시/해제를 연결한다.
5. 작업 점유·재시도·응답 유실·채널 변경·운영자 복구를 구현한다. 권한·카탈로그 갱신은 Gateway 알림 뒤 서버가 실제 Discord를 재조회한다.
6. 기존 node:test 체계에 bot lite 및 web DB/HTTP hard를 추가하고 실제 격리 PostgreSQL·SvelteKit 앱으로 검증한다.
7. 확정 경기 라인업과 ROFL 정상 결과 처리를 같은 게시 작업에 연결한다. 일반 내전은 확정 수동 편성을 경기 생성 시 복사하고, 경매 내전은 Match별 출전을 한 번 확정하여 BO 전체에 재사용한다.
8. 웹 운영자의 명시 요청으로 참가 안내 DM을 예약한다. 현재 선발된 실제 Discord 사용자만 대상으로 하며 내전·사용자별 중복 요청은 새 발송을 만들지 않는다.

전체 흐름은 **모집 생성·게시 → 개인 신청 → 웹 편성·대진 → 확정 경기 출전 → ROFL 결과 저장·게시**다. 참가 안내는 운영자가 필요한 시점에 요청한다.
명령은 초기 준비·모집 생성·목록 진입·게시 실패 복구에 한정한다. 복잡한 운영을 위한 UUID 입력 명령을 나열하지 않는다.

## 저장과 원자성

- `scrim_discord_messages`: 내전·종류·대상별 현재 채널·메시지·반영 버전.
- 게시 작업: 목적지·목표 버전·재시도 시각·횟수·점유 토큰/만료·오류/전달 불명 상태.
- interaction 처리 기록: 고유 interaction ID·실행자·대상·요청 해시·처리 결과. 비밀 interaction 토큰은 저장하지 않는다.

신청의 중복 확인, 업무 변경, 게시 예약, 성공 결과를 하나의 트랜잭션으로 처리한다. 같은 ID의 다른 요청은 거절한다.
신청 수정/철회는 신청 이력 ID를 확인해 오래된 개인 창이 이후 재신청을 바꾸지 못하게 한다.
외부 전송은 커밋 뒤 수행한다. 작업을 한 개씩 점유하고 점유 토큰과 버전이 맞는 처리 결과만 반영한다.
전송 도중 새 변경이 생겼다면 최신 버전을 다시 게시한다. 생성 성공 여부가 불명확하면 무조건 새 글을 만들지 않는다.
채널 미설정과 Discord 장애는 이미 성공한 업무 저장을 취소하지 않는다.

| 게시 종류 | 대상 키 | 목적지 |
| --- | --- | --- |
| `recruitment` | 내전 공통 `scrim` | 모집 채널 |
| `entry` | 내전 공통 `scrim` | 엔트리 채널 |
| `lineup` | Match의 확정 라인업 ID | 엔트리 채널 |
| `result` | 저장된 Game ID | 결과 채널 |
| `confirmation_dm` | 선발자의 Discord 사용자 ID | 해당 사용자 DM |

라인업과 결과 글에는 업무 데이터의 확정된 출전·진영·ROFL 성적만 사용한다. 팀 구성·희망 포지션으로 추측하지 않는다.
ROFL·출전·MMR·시리즈/진출·게시 예약은 함께 커밋하며 실패하면 모두 롤백한다. 마지막 결과 정정은 취소 Game을 보존하고 이전 결과 글을 정리한 뒤 새 Game의 글을 게시한다.
DM은 일반 업무 변경으로 자동 생성하지 않는다. 명시 요청의 선발자별 고유 키가 동시 클릭을 합치고, 발송 시 현재 자격을 다시 확인한다.
DM 완료·전달 불명 보고에는 실제 DM 채널을 남긴다. 불명 전송은 자동 재생성하지 않고 수신자에게 부재를 확인하거나 저장된 채널의 메시지를 대조한 뒤 복구한다.

## 통신·권한·운영

내부 API는 전용 Bearer 토큰을 요구한다. VPS 프록시는 `/internal/`을 외부에 전달하지 않고 앱과 봇은 로컬 주소로 통신한다.
실행자는 인증한 봇 interaction에서 구성하되, 현재 소속·관리 권한·서버/내전 귀속은 웹 서비스가 다시 검사한다.
조회는 GET, 생성/점유는 POST, 신청 수정·철회와 처리 결과는 PATCH, 동기화는 PUT을 사용한다.
실제 탈퇴는 현재 소속 또는 활성 상태에 반영하고 과거 참가·경기 기록을 보존한다. 일시 unavailable을 퇴장으로 처리하지 않는다.
GuildMembers intent가 필요한 멤버 이벤트는 Developer Portal 설정과 함께 안내한다.
명령 등록은 실행과 분리하고 테스트 서버/운영 범위를 명시한다. 토큰·세션·원본 interaction을 로그에 남기지 않는다.

## 표현과 실연동 경계

- 엔트리 게시에는 확정된 팀 구성만 사용한다. 희망 포지션을 경기 출전 포지션으로 바꾸거나 팀을 BLUE/RED로 가정하지 않는다.
- 경기 라인업과 결과는 Discord 네이티브 Components V2 카드로 표시한다. 결과 이미지 생성은 구현 범위가 아니다.
- 경기 라인업은 Match 단위이고 결과는 Game 단위다. 세트마다 라인업 확정을 요구하지 않는다.
- 참가 확정 DM은 MSM1처럼 운영자 요청 기능이며 모집 신청의 자동 부수 효과로 추가하지 않는다.
- 실제 Discord 명령 등록·메시지 발송 검증은 지정된 테스트 서버와 발송 범위가 준비된 뒤 진행한다.

## 검증 기준

lite는 명령/버튼 입력·개인 입력창 수명·메시지 내용·오류 변환·worker 복구 판단을 검사한다.
hard는 실제 DB 트랜잭션과 SvelteKit HTTP로 인증, 교차 서버, 오래된 신청, 중복/동시 요청, 롤백, 점유 만료,
이전 전송 응답과 최신 변경의 경합, 채널 변경, 최초 시즌 생성, 웹 변경의 게시 예약을 검사한다.
라인업 자동 준비/확정과 ROFL 저장 뒤 게시 예약, 결과 정정 후 삭제 순서, DM 중복 클릭·수신자 제외·불명 채널 보존도 검증한다.
Discord 응답은 고정 adapter로 대체하고 실제 발송 성공으로 설명하지 않는다.

## 구현 상태

모집·개인 신청·게시 복구에 이어 경기 라인업·ROFL 결과 게시·운영자 요청 DM까지 코드에 연결했다.
DB 스키마는 게시 대상 키와 DM 채널 점유를 지원하고, 봇은 DB 접근 없이 내부 API와 Discord 전송만 담당한다.
자동 검증 범위와 실행 기록은 [테스트 문서](testing.md)를 따른다. 실제 Discord 로그인·명령 등록·메시지/DM 발송은 이번 검증에서 실행하지 않았다.
