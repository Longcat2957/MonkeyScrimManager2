# 내전 페이지

확인일: 2026-11-05. 대상: `apps/web/src/routes/g/[guildId]/scrims/**`와 내전·편성·대진 컴포넌트의 현재 구현.
목록은 서버 범위 헤더, `[scrimId]` 하위는 내전 범위 헤더를 쓴다.

## 현재 구현 범위

- 실제 서버의 목록·상세·수동 편성·경매·대진·결과를 DB에서 공개 조회한다. 개발 모드의 명시적 샘플 서버만 `lib/mocks/`의 메모리 데이터를 사용한다.
- 모집 생성·신청·선발·철회·설정과 편성·경매·대진·진행 변경은 업무 함수와 DB 트랜잭션에 연결했다. 실행자는 세션에서만 가져오며 조작 전에 현재 Discord 소속·관리 권한을 확인한다. 본인 신청은 해당 서버에 연결된 계정만 받는다.
- 관리 변경은 내전 행 잠금·`expectedRevision`과 서버/내전 소속·상태를 검사한다. 오래된 화면의 제출은 409로 거절하고 다시 읽는다. 생성의 요청 ID와 신청·계정 중복 제약을 검증한다.
- 참가자 MMR은 내전에 고정된 시즌 값을 사용한다. 시즌·사용자 귀속이 확정됐으면 미반영 포지션은 1500, 시즌·사용자가 미확정이면 null이다. 실제 후보 전적·시너지·주 챔피언의 미연결 자료를 목 값으로 채우지 않으며, Data Dragon 이름·이미지는 실제 카탈로그를 사용한다.
- 내전 시작은 양 팀이 정해진 실제 Match를 생성한다. 수동 편성의 확정 포지션은 경기 전체 라인업에 자동 적용한다. ROFL 등록은 세트 결과·MMR·다음 대진 진출과 게시 예약을 함께 저장하고 최종 대진 종료 시 내전도 자동 완료한다. 서비스 목표인 자동 기록은 [purpose.md](../../purpose.md#51-운영-범위와-rofl-기반-전적-등록)를 따른다.

주요 데이터 형식은 `lib/features/scrims/types.ts`, `formation.ts`, `bracket.ts`, 설정·경로 규칙은 `settings.ts`, `paths.ts`에 있다. 컴포넌트는 전달받은 데이터와 현재 페이지의 action을 사용한다.

폼 없는 조작은 `postAction()`으로 action을 호출한다. 성공과 409 충돌이면 `invalidateAll()`로 데이터를 갱신하고, action 실패는 반환 문구를 `toast.error`로 알린다. 네트워크 예외도 재조회 후 연결 오류를 알리며 자동 재전송은 하지 않는다. 신청·설정 팝업은 별도의 `enhance` 처리로 필드/폼 오류를 표시한다.

## 운영 규칙

| 항목 | 현재 동작 |
| --- | --- |
| 정원 | 팀 수 2~4, 팀당 5명, 추가 신청 정원 0~10명. 실출전 정원 = 팀 수 × 5, 전체 신청 정원 = 실출전 + 추가 신청 정원 |
| 새 신청 | 선발 자리가 남으면 `selected`, 찼으면 `standby`. 활성 신청의 사용자·Riot 계정 중복과 전체 신청 정원 초과를 거절 |
| 철회·제외 | 활성 신청을 `withdrawn`·`excluded`로 남김. 빈 선발 자리는 신청 시각이 빠른 대기자부터 채움 |
| 수동 대기 전환 | 그 작업 직후에는 자동 선발을 하지 않음. 이후 철회·제외·모집 설정 저장 때는 같은 대기자가 다시 자동 선발될 수 있음 |
| 모집 마감 | 선발 수가 실출전 정원과 같아야 함. 편성 방식 선택은 마감 조건이 아님 |
| 편성 방식 | 운영자가 모집 중·편성 중 요약에서 수동 편성 또는 경매 선택. 방식을 바꾸면 활성 편성·경매를 초기화하고 이력을 보존 |
| 팀 이름 | 팀 순서대로 `포로팀`, `칼날부리팀`, `돌거북팀`, `바위게팀`. 이름 변경 조작 없음 |
| 경매 | 현재 후보 한 명. 팀장 포함 팀당 5명. 0점 낙찰과 가격 없는 수동 배치를 구분. 되돌린 기록은 `voided`로 남김 |
| 중도 종료 | 진행 중인 내전만 가능. 진행 중 경기는 현재 점수로 `ended_early`, 대기 경기는 `cancelled`. 완료 경기·점수는 유지 |

요약의 운영 줄에서 제공하는 단계 동작은 다음과 같다.

| 내전 상태 | 다음 단계 | 되돌리기 |
| --- | --- | --- |
| `recruit` | `모집 마감`: 선발 정원을 채우면 `preparing` | 없음 |
| `preparing` | 방식 미정이면 다음 단계 버튼 없음. 방식이 있으면 `대진 준비로`가 팀 편성 확정 안내와 함께 비활성. 수동 확정 또는 경매 전원 배치가 자동으로 `ready`로 변경 | `모집 다시 열기`: 편성 초기화·경매 이력 무효화, 선택한 방식 유지 |
| `ready` | `내전 시작`: 대진 확정 후 `in_progress` | `팀 편성 다시 하기`: 대진 삭제, 수동 확정 해제 또는 완료 경매를 진행 중으로 변경 |
| `in_progress` | `내전 종료`: 대진의 모든 경기가 완료돼야 `completed` | `대진 준비로 되돌리기`: 대진에 진행 흔적이 없을 때만 가능 |
| `completed`, `ended_early` | 없음 | `진행 중으로 되돌리기`. 중도 종료로 멈춘 경기는 진행 중, 취소된 대기 경기는 대기로 복원 |
| `cancelled` | 없음 | 없음 |

실제 Game이 있으면 대진 준비로 되돌릴 수 없다. 취소는 시작 전 단계에서만 가능하며 활성 편성·경매·대진과 함께 처리한다. 시작 후 게임이 없으면 대진 준비로 되돌린 뒤 취소하고, 결과가 있으면 중도 종료를 사용해 기록을 보존한다.

## `/g/[guildId]/scrims` — 내전 목록

**목적** 내전을 찾아 열거나 새 모집을 만든다.

**권한** 활성 서버는 누구나 조회한다. `can.createScrim = guild.isAdmin`일 때 생성 버튼을 표시하며 `create` action은 현재 Discord 관리자 권한을 검사한다.

**데이터** `ScrimListItem[]`, `total`, `page`, `pageSize: 20`, `statusFilter`, 필터별 `counts`, `can.createScrim`.
목록 항목에는 제목·상태·일정·편성 방식·팀 수·신청 수/정원·내 신청 상태·활성 참가자 미리보기가 있다.

```text
[h1] 내전                                               [모집 만들기]
[Tab] 전체 n | 모집 중 n | 진행 중 n | 종료 n
───────────────────────────────────────────────────────────────────
[날짜] 내전 제목                 [참가자 얼굴, 데스크톱] [상태]
       요일·시각 · 편성 방식 · 신청/정원 또는 팀 수        내 신청
…
[PageNav]
```

| 영역 | 컴포넌트·동작 |
| --- | --- |
| 모집 만들기 | `Button` → `ScrimSettingsDialog`. 성공하면 새 내전 요약으로 이동 |
| 상태 필터 | `Tab`. `all`, `recruit`, `active`(편성 중·대진 준비·진행 중), `done`(종료·중도 종료·취소). `?status=` 변경 시 `page` 제거 |
| 목록 | `CellGroup` + `ScrimListRow`. 행 전체가 내전 요약 링크. `DateBadge`, 상태 태그, 선발/대기인 내 신청 표시 |
| 부제 | 일정이 있으면 요일·시각, 방식이 정해졌으면 모집 중에도 방식 표시. 모집 중은 신청 수/전체 정원, 그 뒤는 팀 수 |
| 참가자 미리보기 | 데스크톱만 `AvatarStack`: 선발 우선 최대 5명과 남은 수 |
| 페이지 | `PageNav`, 20개씩. `?page=`, 첫 페이지는 쿼리 생략 |

정렬은 다가오는 일정 오름차순 → 지난 일정 내림차순 → 일정 미정 생성 최신순이다. 알 수 없는 상태 필터는 `all`, 페이지는 최소 1로 읽는다. 필터/페이지 이동 중 기존 결과를 흐리게 하고 `Loading`을 표시한다.

**상태** 서버 전체가 비었으면 `아직 내전이 없어요`를 표시하고 필터·목록·페이지 이동을 숨긴다. 생성 권한이 있으면 생성 버튼은 남는다. 필터 또는 페이지 결과가 비었으면 `조건에 맞는 내전이 없어요`를 표시한다.

### 모집 생성·설정 수정 팝업

`ScrimSettingsDialog`는 생성과 요약의 설정 수정이 공유한다. 데스크톱은 중앙, 모바일은 아래쪽 `Popup`이며 긴 내용만 스크롤하고 하단 버튼을 유지한다.

| 필드 | 컴포넌트·현재 검증 |
| --- | --- |
| 제목 | `Input`, 필수, 공백 제거 후 1~50자 |
| 날짜 | 읽기 전용 `Input` → 입력 아래 `Calendar mode="single" popup={null}`. 현재 월부터 6개월 뒤 월까지 제공 |
| 시각 | `Input inputmode="numeric"`, `HH:mm` 형식 |
| 일정 | 날짜와 시각을 함께 입력하거나 모두 비움. 비우면 미정. 입력은 `+09:00`, 표시는 `Asia/Seoul` |
| 팀 수 | `Stepper`, 2~4, 기본 2 |
| 추가 신청 정원 | `Stepper`, 0~10, 기본 2. 계산된 실출전·최대 신청 인원 한 줄 표시 |
| 하드 피어리스 | `SwitchCell`, 생성 기본 꺼짐 |

편성 방식은 팝업에서 받지 않고 요약에서 선택한다. 수정 가능한 필드는 모집 중 전체, 편성 중·대진 준비는 제목/일정/하드 피어리스, 진행 중은 제목/일정이며 끝난 내전에는 설정 수정 메뉴가 없다. action은 현재 단계의 수정 가능 필드를 검사한다. 선발 수보다 실출전 정원, 활성 신청 수보다 전체 정원을 작게 줄이면 409를 반환한다.

변경한 팝업을 닫을 때 폐기 확인을 받는다. 저장 중 닫기를 막고, 필드 오류는 해당 입력으로 포커스를 옮기며, 기타 오류는 팝업 안에서 알린다. 서버는 UI 외부 요청에도 실제 달력 날짜·입력 범위·정원 축소를 검사한다.

## `[scrimId]` 공통 — `ScrimSummary`

`[scrimId]/+layout.server.ts`가 DB `ScrimContext`와 장식용 `artUrl`을 준비하고 `+layout.svelte`가 요약 머리를 한 번 렌더링한다.

| 화면 | 머리 구성 |
| --- | --- |
| 요약, 수동 편성 | 무작위 챔피언 스플래시 배경 카드 + 제목 `h1` + 상태 점/문구 + 일정·팀 수·선택한 편성 방식·하드 피어리스 칩. 그 아래 `Steps` |
| 경매, 대진, 결과 | `compact`: 제목, 일정, 켜져 있으면 하드 피어리스 한 줄. 카드·상태 배지·팀 수·Steps는 표시하지 않음 |

스플래시를 얻지 못하면 어두운 배경색만 쓴다. 편성 방식은 값이 있으면 모집 중에도 표시한다.

| 상태 | `Steps current` |
| --- | --- |
| `recruit`, `preparing`, `ready`, `in_progress` | 각각 1 모집, 2 편성, 3 대진, 4 진행 |
| `completed` | 6, 다섯 단계 모두 완료 |
| `ended_early`, `cancelled` | Steps 없음 |

`Steps`는 번호와 완료 체크로 현재·예정·완료를 구분한다. 화면용은 `aria-hidden`, 보조기기용 `<ol>`은 `aria-current="step"`을 사용한다.

## `/g/[guildId]/scrims/[scrimId]` — 요약

**목적** 참가자가 신청을 관리하고 운영자가 참가자 선발·편성 방식·내전 단계를 관리한다.

**데이터** `scrim`, `participants: ScrimParticipant[]`, 상태별 인원과 두 정원의 `counts`, `me`, `settings`, `editable`, `finished`, `can`.
`me`는 세션 본인의 활성 신청과 해당 서버에 연결된 Riot 계정/대표 계정 ID를 담는다. `can`은 신청 가능 여부·차단 이유, 신청 수정·운영·선발 권한, 다음 단계·되돌리기·중도 종료 정보를 담는다.

```text
ScrimSummary
┌ 내 신청  [선발] Riot ID · 희망 포지션                [철회] [수정] ┐
├ 운영     다음 단계가 막힌 이유                      [⋯] [다음 단계] ┤
├ 편성 방식             [수동 편성] [경매]                           ┤
└───────────────────────────────────────────────────────────────────┘
┌ 참가자  신청 n/정원명 · 선발 n/실출전명                 [선발 관리] ┐
│ [Tab] 전체 | 선발 | 대기 | 철회·제외                                │
│ 얼굴·이름·Riot ID                       희망 포지션          상태   │
└───────────────────────────────────────────────────────────────────┘
```

**권한·구성**

| 영역 | 컴포넌트·동작 |
| --- | --- |
| 내 신청 | `MyRegistrationBar`. `me`가 있고 내전이 끝나지 않았을 때 표시. 활성 신청이 있으면 상태·계정·포지션, 없으면 신청 버튼 또는 차단 이유 |
| 신청·수정 | `RegistrationDialog`: 계정이 하나면 고정 텍스트, 여러 개면 `Radio`, 희망 포지션은 5개 `Checkbox` 중 하나 이상. 기본 계정은 대표 계정. 수정·철회는 모집 중 활성 신청만 가능 |
| 철회 | `confirm` → `withdraw`. 철회 기록은 참가자 목록에 남고 모집 중 조건을 만족하면 다시 신청 가능 |
| 운영 | `ScrimOperationsBar`. `canManage`인 운영자만 다음 단계와 `ActionMenu` 표시. 단계별 조건은 위 운영 규칙 참조. 단계 진행·되돌리기·중도 종료·취소는 확인 후 실행 |
| 설정 수정 | 운영 메뉴 → 같은 설정 팝업. 편집 가능한 필드가 있을 때만 제공 |
| 참가 안내 | 실제 서버의 편성·대진 준비·진행 중 운영 메뉴 → 확인 후 선발 참가자에게 DM 게시 작업 예약. 이미 요청한 대상은 중복 예약하지 않으며 대기·완료·실패·전달 확인 필요 건수를 운영 줄에 표시 |
| 편성 방식 | `FormationMethodChooser`, 운영자 + 모집 중·편성 중. 두 선택 칸에 `aria-pressed`·선택됨 태그. 모집 중 선택은 그대로 머무르고, 편성 중 변경은 기존 방식이 있으면 기록 삭제 확인 후 새 작업판으로 이동 |
| 참가자 머리 | 신청 수/전체 정원. 운영자에게 선발 수/실출전 정원도 표시. 선발 관리는 모집 중 운영자만 가능 |
| 참가자 보기 | `PlayerName` + `PositionChips` + 상태 표시. `userId`가 있으면 선수 상세 링크, 없으면 이름만. 희망 포지션은 선택 순서이며 첫 항목 강조 |
| 참가자 필터 | 클라이언트 `Tab`, URL 상태 없음. 데스크톱만 라벨에 개수. 참가자가 없거나 관리 모드이면 필터 없음 |
| 선발 관리 | 본문을 STDF `List batchSelectable batchMode`로 전환. 활성 신청만 선택하고 `선발`, `대기`, `제외` 일괄 적용. 제외는 확인, 선발 정원 초과는 서버 action 오류. `완료`로 보기 모드 복귀. 관리 중 이름 링크 없음 |

**상태**

- 신청 불가 이유는 모집 마감, 연결 계정 없음, 정원 마감이다. 비로그인 상태에서는 내 신청 줄 자체를 렌더링하지 않는다.
- 신청 성공은 팝업을 닫고 신청 줄을 갱신한다. 오류는 팝업에 표시하며 409이면 정원 데이터를 재조회한다.
- 참가자 전체 없음은 `아직 신청한 사람이 없어요`, 필터 결과 없음은 `해당하는 참가자가 없어요`다.
- 종료·중도 종료는 내 신청 줄을 숨기고 운영자의 되돌리기만 남긴다. 취소는 내 작업 상자 전체를 숨기고 참가자 패널을 남긴다.

## `/g/[guildId]/scrims/[scrimId]/manual` — 수동 편성

**목적** 선발 참가자를 팀·포지션에 배정하고 확정한다.

**권한** `can.edit = canManage && status === 'preparing' && !formation.confirmed`. 선택 방식이 수동이 아니면 실제 방식의 작업판 또는 방식 미정인 요약으로 307 이동한다.

**데이터** `formation`은 팀 목록, `FormationPlayer[]`, 참가 기록 ID → `teamId:position`인 `assignments`, `confirmed`, 참가자 쌍별 `pairs`를 담는다. 모집 중에는 `formation: null`이다. 실제 서버의 `getManualFormation()`은 `pairs: {}`를 고정 반환하며, 쌍별 기록은 개발 샘플에서만 채운다.

**화면** `ManualFormationBoard`는 도구 줄 → 팀 열 → 미배정 목록으로 구성한다. 기본 팀 영역은 최소 30rem의 2열이며 3~4팀은 다음 줄로 이어진다. 좁은 화면은 팀 영역을 가로 스크롤한다. 상세는 최소 56rem이고, 2팀일 때 `[팀 시너지 | 팀 | 라인 상대 전적 | 팀 | 팀 시너지]`, 3~4팀은 시너지/팀 묶음 두 개씩 배치한다.

| 영역 | 컴포넌트·동작 |
| --- | --- |
| 도구 줄 | 배치/전체·미배정 수, `상세` 토글. 편집자는 `방식 다시 고르기`, `초기화`, `편성 확정` |
| 팀 자리 | `FormationTeamCard`: 포지션 아이콘, 얼굴·이름, 해당 포지션 MMR. 희망 밖 포지션이면 `희망 외`. 팀 이름으로만 구분하며 편성 단계에서 진영을 표시하지 않음. 평균 MMR은 상세를 켰을 때만 표시 |
| 배치·교환 | 참가자를 끌어 자리에 놓거나, 참가자 버튼 선택 후 자리를 누름. 다른 사람이 있으면 원래 자리와 교환하고 원래 자리가 없으면 상대를 미배정으로 돌림 |
| 배정 해제 | 자리의 `×` 또는 미배정 목록으로 끌어 놓기 |
| 선택 해제 | 같은 참가자 재선택, `Escape`, `선택 취소` |
| 미배정 | `FormationPool`: 희망 포지션과 희망 포지션 중 최고 MMR. 전원 배정이면 완료 문구. 확정 전에는 열람자에게도 표시 |
| 상세 | `FormationSynergyRail`: 탑-정글·정글-미드·원딜-서폿의 같은 팀 전적 영역. 2팀은 `FormationHeadToHead`의 라인별 상대 전적 영역도 표시. 실제 서버는 데이터 미연결로 배치된 쌍에도 `기록 없음`/`맞대결 없음`을 표시 |
| 초기화 | 확인 후 모두 미배정 |
| 방식 다시 고르기 | `ChangeMethodButton`: 확인 후 방식·편성 기록을 지우고 요약으로 이동 |
| 편성 확정 | 전원 배정·저장 완료 후 활성. 확인 후 확정하고 내전 상태를 대진 준비로 변경. 현재 수동 편성 경로는 유지 |

배치는 응답 전에 화면을 먼저 바꾸며 실패하면 서버 데이터로 돌아가고 오류를 알린다. 확정 후에는 참가자 배치 조작과 미배정 목록이 사라지지만 상세는 계속 열 수 있다. 수정하려면 요약 운영 메뉴의 `팀 편성 다시 하기`를 사용한다.

**상태** 모집 중에는 `모집이 마감되면 선발된 참가자로 팀을 편성할 수 있어요`를 표시한다. 목 초기 편성은 일부 참가자 6명을 미리 배치하며, 이미 대진 준비 이후인 내전은 전원 배정·확정 상태로 만든다.

배치 진행 수는 작업판 머리, 미배정 수는 미배정 목록 머리에서만 표시한다. 빈 미배정 영역은 편집 중 배치 해제 드롭 대상으로 유지하며 읽기 전용에서는 숨긴다.

**현재 한계** 참고 전적의 빈 표시는 실제 과거 기록이 없다는 조회 결과가 아니다. ROFL 전적이 쌓여도 시너지·상대 전적은 아직 집계하지 않는다. 결과 저장은 업로드에서 지정한 해당 세트의 블루 팀을 사용한다.

## `/g/[guildId]/scrims/[scrimId]/auction` — 경매

**목적** 팀장·포인트를 정하고 후보를 낙찰·유찰·수동 배치해 팀을 완성한다.

**권한** 선택 방식이 경매가 아니면 실제 방식의 작업판 또는 요약으로 307 이동한다. 조작은 현재 관리자이며 내전 상태가 `preparing`일 때만 허용한다. 각 action은 경매의 `setup`·`in_progress` 상태와 revision을 추가로 검사한다.

**데이터** `AuctionView`의 상태, 선발 참가자, 팀장·시작/남은 포인트·팀원, 현재 후보 `openLot`, 대기열 `queue`, 유찰자 `unsold`, 기록 `history`, 현재 후보 전적 `openProfile`. 모집 중에는 `auction: null`이다.

### 준비 (`setup`)

`AuctionSetupBoard`는 넓은 화면에서 왼쪽 검색 가능한 팀장 후보 목록과 오른쪽 팀 설정 패널을 붙이고, 좁은 화면에서는 세로로 쌓는다. 오른쪽 머리에 준비 상태·방식 변경, 아래에 팀 카드와 저장/시작 버튼을 둔다.

- 참가자를 누르는 순서대로 비어 있는 첫 팀의 팀장이 되며 다시 누르면 해제된다. 모든 팀장이 정해졌으면 다른 후보는 비활성이다.
- 팀 카드에는 시작 포인트와 팀장을 표시한다. 시작 포인트 기본값은 1000이며 서버는 1 이상의 안전한 정수를 받는다.
- 설정 저장은 변경이 있고 포인트가 유효할 때 가능하다. 팀장을 일부만 정한 설정도 저장할 수 있다.
- 모든 팀장 지정·유효 포인트·저장 완료 후 `경매 시작`이 활성화된다. 확인 후 팀장을 제외한 참가자를 무작위 대기열에 넣고 경매 상태를 진행 중으로 바꾼다. 현재 후보는 `다음 후보`로 별도 선택한다.
- 열람자는 후보 검색·선택과 저장/시작 조작 없이 팀 설정만 본다. 검색 결과가 없으면 빈 결과 문구를 표시한다.

### 진행 (`in_progress`)

```text
내전 제목 · 일정                                  ← compact 요약
[h2] 경매 [진행 중]               [팀장 다시 정하기] [방식 다시 고르기]
[조정 타이머: 남은 초]                             ← 운영자 + 현재 후보
┌ 현재 매물 [되돌리기] [상세보기] [다음 후보] ┬ 팀 패널 2열 ───────────┐
│ 라인·티어 / 얼굴·이름·주 포지션 MMR         │ 팀·팀장·남은 포인트     │
│ 승률·승패·최근 전적 또는 상세 전적         │ 인원 / 입찰 / 팀원      │
│                                   [유찰] │                        │
├ 후보 현황 [후보 목록] [순서 섞기] [초기화] │                        │
```

`xl` 이상에서는 현재 매물/후보 현황이 왼쪽, 팀 패널이 오른쪽이며 작업판 높이는 52rem다. 더 좁으면 세로로 쌓고 팀 패널은 `md` 이상 2열이다.

| 영역 | 컴포넌트·동작 |
| --- | --- |
| 현재 매물 | `PlayerFace`, 첫 희망 포지션(없으면 프로필 주력 포지션 또는 `mid`), 해당 MMR. 프로필이 있을 때만 Riot 티어·승률·승패·최근 전적을 표시 |
| 다음 후보 | 대기열 맨 앞을 꺼냄. 현재 후보가 있거나 대기열이 비면 비활성. 시작/순서 섞기에서 대기열을 무작위화하며 매번 무작위로 뽑는 방식은 아님 |
| 상세보기 | `AuctionTargetProfile`: 내전 전적·주력 챔피언·라인별 MMR/게임 수·선호 챔피언·최근 게임·Riot 전적. 현재 실제 서버는 `openProfile: null`이라 버튼과 상세를 표시하지 않으며 개발 샘플에서만 확인 가능 |
| 조정 타이머 | 현재 후보가 있는 운영자에게만 10초 표시. 후보 또는 입찰가 변경 때 다시 시작. 10~7초 녹색, 6~3초 주황, 3초 미만 빨강. 로컬 안내이며 자동 낙찰·유찰 없음 |
| 팀 카드 | `AuctionTeamCard`: 시작/남은 포인트, 팀장 포함 인원, 팀원과 영입 경로. 현재 후보가 있고 정원이 남은 팀에만 입찰 줄 표시 |
| 입찰·낙찰 | 0 이상의 정수, 남은 포인트 이하. 입력 + `±10`·`±50` + `낙찰`. 조정 버튼 좌클릭은 증가, 우클릭은 감소, 키보드는 입력값 직접 수정 가능 |
| 현재 후보 수동 배치 | 현재 매물 카드를 팀 패널로 끌거나 후보 목록의 현재 후보 아래 팀별 `수동 배치` 버튼으로 가격 없이 배치. 0점 낙찰과 별도 기록 |
| 유찰 | 현재 매물 아래 `유찰`. 후보를 유찰 목록에 넣고 현재 후보를 비움 |
| 후보 목록 | `CandidateListDialog`, 현재 후보·실제 순서의 대기열·유찰자를 표시. 현재 후보는 팀별 수동 배치, 유찰자는 팀별 배치 또는 다시 올리기 버튼 사용. 현재 후보가 있으면 유찰자 조작 비활성 |
| 순서 섞기 | 대기열 2명 이상일 때 활성 |
| 되돌리기 | 현재 매물 머리. 확인 후 마지막 유효 낙찰·유찰 기록을 무효 처리하고 해당 후보를 다시 현재 후보로. 기존 현재 후보는 대기열 맨 앞. 후보 추첨만 따로 되돌리는 동작은 아님 |
| 초기화 | 유효 기록이 있을 때 활성. 확인 후 기록을 무효로 남기고 팀장·시작 포인트만 유지하며 대기열을 다시 섞음 |
| 팀장 다시 정하기 | 확인 후 영입·lot 기록을 무효화하고 대기열을 비운 뒤 준비로 복귀. 팀장·시작 포인트는 유지 |
| 방식 다시 고르기 | 확인 후 활성 경매 효과와 방식 선택을 초기화하고 요약으로 이동. 기존 원장 보존 |
| 낙찰·배치 효과 | 성공한 팀에 1.8초 도장·색종이·팀원 등장 효과. `aria-hidden`; 동작 줄이기 설정이면 움직임 없이 도장만 표시 |
| 경매 이야기 | 세로 `NoticeBar`, 4초 간격. 낙찰 가격·지출·남은 포인트·로스터 이야기. 화면용은 `inert`/`aria-hidden`, 보조기기에는 같은 내용을 목록으로 제공 |
| 경매 기록 | `Accordion` + 표. 순서·후보·결과·팀·가격. 무효 기록은 흐리게 하고 이름 취소선과 되돌림 문구 표시 |

진행 작업은 응답 후 갱신한다. 열람자는 진행 중에 `새로고침`으로 `invalidate('app:auction')`을 호출한다. 실시간 구독은 없다. 현재 후보·유찰 후보의 수동 배치 버튼은 후보 목록 팝업에 있다.

모든 팀이 5명이 되면 경매는 완료, 내전은 대진 준비가 된다. 요약에서 `팀 편성 다시 하기`를 실행하면 경매 진행 중으로 돌아가 기록 되돌리기·초기화·팀장 다시 정하기를 사용할 수 있다.

**상태** 모집 중에는 경매 준비 안내, 현재 후보 없음은 후보 대기 안내를 표시한다. 완료 경매는 상태·팀 카드·경매 이야기·기록만 표시한다. 실제 내전을 취소하면 경매도 취소하고 유효 영입 기록을 무효화한다.

**현재 한계** `getAuction()`은 실제 후보 상세 프로필을 조회하지 않는다. 경매 자체의 설정·낙찰·유찰·배치·되돌리기와, 후보의 과거 전적·주력/선호 챔피언·Riot 요약 연결은 별도 구현 범위다. 되돌리기는 최종 `sold`/`unsold` lot를 기준으로 하므로 A 낙찰 후 B를 추첨하고 되돌리면 B 추첨만 취소되는 것이 아니라 A 낙찰까지 되돌아간다. 모든 작업을 순서대로 되감는 동작은 아직 제공하지 않는다.

## `/g/[guildId]/scrims/[scrimId]/bracket` · `/g/[guildId]/scrims/[scrimId]/result` — 대진·결과

**목적** 확정된 팀을 대진 자리에 배치하고 확정한 뒤 점수·승자를 조회한다.

**경로·권한** 대진·결과 경로가 내전 상태와 맞지 않으면 종료·중도 종료는 `/result`, 나머지는 `/bracket`으로 307 이동한다. `/result`에는 편집 action이 없다. 두 경로 모두 `BracketBoard`를 사용하므로 본문 제목은 현재 `대진`이며 브라우저 제목만 각각 대진/결과다.
`can.edit`는 운영자 + 대진 준비 + 미확정, `can.unlock`은 운영자 + 대진 준비 + 확정이다.

**데이터** `BracketView`의 팀/팀원, 경기 목록, 라운드별 `bestOf`, 확정 여부, 편집/확정 해제 권한. 각 경기에는 직접 배치 `seat` 또는 이전 경기 승자 `from`, 팀 ID, 점수·상태·승자, 경기 상세용 `matchId`가 있다. 팀 편성 전은 `bracket: null`이다.

| 팀 수 | 틀 | 초기 경기 방식 |
| --- | --- | --- |
| 2팀 | 결승 한 경기 | 3전 2선승 |
| 3팀 | 준결승 한 경기 + 결승 직행 자리 | 준결승 3전 2선승, 결승 5전 3선승 |
| 4팀 | 준결승 A·B + 결승 | 준결승 3전 2선승, 결승 5전 3선승 |

`bracketTemplate()`이 틀을 만들며 결승 직행은 자동 승리/점수가 아닌 운영자가 정하는 시드다. `resolveWinners()`는 `completed` 경기의 승자만 다음 자리에 올린다.

**화면** 도구 줄 아래 `[팀 풀 | 준결승 | 결승]`. 팀 풀은 편집 중에만 표시하고 `lg` 미만은 위로 쌓는다. 라운드 열은 `md` 미만에서 세로로 쌓는다.

| 영역 | 컴포넌트·동작 |
| --- | --- |
| 도구 줄 | 팀 수, 편집 중 배치 수. `초기화`는 확인 후 배치만 지우고 경기 방식 유지. 전원 배치 시 `대진 확정` 활성·확인 후 잠금 |
| 다시 편성 | 확정 뒤 시작 전 운영자에게 표시. 별도 확인 없이 확정만 해제하고 배치 유지 |
| 팀 풀·배치 자리 | `BracketTeamContent`: 팀명·팀원 이름, `sm` 이상 얼굴 묶음. 팀을 선택하거나 끌어 배치. 기존 팀을 옮기면 원래 자리를 비우고 도착 자리에 있던 팀은 풀로 반환 |
| 배치 해제 | 자리의 `×` 또는 팀 풀로 끌어 놓기 |
| 선택 해제 | 같은 팀 재선택, `Escape`, `선택 취소` |
| 경기 방식 | `BracketFormatControl`의 `Radio`: 준결승/결승 각각 단판·3전 2선승·5전 3선승. 확정 후에는 텍스트만 표시 |
| 경기 표시 | `BracketMatchBox`: 확정/열람 시 팀명·점수·승자. 대기·취소는 점수 `–`, 진행 중은 경고 테두리. 대기 외 상태 태그 표시. `matchId`가 있을 때만 경기 상세 링크 |

작업 중 로딩과 `aria-busy`를 표시한다. 배치는 서버 응답 후 갱신한다. HTML 드래그 외에 버튼 선택·배치를 지원한다.

**상태** 팀 미확정이면 `팀 편성이 끝나면 대진을 만들 수 있어요`. 대진 준비 첫 진입은 빈 틀과 팀 풀, 모두 배치하면 풀에 완료 문구를 표시한다. 중도 종료는 진행 중 경기의 점수를 유지하고 승자를 새로 정하지 않으며, 대기 경기에는 취소를 표시한다.

**연결 범위** 실제 대진 배치·확정은 DB에 저장하고 내전 시작 시 양 팀이 정해진 Match를 생성한다. 점수·완료 결과는 저장된 경기 자료를 읽는다. ROFL 등록 시 점수·승자를 갱신하고 다음 대진으로 자동 진출시킨다. 개발 샘플만 고정 `RESULTS`를 사용한다. 밴픽·픽 순서·경기 중 진행 입력은 이 화면의 기능이 아니다.
