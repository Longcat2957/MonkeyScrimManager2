# 전역 페이지 UI/UX 배치안

작성일: 2026-10-29. 상태: 글로 작성한 구현 전 계획.

[전역 페이지의 업무 요구사항](../pages/global.md)과 [공통 UI 계획](../ui-plan.md)을 따른다.
아래 모든 경로는 `GlobalHeader → 본문 → AppFooter`를 사용하며 서버·내전 헤더를 함께 표시하지 않는다.
헤더의 로그인·서버 선택·개인 메뉴·화면 모드와 푸터의 정책 링크는 본문에 중복하지 않는다.

## 1. `/` — 서비스 홈

### 목표·우선순위

서비스가 어떤 업무를 돕는지 짧게 이해하고 헤더에서 서버를 선택하게 한다.
첫 화면의 주인공은 기능 소개와 실제 진입 경로이며, 장식용 대시보드·사용량 수치·가짜 내전 미리보기는 두지 않는다.

### 데스크톱 배치

```text
GlobalHeader: 브랜드 | 서버 선택 | 화면 모드 | 개인 메뉴/로그인
읽기 폭을 제한한 본문
  내전 운영과 기록을 설명하는 제목
  모집·참가 → 팀 편성·대진 → ROFL 결과 기록의 짧은 흐름
AppFooter
```

제목과 흐름의 설명을 서로 바꿔 말하지 않는다. 흐름은 세 개의 큰 Card나 클릭 가능한 단계가 아닌 간결한 순서 목록이다.
서비스명은 헤더에서 식별하므로 본문에 큰 워드마크를 한 번 더 반복하지 않는다.

### 모바일 배치

같은 순서 목록을 세로로 읽는다. 헤더의 서버 선택은 그대로 남기며 소개 아래에 별도 시작 버튼을 만들지 않는다.
짧은 콘텐츠는 자연스럽게 끝나고 푸터가 화면 하단에 온다.

### 컴포넌트 책임

| 구성 | 입력·행동 | STDF 조합·범위 |
| --- | --- | --- |
| 홈 본문 | 확정된 소개 문구. 자체 변경 행동 없음 | 의미 있는 제목·문단·순서 목록. 단독 소개를 위한 서비스 컴포넌트 분리 불필요 |
| 개발 바로가기 | 개발 모드의 검증용 목적지 | 제품 내용과 분리한 일반 링크 목록. 같은 화면의 공통 메뉴가 제공하는 목적지는 중복 제외 |

### 흐름·상태

소개는 로그인 여부에 따라 바꾸지 않는다. 서버 조회 중·목록 없음·실패는 `GuildSwitcher` 안에서 처리한다.
개발 모드 외에는 임시 ID와 개발 도구가 보이지 않는다. 정적 소개를 위해 로딩 카드나 API를 만들지 않는다.

### 미정 정책의 배치 영향

공개 기능 문구가 바뀌어도 구조는 유지한다. 봇 초대·서버 등록이 합의되기 전에는 소개에 해당 버튼을 추가하지 않는다.

## 2. `/me` — 내 정보

구현 상태: 개발 모드의 목 데이터 기반 UI·상호작용을 구현했다. [목 상태 미리보기](../../../apps/web/src/lib/mocks/README.md)로 정상·빈 데이터·오류를 확인할 수 있다.
실제 Discord 인증·계정 소유권 확인·DB 저장은 후속 작업이며, 아래 업무 정책의 미결정 상태는 유지한다.

### 목표·우선순위

본인이 어떤 계정으로 로그인했는지 확인하고, 참가에 필요한 Riot 계정을 연결한 뒤 공개 범위를 관리한다.
한 열의 약 44rem 읽기 폭으로 두며 계정 연결과 공개 설정은 저장 목적이 다르므로 별도 작업으로 나눈다.

### 데스크톱 배치

```text
내 정보
본인의 Discord 표시 정보                  ← 정적 식별, 프로필 편집 없음

연결한 Riot 계정                          [계정 연결]
  계정 이름·플랫폼·확인 상태              [연결 해제: 정책 허용 시]
  다음 계정 …

공개 범위                                ← 효과가 확정된 설정만
  [선택 입력] 프로필 공개                 필요한 효과 설명
  [선택 입력] Riot ID 표시                필요한 효과 설명
  외부 검색 허용                         ← 실제 기능 채택 시에만
  저장 결과                              [변경 취소] [공개 범위 저장]
```

읽기 전용 신상 영역을 큰 프로필 카드로 꾸미지 않는다. Riot 계정마다 공개 설정을 반복하지 않는다.
개인 선호 챔피언은 실제 사용처가 정해질 때 마지막 별도 편집 영역으로 추가한다. 지금은 빈 카드·비활성 필드를 만들지 않는다.

### 모바일 배치

전체 순서는 같다. 계정명·플랫폼은 첫 줄, 상태·허용된 해제 행동은 다음 줄로 옮긴다.
공개 설정은 라벨과 설명을 한 묶음으로 읽고 선택 입력을 그 앞에 둔다. 저장은 폼 끝에 한 곳만 둔다.
긴 이름을 잘라 식별을 어렵게 만들지 않는다. 화면 모드·로그아웃은 헤더 메뉴에 유지한다.

### 컴포넌트 책임

| 구성 | 입력·행동 | STDF 조합·범위 |
| --- | --- | --- |
| 본인 식별 영역 | 로그인 사용자 표시명·정적 이미지 | 링크 없는 `ParticipantIdentity`. Discord 편집 작업 없음 |
| `RiotAccountConnections` | 연결 목록·계정별 상태·허용된 행동 | 일반 목록 + STDF `Button`. 계정 연결/해제 요청 의도를 부모에 전달 |
| `RiotAccountLinkForm` | 입력 초안·조회 결과·소유권/연결 검증 상태 | `TaskDialog` + STDF `Input`·`Button`·`Loading`. 조회와 저장을 구분하는 페이지 전용 책임 |
| `PrivacySettingsForm` | 저장한 공개값·편집값·설정별 실제 효과 | 라벨 있는 네이티브 체크박스 + STDF `Button`. 독립 저장·오류 처리 |
| 연결 해제 확인 | 정책이 허용한 대상·현재 참가에 대한 영향 | STDF `Dialog`. 단순 확인을 위해 별도 공용 래퍼를 추가하지 않음 |

공개 설정은 저장 전의 편집값이므로 즉시 반영을 암시하는 스위치보다 체크박스와 명시적인 저장을 추천한다.
설치된 STDF 선택 컨트롤의 라벨·선택 상태 제약은 [적용 근거](stdf-components.md)에 기록한다.
선택 의미를 충족하는 공개 API가 없는 부분에만 네이티브 입력을 사용하고 주변 입력·행동은 STDF를 유지한다.

### 흐름·상태

```text
계정 연결 TaskDialog
  제목
  Riot ID 이름 Input | 태그 Input
  조회·연결 상태 한 곳
  닫기 | 조회 → 확인된 대상·연결 조건을 충족하면 연결
```

- 이름·태그는 넓은 화면에서 같은 줄, 작은 화면에서 이름 → 태그 순으로 배치한다. Input에는 placeholder와 별개로 제목을 둔다.
- 조회 뒤에는 확인한 계정과 실제 연결 가능 조건을 표시한다. 조회 성공을 소유권 확인으로 오해시키지 않는다. 값을 바꾸면 이전 조회 결과로 연결할 수 없다.
- 주요 행동은 현재 단계의 조회 또는 연결 한 곳이다. 제출 완료 후 목록을 갱신하고 패널을 닫는다. ROFL과 다른 계정 등록 흐름임을 구분한다.
- 미연결이면 목록 자리의 한 문장만 표시하고 기존 계정 연결 버튼을 유지한다. 목록 로딩은 해당 자리의 Skeleton으로 표현한다.
- 조회 실패는 패널 안, 공개 설정 저장 실패는 폼 안에 남긴다. 성공 전 공개값을 저장된 값처럼 표시하지 않는다.
- 공개 설정 변경과 계정 연결은 다른 요청이다. 한 작업의 실패로 다른 영역의 정상 데이터를 모두 지우지 않는다.
- 응답 유실·연결 충돌·세션 만료는 실제 저장 상태를 확인한다. 동일 계정을 자동 재연결하거나 다른 사용자의 연결 정보를 공개하지 않는다.

### 미정 정책의 배치 영향

| 정책 | 배치에 미치는 영향 |
| --- | --- |
| 소유권 확인·기존 연결 충돌 | 계정 조회 뒤의 조건과 연결 행동. 확인 방법이 정해지기 전 가짜 인증 단계를 만들지 않음 |
| 진행 중 참가와 연결 해제 | 해제 버튼 제공 여부·Dialog의 영향 설명 |
| 공개 설정의 실제 대상·외부 검색 | 제공하는 체크박스와 효과 설명. 저장 열만 있는 설정은 미노출 |
| 선호 챔피언의 사용처 | 실제 필요할 때 마지막 편집 영역 추가. 이번 단계에서는 미배치 |
| 서비스 탈퇴·삭제 | 별도 정책 확정 전 삭제 버튼·위험 영역을 만들지 않음 |

## 3. `/docs` — 이용 문서

### 목표·우선순위

필요한 업무 절차를 찾아 읽는다. 문서 자체의 검색·댓글·평가 같은 기능은 추가하지 않는다.

### 데스크톱 배치

```text
이용 문서
주제 목차: 모집 참여 / 팀 편성 / 대진 / 결과 등록 중 공개된 주제
본문: 주제 제목 → 절차 → 해당 절차의 예외
```

약 48rem 읽기 폭의 한 열이다. 고정 목차 사이드바 없이 상단 목차에서 본문 위치로 이동한다.
항상 읽어야 하는 절차는 Accordion 안에 숨기지 않는다.

### 모바일 배치

목차를 줄바꿈하고 본문은 같은 순서로 유지한다. 제목으로 이동하면 고정 헤더에 가려지지 않도록 공통 스크롤 여백을 사용한다.

### 컴포넌트 책임

`DocumentPage`에 제목·주제·본문을 전달한다. 목차는 같은 페이지의 앵커다.
정적 내용에 Card·Form을 억지로 넣지 않으며, 읽기 구조는 제목·문단·목록을 사용한다.

### 흐름·상태

주제 선택 → 본문 제목으로 이동 → 절차 읽기. 실제 작업은 해당 업무 화면에서 수행한다.
준비된 주제만 목차에 넣는다. 미작성과 조회 오류를 구분하고 오류에는 허용된 재시도만 둔다.

### 미정 정책의 배치 영향

첫 공개 주제·문의 경로가 정해지면 본문 데이터를 추가한다. 실제로 동작하지 않는 문의 버튼이나 준비 중 목차를 만들지 않는다.

## 4. `/terms` — 이용약관

### 목표·우선순위

현재 적용되는 이용 조건을 읽는다. 이번 계획은 약관의 내용·법적 요건을 정하지 않는다.

### 데스크톱 배치

`DocumentPage`: 약관 제목 → 확정된 적용일 → 본문 목차(길이에 따라) → 약관 전문 순서, 약 48rem 한 열.
본문을 모두 읽을 수 있게 펼쳐 두며 요약 카드나 동의 버튼을 추가하지 않는다.

### 모바일 배치

같은 순서로 읽고 긴 목록·조항은 자연스럽게 줄바꿈한다. 별도 약관 전용 고정 헤더를 만들지 않는다.

### 컴포넌트 책임

이용 문서와 읽기 틀을 공유한다. 제목·적용일·본문만 전달하며, 약관 동의를 이 페이지의 Form으로 가정하지 않는다.

### 흐름·상태

푸터에서 진입해 목차 또는 본문을 읽는다. 로그인 없이 접근한다. 적용일은 실제 발행본이 있을 때만 표시한다.
미작성 본문을 예시 조항으로 채우지 않는다. 본문 조회 오류는 공통 오류 처리를 따른다.

### 미정 정책의 배치 영향

개정본 탐색이나 별도 동의가 필요해지면 해당 흐름을 먼저 합의한다. 현재는 버전 선택·동의 이력 영역을 배치하지 않는다.

## 5. `/privacy` — 개인정보 처리방침

### 목표·우선순위

서비스의 실제 개인정보 처리 내용을 읽는다. 개인 공개 범위 설정은 이곳에서 편집하지 않는다.

### 데스크톱 배치

`DocumentPage`: 처리방침 제목 → 확정된 적용일 → 본문 목차(길이에 따라) → 전문 → 실제로 정해진 요청 절차 순서.
다른 정책 페이지와 같은 읽기 폭·제목 계층을 유지한다.

### 모바일 배치

한 열의 같은 본문을 사용한다. 정보 처리 항목이 표라면 셀 내용을 줄바꿈하고 좁은 화면에서도 항목·설명을 대응시켜 읽는다.

### 컴포넌트 책임

`DocumentPage`는 읽기 틀만 담당한다. 설정 입력이나 `/me`의 중복 진입 버튼을 포함하지 않는다.
처리방침에 필요한 표는 의미 있는 HTML 표를 사용하며 존재하지 않는 STDF Table을 가정하지 않는다.

### 흐름·상태

로그인·서버 선택 없이 읽는다. 본문 미작성·조회 오류를 구분한다. 요청 수단은 실제 담당과 경로가 확정된 경우에만 제공한다.

### 미정 정책의 배치 영향

확정된 방침·적용일·요청 경로에 따라 내용이 달라진다. 임의 연락처·보관 기간·내보내기 기능을 배치하지 않는다.

## 6. `/backoffice` — 서비스 전체 관리

### 목표·우선순위

서비스 운영자가 합의된 업무를 수행할 영역이다. 현재 업무 범위가 없으므로 완성된 관리 대시보드를 꾸며 내지 않는다.

### 데스크톱 배치

`GlobalHeader → 백오피스 제목 → 확정된 업무 본문 → 푸터`의 한 열을 기본 틀로 둔다.
업무 확정 전에는 세부 작업을 배치하지 않는다. 사용자 수 카드·서비스 상태 그래프·가짜 메뉴는 계획 범위에 없다.

### 모바일 배치

같은 전역 헤더와 한 열 본문을 사용한다. 길드 관리 메뉴를 가져오거나 별도 모바일 관리자 탭을 만들지 않는다.

### 컴포넌트 책임

현재는 페이지 조립만 필요하다. 전용 사이드바·운영 폼·통계 컴포넌트는 실제 반복 업무가 생긴 다음 정한다.

### 흐름·상태

개인 메뉴에서 진입 → 서비스 운영 권한 확인 → 허용된 본문. 대기 중 운영 데이터와 작업을 먼저 노출하지 않는다.
권한 없음·회수는 공통 접근 오류로 처리한다. 업무 미정이라는 개발 설명을 제품 본문에 채우지 않는다.

### 미정 정책의 배치 영향

운영 업무·권한·복구 요구가 이 화면의 컴포넌트를 결정한다. 현재 문서만으로 출시할 운영 화면이 확정된 것은 아니다.

## 7. `/dev/components` — 개발 작업 공간

### 목표·우선순위

후속 컴포넌트의 실제 상태와 접근성을 검토할 공간이다. 지금은 빈 작업 공간이라는 기존 범위를 유지한다.

### 데스크톱 배치

`GlobalHeader → 작업 공간 제목 → 검토 대상 한 묶음 → 푸터`. 현재는 대상 묶음이 없다.
나중에 준비할 때도 전체 STDF 카탈로그나 제품 대시보드를 복사하지 않는다.

### 모바일 배치

실제 검토 대상의 모바일 배치를 그대로 확인한다. 대상과 다른 고정 폭을 강제해 반응형 문제를 숨기지 않는다.

### 컴포넌트 책임

검토 대상과 그 상태 입력만 조립한다. 샘플은 실제 화면을 구현할 때 필요한 만큼 기존 목 데이터 위치에서 준비한다.

### 흐름·상태

개발 모드에서만 접근한다. 이후 준비된 사례의 정상·로딩·빈 데이터·오류·비활성 상태를 확인한다. 운영에서는 직접 접근도 404다.

### 미정 정책의 배치 영향

검토할 컴포넌트 목록은 구현 순서에 따른다. 현재 상태 선택기나 테스트 예제 코드를 추가하지 않는다.

## 8. `/dev/error` — 공통 오류 미리보기

### 목표·우선순위

제품의 실제 공통 오류 화면을 확인한다. 따로 만든 데모용 오류 카드는 사용하지 않는다.

### 데스크톱 배치

`GlobalHeader → 오류 제목 → 필요한 이유 한 문장 → 5xx에서만 재시도 Button → 푸터`.
넓은 화면을 채우는 그림 대신 짧은 읽기 폭으로 배치한다. 홈 이동은 헤더의 기존 링크를 사용한다.

### 모바일 배치

같은 내용을 세로로 읽는다. 오류 제목과 행동이 화면 밖으로 밀리지 않으며 추가 고정 버튼이 없다.

### 컴포넌트 책임

기존 공통 오류 페이지가 본문을 제공하고 STDF `Button`을 사용한다. 오류 상태를 바꾸는 별도 UI는 추가하지 않는다.

### 흐름·상태

직접 URL의 `status`로 403·404·500을 확인한다. 기본과 나머지 값은 404다.
500의 재시도는 같은 오류를 다시 반환하는 미리보기이며, 403·404에는 재시도를 제공하지 않는다. 운영에서는 항상 404다.

### 미정 정책의 배치 영향

현재 범위에서는 없다. 제품 오류의 문구 변경이 생기면 같은 공통 페이지에서 반영한다.
