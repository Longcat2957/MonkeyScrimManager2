# 내전 페이지 UI·UX 구성 계획

작성일: 2026-10-29. 상태: 구현 전 배치·컴포넌트 구성 초안.

[공통 UI 계획](../ui-plan.md) · [페이지 역할·상호작용 요구사항](../pages/scrims.md) · [라우트 설계](../routing.md)

이 문서는 화면에 무엇을 어느 순서로 배치할지 정한다. 아래 컴포넌트명은 구현 책임을 설명하는 가칭이며 파일 생성 지시가 아니다.
업무 권한·경매 규칙·상태 전환 정책은 요구사항 문서의 미결정 사항을 유지한다.

## 공통 적용

- 기존 헤더 전체를 현재 범위의 `GuildHeader` 또는 `ScrimHeader`로 교체한다. 헤더를 누적하지 않으며 공통 도구와 문맥 이동은 그 헤더 한 곳에서 제공한다.
- 내전 전용 헤더 아래에 `ScrimContext` → 업무 본문을 배치한다. 제목·상태·예정 시각은 `ScrimContext` 한 곳에만 표시하고, 고정 영역은 현재 헤더만 둔다.
- 서버·내전 이동은 헤더의 실제 주소 링크가 담당한다. 본문에 별도 하위 내비게이션을 추가하거나 방식·단계 전환처럼 보이는 로컬 탭으로 대체하지 않는다.
- 기본 본문은 같은 DOM을 재배치한다. 모바일용 조작과 데스크톱용 조작을 동시에 두지 않는다.
- 아래 표에서 `ParticipantIdentity`는 이름·필요한 계정 식별 정보와 허용된 프로필 링크 한 개를 담당하는 공통 표시 영역이다.
- 목록 행 전체와 내부 제목을 각각 클릭 대상으로 만들지 않는다. 표·목록은 의미 있는 HTML 구조, 조작은 STDF를 조합한다.
- 지속되는 오류·제약은 해당 작업 영역의 문장으로 표시한다. 오류를 사라지는 알림에만 맡기거나 모든 화면 상단에서 반복하지 않는다.
- 폼은 라벨과 입력을 함께 제공한다. 필수 표시, 접근 가능한 이름, 업무 검증은 서로 다른 책임으로 검토한다.
- 입력 팝업은 공통 `TaskDialog`를 사용한다. 내부 `Popup`의 배치와 서비스의 초점·배경 차단·닫기 규칙을 각 페이지에서 다시 구현하지 않는다.
- 설치 버전의 선택 컨트롤은 의미·키보드 지원이 부족한 항목에 한해 네이티브 `select`·`radio`·`input`으로 대체한다. 상세 근거는 문서 끝에 둔다.

## `/g/[guildId]/scrims` — 내전 목록

### 목표·우선순위

1. 찾는 내전의 현재 모집·운영 상태를 비교한다.
2. 특정 내전을 열거나, 권한이 있을 때 새 모집을 만든다.
3. 긴 목록의 탐색 위치를 잃지 않는다.

카드 격자 대신 한 줄씩 비교할 수 있는 목록을 선택한다. 제목과 예정 시각을 먼저 읽고 상태·인원을 비교한다.
기본 목록은 최근 생성 순, 상태 필터는 전체 선택, 페이지당 20개를 UI 초안으로 제안한다.

### 데스크톱 배치

```text
서버 전용 헤더(기존 전역 헤더 대체)
┌ 내전                                              [모집 생성] ┐
│ 상태 범위: 전체 / 모집 / 준비·진행 / 종료                       │
├ 제목                    예정 시각     상태    신청/정원   방식 ┤
│ 내전 제목 링크           날짜·시각      모집       8/12     미정 │
│ 내전 제목 링크           날짜·시각      진행      10/10     수동 │
│ …                                                             │
└                      페이지 이동                              ┘
공통 푸터

생성 진입 시: 중앙 입력 팝업
제목 → 예정 시각 → 팀 수·추가 신청 정원 → 편성 방식 → 피어리스
[생성]  [취소]
```

신청 수와 전체 신청 정원은 하나의 열로 표시하고 실출전 인원은 정원 표현 안에서 구별한다.
생성 권한이 없으면 버튼 영역을 비워 두며 대체 홍보 카드나 중복 안내를 넣지 않는다.

### 모바일 배치

- 제목과 생성 버튼은 같은 머리 영역에 두고 폭이 부족할 때 버튼만 다음 줄로 보낸다.
- 상태 범위는 줄바꿈한다. 필터를 별도 팝업에 숨기지 않는다.
- 같은 목록 행을 제목·상태 첫 줄, 예정 시각·신청 정원·방식 둘째 줄로 재배치한다.
- 페이지 이동은 목록 아래 한 곳에 둔다. 상단이나 고정 하단에 복제하지 않는다.
- 생성 팝업은 화면 폭에 맞는 한 열 폼으로 표시하고 높이가 넘치면 내부를 스크롤한다. 제출·취소는 폼 끝에 한 번 둔다.

### 컴포넌트 책임

| 서비스 컴포넌트 | 책임·입력 | 사용자 행동 | 실제 조합 | 범위 |
| --- | --- | --- | --- | --- |
| `ScrimList` | 내전 목록·표시 열·빈 상태 | 제목 링크로 특정 내전 열기 | 의미 있는 목록·네이티브 링크, 첫 조회의 `Skeleton` | 서버 홈·내전 목록 공통 |
| `ScrimListControls` | 선택한 상태 범위·조회 중 여부 | 상태 범위 선택 | 그룹 이름이 연결된 네이티브 radio | 이 페이지 |
| `ScrimListPagination` | 전체 수·페이지 크기·현재 페이지 | 목록 페이지 변경 | `Pagination` | 이 페이지의 조립 영역, 독립 공통 래퍼 불필요 |
| `ScrimCreateDialog` | 생성 입력값·허용 옵션·오류·제출 상태 | 작성·생성·취소 | `TaskDialog`의 `Popup` + 텍스트용 `Form` + 아래 선택 입력 + `Button` | 이 페이지 |
| `ScrimSettingsFields` | 제목·시각·정원·방식·피어리스 입력 정의 | 모집 설정 입력 | 텍스트는 `Form`·`Input`, 선택은 네이티브 select·radio, 시각·정원·불리언은 네이티브 input | 생성과 상세의 모집 정보 편집 공통 |

`ScrimList`에는 생성 버튼·필터를 넣지 않는다. 서버 홈에서는 그 페이지가 준비한 일부 항목만 받는다.
생성 팝업에서 작업 제출 하나와 취소 하나만 제공하고 기본 초기화 버튼은 노출하지 않는다.
팀 수는 허용 옵션의 select, 추가 신청 정원은 number 입력, 예정 시각은 datetime-local 입력, 방식은 radio, 피어리스는 checkbox로 배치한다.
`Form`에는 지원하는 텍스트 필드만 맡기고 선택 필드는 같은 입력 영역의 형제로 조립한다. `Form` 자체 제출·초기화는 숨기고 상위 작업이 값을 모아 한 번 제출한다.
생성 폼의 각 항목 순서는 배치도대로 고정하고 별도 설정 단계나 마법사로 나누지 않는다.

### 흐름·상태

| 상황 | 화면 변화·초점·피드백 |
| --- | --- |
| 첫 조회 | 목록 자리만 `Skeleton`으로 대체. 제목과 허용된 조작의 위치는 유지 |
| 필터·페이지 변경 | 선택한 조건을 유지하며 해당 목록만 갱신. 완료 후 결과 영역을 인지할 수 있는 상태 피드백 제공 |
| 서버 내전 없음 | 목록 자리에 한 문장 표시. 기존 생성 버튼을 그대로 사용 |
| 선택 범위 결과 없음 | 같은 자리에 조건 일치 결과 없음 표시. 상태 선택에서 범위를 변경 |
| 생성 팝업 열기 | 제목 입력으로 초점 이동, 배경 조작 차단. 취소하면 생성 버튼으로 복귀 |
| 생성 실패 | 팝업과 입력 유지, 필드 오류는 필드에 표시. 네트워크 오류는 제출 영역에 표시 |
| 생성 성공 | 새 내전 상세로 이동. 목록에 성공 카드나 별도 이동 버튼을 남기지 않음 |

계정·시간 선택을 위해 두 번째 서비스 팝업을 열지 않는다. 네이티브 시각 입력은 키보드로 날짜·시각을 모두 수정할 수 있고,
현재값·입력 라벨·오류가 읽히며, 브라우저 선택기를 취소해도 기존값이 보존되는지 `TaskDialog` 안에서 확인한다.

### 미정 정책의 배치 영향

- 생성 권한·지원 팀 수·입력 기본값은 폼 데이터와 버튼 노출을 바꾼다. 현재 배치 순서를 변경할 이유는 없다.
- 시각 입력은 표시 시간대를 라벨 근처 한 곳에 둔다. 서비스 시간대 정책이 확정되면 시각 변환과 유효 범위를 맞춘다.
- 목록 정렬·20개 페이지·상태 묶음은 UI 제안이며 요구사항 확정 시 조정한다. 현재 단계에는 검색·기간·정렬 선택기를 추가하지 않는다.

## `/g/[guildId]/scrims/[scrimId]` — 모집·참가·운영 요약

### 목표·우선순위

1. 자신이 신청했는지와 현재 선발 상태를 확인하고 필요한 신청 작업을 한다.
2. 참가자와 정원을 비교한다.
3. 내전 운영 권한 보유자는 선발·모집 정보·운영 단계를 관리한다.

신청 상태와 신청 조작은 명단의 본인 영역 한 곳에 둔다. 본인 요약 카드와 같은 내용의 명단 행을 중복 표시하지 않는다.

### 데스크톱 배치

```text
내전 전용 헤더(기존 전역/서버 헤더 대체)
ScrimContext: 제목·상태·예정 시각
┌ 참가 현황: 신청 12/12 · 선발 10/10 ───────┬ 운영 권한 보유자만 ┐
│ 미신청: [참가 신청]                      │ [모집 정보 수정]    │
│ 또는 본인 행: 이름 / 상태 / [신청 관리]  │ 현재 허용된 운영 작업│
├ 다른 참가자 이름 / 계정 / 희망 / 상태 ──┤ 작업 제한 사유      │
│ 각 대상의 [관리]는 권한 보유자에게만     │                     │
│ …                                       │                     │
├ 필요한 대상의 신청 이력 펼침 ───────────┴─────────────────────┤
└ 일반 열람자에게는 명단을 전체 폭으로 사용                        ┘
```

본인은 명단 맨 앞에서 한 번만 표시한다. 미신청자에게는 실제 참가 행을 만들지 않고 신청 진입만 둔다.
본인 상태와 다른 참가자 상태는 같은 표기 규칙을 사용한다. 별도의 현재 단계 설명 카드·진행률을 추가하지 않는다.
운영 작업은 오른쪽에 두되 상태값 전체를 펼친 선택기로 만들지 않고 현재 가능한 작업만 표시한다.

### 모바일 배치

- 참가 현황 → 본인 신청 영역 → 운영 작업(권한 보유자만) → 나머지 참가 명단 → 필요한 이력 순서다.
- 참가자 행은 이름·신청 상태, 계정·희망 포지션, 관리 진입 순서로 세로 배치한다.
- 본인 신청은 `TaskDialog`의 한 열 폼으로 연다. 운영자의 다른 참가자 처리는 해당 행 다음에 펼치며 동시에 여러 편집 영역을 열지 않는다.
- 신청·철회·선발 조작을 화면 하단에 고정하지 않는다. 키보드를 열어도 입력과 제출을 스크롤로 접근할 수 있게 한다.

### 컴포넌트 책임

| 서비스 컴포넌트 | 책임·입력 | 사용자 행동 | 실제 조합 | 범위 |
| --- | --- | --- | --- | --- |
| `ParticipantRoster` | 정원·현재 신청·명단·작업 권한 | 참가자 전적 또는 대상 관리 열기 | 의미 있는 목록, `ParticipantIdentity`, `Button`, `Skeleton` | 이 페이지 |
| `OwnRegistration` | 본인 신청과 계정·희망 포지션 옵션 | 신청·변경·철회·재신청 | `TaskDialog`, 라벨 있는 네이티브 select, `Button`, 필요한 영향 확인의 `Dialog` | 이 페이지 |
| `ParticipantSelectionEditor` | 선택한 참가자·가능한 처리·사유 | 선발·대기·제외 처리 | 행 아래 네이티브 radio + 사유용 `Input`, 제출 `Button` | 이 페이지 |
| `RegistrationHistory` | 대상별 신청·철회·제외 이력 | 필요한 이력 펼치기 | `Accordion` + 의미 있는 순서 목록 | 이 페이지 |
| `ScrimOperationPanel` | 가능한 운영 작업·제한 이유 | 모집 정보 수정·허용 단계 변경 | `Button`, 편집용 `TaskDialog`·`ScrimSettingsFields`, 영향 확인용 `Dialog` | 이 페이지 |
| `ScrimSettingsFields` | 현재 수정 가능한 모집 설정 | 설정 수정 | 목록 생성과 동일 입력 정의, 수정 불가 값은 읽기 전용 문장 | 내전 생성·편집 공통 |

본인이 운영 권한도 가진 경우, 본인 신청 편집을 명단의 관리 메뉴에 다시 넣지 않는다.
제외·철회 사유는 대상 이력의 정보이며 모든 참가자가 볼 수 있는 공지로 복제하지 않는다.
희망 포지션 입력은 확정된 순위 수만큼 라벨 있는 select를 한 열로 배열하고 동일 포지션 중복은 입력 오류로 표시한다.

### 흐름·상태

| 상황 | 화면 변화·초점·피드백 |
| --- | --- |
| 미신청 → 신청 작성 | 신청 버튼에서 `TaskDialog`를 열고 첫 입력으로 초점 이동. 취소하면 원래 신청 버튼으로 복귀 |
| 신청 완료 | 입력 팝업을 닫고 본인 행과 서버가 반환한 신청 상태 표시. 기존 신청 버튼을 대체한 본인 행의 신청 관리 조작으로 초점 이동. 추가 성공 안내를 명단 전체에 반복하지 않음 |
| 신청 변경·철회 | 본인 영역에서 연 입력·확인 패널에서 처리. 취소하면 원래 정보, 성공하면 바뀐 상태로 복귀 |
| 선발·대기·제외 | 대상 행 아래에서 입력·제출. 성공 시 해당 행과 상단 인원 집계가 함께 갱신 |
| 정원·권한 경합 | 해당 작업 영역에 변경된 조건 표시. 작성 중 내용을 유지하되 서버가 거절한 상태를 확정값으로 표시하지 않음 |
| 종료·취소 | 신청·편집 영역을 조회 정보로 바꾸고 보존 이력 유지 |
| 계정 조건 미충족 | 신청 위치에 필요한 준비를 한 번 안내. 계정 연결 입력을 이 화면에 추가하지 않음 |

내전 상태는 `ScrimContext`, 신청 상태는 각 참가자 행이 소유한다. 동일 상태를 운영 패널의 설명으로 반복하지 않는다.
운영 변경의 확인 창에는 영향을 받는 대상·되돌릴 수 있는 범위만 담고 평범한 신청마다 확인 단계를 추가하지 않는다.

### 미정 정책의 배치 영향

- 운영 권한 부여 기준은 패널과 대상별 조작의 노출을 바꾼다. 명단 조회 구조는 유지한다.
- 계정 미연결 참가 여부·포지션 순위 수는 신청 폼에 반영한다. 정해지지 않은 규칙을 필수 입력으로 강제하지 않는다.
- 선발 확정·시작·종료·복귀 정책을 정한 뒤 운영 패널의 정확한 행동 이름과 확인 내용을 채운다.
- 제외 사유 공개 범위가 좁으면 해당 이력의 내용을 권한별로 줄인다. 공개 가능한 상태까지 지우지는 않는다.

## `/g/[guildId]/scrims/[scrimId]/teams` — 팀 편성·경매

### 목표·우선순위

1. 수동 방식은 누가 어느 팀·포지션에 배정되었는지와 남은 자리를 확인한다.
2. 경매 방식은 현재 후보·처리와 팀별 잔여 포인트·영입 결과를 함께 확인한다.
3. 완료 후에는 최종 팀과 이력을 편하게 읽는다.

편성 방식은 내전 데이터로 결정한다. 이 페이지에 수동/경매를 바꾸는 탭을 두지 않는다.
한 참가자는 현재 편성 영역에서 미배정 목록 또는 팀 목록 중 한 곳에만 나타난다.

### 데스크톱 배치

```text
내전 전용 헤더(기존 전역/서버 헤더 대체)
ScrimContext: 제목·상태·예정 시각
수동 방식
┌ 팀 편성                                      [편성 확정] ┐
├ 미배정 참가자 ───────┬ 팀 A ─────────────┬ 팀 B ─────────┤
│ 이름·희망·[배정]    │ 포지션·이름·[수정]│ 포지션·이름     │
│ …                   │ …                │ …              │
└─────────────────────┴──────────────────┴────────────────┘
20인: 미배정 영역 옆에 팀 A·B, 다음 줄에 팀 C·D

경매 방식: 준비 때는 팀장·시작 포인트 폼
진행 때
┌ 현재 후보 / 필요한 참가 정보 ──┬ 팀별 포인트·현재 명단 ─┐
│ [처리 입력 열기]                │ 팀장 표시는 해당 명단 행│
│ 낙찰 팀·가격 또는 유찰 입력    │ …                      │
├ 후보 등장·구매 이력 펼침 ───────┴────────────────────────┤
└                                             [편성 완료] ┘
```

편성 확정과 완료는 방식별 같은 업무의 진입이므로 해당 방식에서 한 곳만 나타난다.
경매 완료 뒤에는 현재 후보 영역을 제거하고 최종 팀 목록을 본문 상단 전체 폭으로 배치한다.

### 모바일 배치

- 수동 방식은 미배정 명단 → 팀 A → 팀 B → 나머지 팀 순서로 한 열 배치한다.
- 배정·수정은 참가자 위치의 바로 아래에서 펼친다. 팀·포지션 선택만으로 처리할 수 있으며 드래그를 요구하지 않는다.
- 경매 진행은 현재 후보·입력 → 팀별 포인트·명단 → 이력 → 완료 조작 순서다.
- 이력은 `Accordion`으로 필요한 부분만 연다. 현재 후보나 정원 부족 같은 진행 필수 정보는 접지 않는다.
- 완료 조작과 오류는 문서 흐름에 두고 고정 패널·별도 모바일 입찰 버튼을 만들지 않는다.

### 컴포넌트 책임

| 서비스 컴포넌트 | 책임·입력 | 사용자 행동 | 실제 조합 | 범위 |
| --- | --- | --- | --- | --- |

가격 입력은 `Input`의 숫자 입력 모드로 받되 문자열을 업무 금액으로 검증한다. 큰 포인트 값을 반복 증감하는 조작을 요구하지 않는다.
영입 이력에는 당시 팀·구매자·가격·유효 여부를 표시한다. 현재 명단과 이력은 각각 현재 상태와 과거 거래를 설명한다.

| 상황 | 화면 변화·초점·피드백 |
| --- | --- |
| 방식 미정·선발 부족 | 본문 자리에 필요한 조건 표시. 편성 도구를 먼저 노출하지 않음 |
| 수동 배정 편집 | 선택 참가자 아래 편집 영역 한 개. 저장 성공 후 해당 참가자를 새 팀 위치로 옮기고 초점을 추적 가능한 위치로 복귀 |

| 경매 준비 → 진행 | 준비 폼을 현재 후보 영역으로 교체. 시작 포인트·팀장 수정 조작 제거 |

| 유찰·정정 | 이전 시도·거래를 이력에 유지하고 유효 결과를 구분. 취소 행을 현재 영입으로 합산하지 않음 |
| 편성 완료·경기 시작 | 수정 조작 대신 최종 팀을 표시. 하단 이력은 허용된 범위에서 조회 |

### 미정 정책의 배치 영향

- 후보 선정·낙찰 입력 주체·유찰 규칙을 정한 뒤 현재 후보 영역의 조작을 채운다. 현재 계획에는 온라인 입찰·타이머·자동 낙찰을 넣지 않는다.
- 시작 포인트·가격 단위는 데이터와 검증에 반영하며 임의 기본 금액을 제시하지 않는다.
- 저장 단위·정정 허용 시점에 따라 제출 묶음이 달라진다. 편집은 대상 옆, 결과는 원래 위치라는 배치는 유지한다.
- 팀 수가 늘어나면 같은 팀 카드를 다음 행에 배치한다. 지원 인원 확정 전 임의 팀 추가 버튼을 만들지 않는다.

## `/g/[guildId]/scrims/[scrimId]/bracket` — 대진 운영

### 목표·우선순위

1. 라운드별로 누가 누구와 경기하며 어느 대진 결과를 기다리는지 읽는다.
2. 운영 권한 보유자는 구성 대상을 선택해 수정한다.
3. 특정 Match를 열어 결과·통계·ROFL 등록 작업으로 이어 간다.

대진은 라운드별 열과 경기 단위 카드로 배치한다. 초기 계획에는 연결선을 편집하는 캔버스를 사용하지 않는다.
앞선 대진의 승자라는 관계를 자리의 문장으로 표시해 선 없이도 이해할 수 있게 한다.

### 데스크톱 배치

```text
내전 전용 헤더(기존 전역/서버 헤더 대체)
ScrimContext: 제목·상태·예정 시각
┌ 대진                                              [구성 편집] ┐
├ 1라운드 · BO 형식 ─────────┬ 2라운드 · BO 형식 ────────────────┤
│ 경기 이름 링크            │ 경기 이름 링크 또는 대진 이름    │
│ 팀 A             점수     │ 1라운드 1경기 승자 / 미정         │
│ 팀 B             점수     │ 1라운드 2경기 승자 / 미정         │
│ 상태                      │ 상태                             │
│ 다음 경기 …               │                                  │
└───────────────────────────┴──────────────────────────────────┘
구성 편집 시: 선택한 라운드·대진 아래 팀/이전 승자·BO 입력
```

Match가 연결되면 경기 이름 한 곳만 링크가 된다. 카드 클릭과 별도 상세 버튼을 추가하지 않는다.
점수는 각 팀 행에, 상태는 경기 카드 아래에 한 번 표시한다. 미정·취소·중도 종료를 0점 패배로 바꾸지 않는다.

### 모바일 배치

- 라운드를 순서대로 세로 배치하고 각 라운드의 모든 대진을 보여 준다.
- 라운드를 숨기는 탭이나 가로 스와이프를 기본 탐색 방식으로 사용하지 않는다.
- 팀 이름이 길면 줄바꿈하고 점수는 팀 이름 옆의 일정한 열을 유지한다.
- 편집은 선택 대진의 바로 아래 한 열로 연다. 다른 대진은 읽을 수 있지만 동시 편집은 하나로 제한한다.

### 컴포넌트 책임

| 서비스 컴포넌트 | 책임·입력 | 사용자 행동 | 실제 조합 | 범위 |
| --- | --- | --- | --- | --- |
| `BracketBoard` | 라운드 순서·대진·결과·미정 연결 | 경기 탐색 | 의미 있는 라운드 섹션·순서 목록, CSS 배치 | 이 페이지 |
| `BracketMatch` | 두 자리·BO·Match 링크·점수·상태 | 연결된 Match 열기 | 비클릭 `Card` + 네이티브 링크 한 개 | 이 페이지 |
| `BracketEditor` | 선택한 라운드·대진과 변경 가능한 필드 | 팀/이전 승자 지정·BO 입력·저장 | 출처 방식용 네이티브 radio, 팀/대진용 select, BO용 number 입력, `Button` | 이 페이지 |
| `BracketOperationEntry` | 구성 가능 여부·가능한 작업 | 구성 편집 시작·마치기 | `Button`, 지속 제약 문장 | 이 페이지의 조립 영역 |

구성 편집에 들어간 뒤 대상별 편집 진입을 표시하며, 평소 열람 화면에는 편집 버튼을 모든 카드에 늘어놓지 않는다.
이전 대진 승자는 선택 입력에서 출처로 표시하고, 결과 화면의 출처 문장은 추가 탐색 링크로 만들지 않는다.

### 흐름·상태

| 상황 | 화면 변화·초점·피드백 |
| --- | --- |
| 팀 미확정 | 구성 도구 대신 미충족 조건을 해당 영역에 표시 |
| 대진 없음 | 본문 빈 상태 한 곳. 권한이 있으면 기존 구성 편집 진입 사용 |
| 구성 편집 | 변경 가능한 대상만 선택 가능. 저장 실패 시 입력 유지, 성공 시 같은 대진 위치 갱신 |
| 상대 미정 | 출처와 결과 대기를 표시. 아직 없는 Match 링크 생성 금지 |
| 결과 등록 | 해당 시리즈의 점수·상태와 결정 가능한 후속 자리 갱신. ROFL 입력은 이곳에 만들지 않음 |
| 시작 후 변경 제한 | 수정 불가 값은 결과 정보로 표시. 실패할 입력을 계속 편집 가능하게 두지 않음 |
| 종료·중도 종료·취소 | 저장된 결과·관계를 유지. 미완료 시리즈의 승자를 장식이나 진행선으로 암시하지 않음 |

### 미정 정책의 배치 영향

- 지원 대진 형식·부전승·순위 결정전은 라운드 데이터와 구성 입력을 바꾼다. 미정인 형식 선택지를 선제 제공하지 않는다.
- Match 생성·승자 반영 시점을 확정하면 입력 결과와 상태 갱신 시점을 연결한다. 조회 카드 배치는 유지한다.
- BO는 허용된 홀수 값 범위로 제한한다. 서비스가 허용하는 상한은 업무 정책에서 정한다.
- Match 취소·중도 종료의 조작 위치가 정해지기 전에는 대진과 경기 상세 양쪽에 같은 행동을 두지 않는다.

## STDF 3.0.0 확인과 구현 검증 항목

선택한 구성은 설치된 `stdf@3.0.0`의 타입·소스와 STDF 스킬의 각 상세 문서를 함께 확인했다.
사용 대상은 `Button`, `Form`, `Input`, `Popup`(`TaskDialog` 기반), `Dialog`, `Card`, `Pagination`, `Skeleton`, `Accordion`이다.
`Radio`, `Stepper`, `Switch`, `TimePicker`, `Picker`도 검토했으며 아래 접근성 제약 때문에 해당 입력만 네이티브 조합을 선택했다.

| 확인 대상 | 계획에 반영한 지원 범위·제약 |
| --- | --- |
| `Form` | `form` 배열·항목 `label`·지원 텍스트 입력을 사용. 네이티브 select를 항목에 넣는 API는 없으므로 선택 필드는 형제로 조립하고 자체 제출은 비움. `required`는 업무 검증이 아님 |
| `Input` | 제목이 실제 `label` 안에 들어감. 숫자 모드도 반환값은 문자열로 취급. 날짜·파일 입력 타입을 가정하지 않음 |
| `TimePicker`·`Picker` | 날짜·시각과 선택 기능은 지원하지만 내부 `ScrollRadio`에 키보드 선택·선택값 의미가 없음. 현 버전에서는 예정 시각을 datetime-local, 계정·팀장·팀/출처를 라벨 있는 select로 대체하고 중첩 팝업을 줄임 |
| `Popup`·`Dialog` | 배치·내용 구성은 지원. 입력 팝업은 `TaskDialog`가 초점 격리·Escape·배경 비활성·복원·이름을 담당. 단순 확인 `Dialog`에도 같은 공통 규칙 적용 |
| `Radio`·`Switch`·`Stepper` | 이름·선택 상태·값 의미가 필요한 공개 속성으로 연결되지 않음. 상태·방식은 fieldset/legend가 있는 radio, 불리언은 label이 연결된 checkbox, 인원·BO는 label이 연결된 number 입력을 이번 계획의 한정 예외로 선택 |
| `Card` | `onclick`을 주면 button이 됨. 내부 링크·조작을 포함하는 팀·대진 카드는 `onclick` 없는 표시 컨테이너로 사용 |
| `Accordion` | 이력 접기·펼치기와 내용 구성 지원. 설치 소스에는 확장 상태 속성이 없으므로 공개 API만으로 보완되지 않으면 해당 이력의 접기·펼치기는 네이티브 details/summary로 한정 대체 |
| `Pagination` | 전체 수·페이지 크기·현재 페이지와 변경 이벤트 지원. 단일 페이지·빈 목록에서는 페이지 조작을 생략 |
| 버전 차이 | 문서의 Button 로딩 중 비활성 기본값과 설치 소스가 다름. 설치 계약을 우선하고 암묵적 기본값에 의존하지 않음 |

검증에서는 각 입력의 이름·현재값·오류를 읽을 수 있는지, Tab과 방향키로 선택·수정 가능한지, Enter가 중복 제출하지 않는지 확인한다.
시각 입력은 날짜와 시각의 직접 수정·취소 시 값 보존·시간대 변환을 확인하며 네이티브 입력도 서비스 시간대까지 자동 처리한다고 가정하지 않는다.
`TaskDialog` 안에서는 열린 브라우저 선택기를 닫은 뒤 해당 입력으로 복귀하고, 작업을 닫은 뒤 원래 진입으로 복귀하는지를 확인한다.
이번 단계에는 컴포넌트·CSS·목 데이터·이벤트 처리 코드를 추가하지 않는다.
