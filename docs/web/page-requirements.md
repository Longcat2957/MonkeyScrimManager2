# MSM2 페이지 역할·상호작용 명세

작성일: 2026-10-29

상태: 프론트엔드 구현을 위한 문서 초안. 컴포넌트·화면 배치·서비스 동작을 구현하지 않는다.

## 1. 목적과 읽는 순서

각 페이지에서 사용자가 무엇을 확인하고 어떤 일을 끝내야 하는지 정의한다.
라우트와 내비게이션의 소유 위치는 [라우트 설계](routing.md)를 유지하고, 이 문서는 페이지의 행동과 상태를 구체화한다.
공통 규칙을 먼저 읽고 아래 색인에서 필요한 페이지의 상세 명세로 이동한다.
이 요구사항을 화면의 읽기 순서·컴포넌트·반응형 배치로 구체화한 후속 문서는 [UI 배치 계획](ui-plan.md)이다.
현재 경로에 따라 전역·서버·내전 헤더 전체를 교체하며, 이동·설명 소유 원칙은 아래와 같이 유지한다.

| 구분 | 의미 |
| --- | --- |
| 기존 합의 | 프로젝트 목적·라우트 문서·프로젝트 규칙에서 이미 정한 서비스 범위와 책임 |
| 데이터 계약 | ERD·스키마·ROFL·MMR 문서에서 확인한 식별 기준과 저장 제약. 화면 기능이나 운영 권한의 합의를 뜻하지 않음 |
| 상호작용 초안 | 이번에 구체화한 사용자 행동·피드백·상태 처리. 기존 합의를 만족시키기 위한 설계안이며 구현 완료를 뜻하지 않음 |
| 미결정 사항 | 기능 구현 전에 판단해야 할 정책·입력 범위·역할별 권한. 임의의 기본값이나 동작으로 채우지 않음 |

상세 문서의 행동과 상태 처리는 별도 근거가 명시된 기존 합의·데이터 계약을 제외하면 **상호작용 초안**이다.
DB 열이나 상태 값이 존재한다는 이유만으로 편집 버튼·업무 화면·API를 추가하지 않는다.
현재 페이지 대부분은 제목만 갖춘 상태이고, 인증·권한·업무 데이터 연결은 미구현이다.

## 2. 전체 라우트 색인

| 라우트 | 사용자가 끝내는 일 | 상세 명세 |
| --- | --- | --- |
| `/` | 서비스의 용도를 이해하고 이용을 시작 | [전역 페이지](pages/global.md) |
| `/me` | 본인의 계정 연결·개인 설정·공개 범위 관리 | [전역 페이지](pages/global.md) |
| `/docs` | 이용 중 필요한 절차와 문제 해결 방법 확인 | [전역 페이지](pages/global.md) |
| `/terms` | 서비스 이용 조건 확인 | [전역 페이지](pages/global.md) |
| `/privacy` | 개인정보 처리 내용 확인 | [전역 페이지](pages/global.md) |
| `/backoffice` | 서비스 전체 운영 업무에 접근. 세부 업무는 미정 | [전역 페이지](pages/global.md) |
| `/g/[guildId]` | 현재 서버에서 확인할 내전·경기를 선택 | [서버 페이지](pages/guild.md) |
| `/g/[guildId]/scrims` | 내전을 찾거나 새 모집 생성 | [내전 페이지](pages/scrims.md) |
| `/g/[guildId]/scrims/[scrimId]` | 참가 신청·참가자 관리와 내전 운영 상태 확인 | [내전 페이지](pages/scrims.md) |
| `/g/[guildId]/scrims/[scrimId]/teams` | 설정된 편성 방식의 페이지로 진입. 방식 미정이면 조건 확인 | [내전 페이지](pages/scrims.md) |
| `/g/[guildId]/scrims/[scrimId]/teams/manual` | 수동 팀·포지션 배정과 확정 결과 확인 | [내전 페이지](pages/scrims.md) |
| `/g/[guildId]/scrims/[scrimId]/teams/auction` | 경매 준비·진행·이력과 최종 팀 확인 | [내전 페이지](pages/scrims.md) |
| `/g/[guildId]/scrims/[scrimId]/bracket` | 라운드·대진 구성과 시리즈 진행 결과 확인 | [내전 페이지](pages/scrims.md) |
| `/g/[guildId]/matches` | 서버 안의 시리즈 검색·열람 | [기록 페이지](pages/records.md) |
| `/g/[guildId]/matches/[matchId]` | 시리즈·Game 결과 조회와 ROFL 등록 | [기록 페이지](pages/records.md) |
| `/g/[guildId]/players/[userId]` | 한 사용자의 해당 서버 누적 전적 확인 | [기록 페이지](pages/records.md) |
| `/g/[guildId]/stats` | 서버 전체 누적 통계 확인 | [기록 페이지](pages/records.md) |
| `/g/[guildId]/admin` | 해당 서버의 설정·멤버·관리 권한 관리 | [서버 페이지](pages/guild.md) |
| `/dev/components` | 개발 중 컴포넌트 동작 확인 | [전역 페이지](pages/global.md) |
| `/dev/error` | 개발 중 공통 오류 화면 확인 | [전역 페이지](pages/global.md) |

`[userId]`는 목표 경로의 파라미터 이름이다. 현재 `[playerId]` 디렉터리는 이번 문서 작업에서 변경하지 않는다.
HTTP API·OAuth 콜백은 페이지 명세 대상이 아니며, 별도의 모집 생성·업로드·밴픽 페이지를 추가하지 않는다.

## 3. 상세 페이지의 공통 형식

| 항목 | 기록할 내용 |
| --- | --- |
| 역할 | 이 페이지에서 끝내는 사용자 업무와 인접 페이지와의 경계 |
| 접근 대상 | 열람·변경에 필요한 권한, 확정되지 않은 권한 부여 조건 |
| 필요한 정보 | 판단에 필요한 데이터와 조회 범위. 저장 필드 전체를 화면에 나열하지 않음 |
| 상호작용 | 사용자 행동, 입력·전제 조건, 완료 후 결과와 이동 |
| 상태별 처리 | 해당 페이지에 필요한 로딩·빈 데이터·실패·권한 부족·처리 중·읽기 전용 상태 |
| 미결정 사항 | 구현 전에 정할 정책과 그 영향을 받는 행동 |

## 4. 용어와 권한의 기준

| 용어 | 의미 |
| --- | --- |
| 서버·길드 | Discord 서버 하나. 문서의 경로·데이터 설명에서는 길드, 사용자 문구에서는 서버 사용 |
| 내전·Scrim | 모집부터 종료까지의 운영 단위 |
| 시리즈·Match | 한 내전 안에서 두 팀이 치르는 경기 묶음 |
| Game | 시리즈를 구성하는 개별 경기. 결과는 ROFL에서 기록 |
| 열람자 | 해당 자원을 볼 수 있는 사람. 비로그인·비멤버의 열람 범위는 공개 정책으로 결정 |
| 참가자 | 내전에 연결된 사람. 신청·선발·실제 출전 상태를 구분 |
| 내전 운영 권한 보유자 | 참가자·편성·대진 등 허용된 운영 작업을 수행하는 사람. 생성자·팀장·길드 관리자 중 누가 어떤 권한을 받는지는 미정 |
| 길드 관리자 | 해당 길드의 관리 권한을 가진 사용자. `guild_members.is_admin`에 대응 |
| 서비스 운영자 | 서비스 전체 운영 권한을 가진 사용자. `users.isServiceAdmin`에 대응 |

길드 관리자와 서비스 운영자는 서로 자동 승격되거나 동일한 권한을 갖지 않는다.
열람 가능 여부와 변경 가능 여부도 분리한다. 숨긴 메뉴나 비활성 컨트롤이 서버의 권한 검사를 대신하지 않는다.
직접 URL 진입·다른 서버로 전환·로그아웃·작업 중 권한 변경에도 같은 기준을 적용한다.

## 5. 공통 영역의 상호작용과 소유 위치

이 표는 [라우트 설계의 내비게이션 소유 원칙](routing.md#레이아웃과-내비게이션의-소유-위치)을 행동 단위로 풀어 쓴 것이다.

| 영역 | 행동 | 조건과 결과 |
| --- | --- | --- |
| 현재 범위 헤더의 로고 | 서비스 홈 이동 | `/`로 이동. 별도 홈 버튼·푸터 홈 링크를 중복 제공하지 않음 |
| 현재 범위 헤더의 서버 선택기 | 서버 선택·전환 | 접근 가능한 서버를 선택하면 해당 `/g/[guildId]`로 이동. 현재 서버 항목은 중복 이동 링크로 만들지 않음 |
| 현재 범위 헤더의 인증·개인 메뉴 | Discord 로그인·로그아웃, 내 정보 이동 | 로그인 성공 후 허용된 원래 목적지 복귀를 초안으로 둠. 로그인 실패·취소 시 이전 화면 유지. `/me` 이동은 한 곳에서 제공 |
| 개인 메뉴의 운영자 항목 | 백오피스 진입 | 서비스 운영자에게만 `/backoffice` 진입 제공. 서버에서도 권한 검사 |
| 현재 범위 헤더의 화면 모드 | 라이트·다크 전환 | 즉시 화면 모드 반영. `/me`에 같은 설정을 중복하지 않음. 선택 보존 방식은 미정 |
| 서버 전용 헤더의 메뉴 | 서버 홈·내전·경기 기록·통계·관리 이동 | 현재 길드를 유지. 관리 항목은 권한에 따라 제공. 내전 안에서는 내전 헤더의 서버 메뉴에서 제공 |
| 내전 전용 헤더의 메뉴 | 요약·팀 편성·대진 이동 | 현재 길드와 내전을 유지. 페이지 본문에 같은 목적지 버튼을 추가하지 않음 |
| 푸터 | 문서·약관·개인정보 처리방침 열람 | 같은 탭의 내부 경로로 이동 |

서버 목록을 불러오는 중·접근 가능한 서버 없음·목록 조회 실패는 서버 선택기에서 구분한다.
빈 목록을 오류로 표시하거나 본문에 두 번째 서버 선택기를 만들지 않는다.
가입·봇 초대·서버 등록 흐름은 아직 합의하지 않았으므로 빈 상태에 작동하지 않는 진입점을 추가하지 않는다.

같은 대상·동작의 조작은 화면 전체에서 하나만 제공한다. 메뉴가 담당하는 목적지와 목록의 개별 내전·시리즈 링크를 구분한다.
동일 기록이 요약 여러 곳에 포함되면 같은 목적지 링크가 반복되지 않도록 한 곳으로 모은다.
모달이 열리면 배경 조작을 막고, 닫으면 진입 지점으로 키보드 포커스를 돌린다.
모바일·데스크톱 메뉴는 동시에 표시·조작되지 않아야 한다.

## 6. 공통 상태·변경 처리 초안

| 상태 | 사용자에게 필요한 동작·피드백 |
| --- | --- |
| 최초 로딩 | 아직 조회 중인 것과 실제 데이터가 없는 것을 구분. 이전 서버의 데이터를 현재 서버 데이터처럼 표시하지 않음 |
| 빈 데이터 | 최초 기록 없음과 검색 결과 없음 구분. 기존 생성·검색 컨트롤이 있으면 같은 동작을 빈 상태에 다시 만들지 않음 |
| 부분 실패 | 이미 유효한 정보는 유지하고 실패한 영역과 복구 동작만 제공. 외부 프로필 조회 실패 때문에 내부 경기 기록을 지우지 않음 |
| 비로그인 | 로그인 필요성은 작업 위치에서 알리고 인증 진입은 공통 헤더 한 곳 사용. 입력 중 재인증 후 복구 범위는 별도 결정 |
| 권한·상태로 변경 불가 | 수행할 수 없는 작업과 이유를 작업 위치에서 설명. 열람이 허용되면 내용을 읽을 수 있게 유지 |
| 입력 검증 실패 | 해당 입력과 오류를 연결하고 수정 가능한 값을 유지. 완료로 표시하거나 조용히 입력을 덮어쓰지 않음 |
| 제출·저장 중 | 같은 요청의 중복 제출 차단. 서버가 저장을 확인한 뒤 완료 결과 반영 |
| 동시 수정·응답 유실 | 성공·실패를 추정하지 않고 현재 저장 상태 확인. 충돌한 변경을 자동 덮어쓰지 않음 |
| 저장 성공 | 바뀐 대상·상태를 반영하고 필요한 완료 피드백 한 곳 제공. 웹·봇의 최신 변경도 같은 기준으로 조회 |
| 미저장 변경 | 이동·닫기로 입력이 사라지는 작업에만 처리 방식을 정함. 단순 열람에 확인 절차를 추가하지 않음 |

직접 진입한 페이지의 403·404·기타 오류는 기존 `+error.svelte`의 공통 오류 화면을 사용한다.
공통 오류 화면의 새로고침은 5xx에만 제공한다. 입력 오류·업로드 실패·부분 조회 실패는 가능한 한 해당 작업 안에서 처리한다.
접근 거부 시 403 또는 자원 존재를 숨기는 404를 사용할 구체적 정책은 미결정이며, 없는 데이터와 비공개 데이터를 섞어 집계하지 않는다.

필터·선택 상태는 페이지별 명세에 따라 이동 후 복원할 대상을 정한다. 이미 합의한 URL 상태는 Match의 `?game=<gameId>`다.
그 외 검색 파라미터 이름·기본값·페이지 크기·자동 갱신 주기는 구현 전에 확정한다.
경매·참가자·결과 변경의 최신성은 필요한 상호작용이지만 WebSocket·폴링 같은 전송 방식은 이 문서에서 정하지 않는다.

## 7. 화면 구현 단계의 확인 기준

- 각 라우트의 목적, 입력, 성공 결과, 실패 후 가능한 행동을 상세 명세에서 찾을 수 있어야 한다.
- 정상·로딩·빈 데이터·오류·비활성 상태 중 해당 기능에 필요한 상태를 준비한다.
- 본문·공통 메뉴·푸터·열린 모달을 함께 보고 동작과 설명의 중복을 확인한다.
- 모바일과 데스크톱, 키보드만 사용하는 경우에 같은 업무를 완료할 수 있어야 한다. 입력 라벨·접근 가능한 이름·보이는 포커스를 확인한다.
- 읽기 전용, 동시 변경, 웹·봇에서 만든 같은 자원의 직접 진입을 확인한다.
- 공개 범위가 제한된 데이터는 서버가 조회·반환 단계부터 적용하며, 화면에서 가리는 것으로 대신하지 않는다.
- 사용자 표시명은 `Monkeybot`을 사용하며 실제 UI 작성 시 `SERVICE_NAME`과 브랜드 규칙을 따른다.

이번 문서 작업은 렌더링·컴포넌트 선택·목 데이터·API·DB·테스트 코드 추가를 포함하지 않는다.
후속 구현에서는 위 기준으로 실제 화면을 검토하고, UI 변경에 필요한 `pnpm check:branding`을 실행한다.

## 8. 구현 전에 먼저 정할 공통 정책

| 정책 | 결정해야 할 내용 | 영향 범위 |
| --- | --- | --- |
| 열람 범위 | 비로그인·길드 멤버·외부인별 열람, 개인 공개 설정과 길드 정책의 적용 관계 | 서버 전체 페이지와 공개 전적 |
| 변경 권한 | 내전 생성·운영·팀장 작업·ROFL 업로드 권한의 부여와 회수 기준 | 모집·편성·대진·결과 등록 |
| 계정 연결 | Riot 계정 소유권 검증, 기존 연결 충돌, 연결 해제 조건 | `/me`, 참가 신청, ROFL 참가자 연결 |
| 운영 상태 전이 | 모집 마감·편성 확정·내전/시리즈 시작·종료·중도 종료·취소의 전제와 담당 페이지 | 내전 하위 페이지와 Match 상세 |
| 예외 복구 | 참가자 연결 실패·결과 충돌·이미 기록한 결과 정정의 담당자와 처리 위치 | Match 상세, 관리 범위 |
| 운영 업무 범위 | 길드 관리와 서비스 전체 관리에서 실제 제공할 작업 | `/admin`, `/backoffice` |

각 페이지의 세부 미결정 사항은 상세 문서에 둔다. 미결정 사항을 승인된 기능이나 구현 요청으로 해석하지 않는다.
