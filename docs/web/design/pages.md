# 페이지 코드 계획

작성일: 2026-10-29. 선행: [디자인 시스템](system.md) · [코드 구조](architecture.md) · [컴포넌트](components.md)

각 라우트가 **첫 화면에서 보여 줄 정보의 순서**, **데이터 계약**, **상태**, **반응형**, **완료 기준**을 확정한다.
와이어프레임은 픽셀이 아니라 읽기 순서다. 컴포넌트 이름은 [components.md](components.md)에 등록된 것만 사용한다.

## 0. 공통 규칙

| 규칙 | 내용 |
| --- | --- |
| 첫 화면 | 제목 → (지금 상태) → 사용자가 지금 할 수 있는 일 → 상세. 스크롤 없이 주 행동을 볼 수 있어야 한다 |
| 주 행동 | 페이지당 1개. `Button fill="base" state="theme"`(시안). 보조 행동은 `fill="line"` |
| 중복 금지 | 헤더 레일이 제공하는 목적지를 본문 버튼으로 반복하지 않는다. 같은 사실을 제목·설명·태그로 세 번 말하지 않는다 |
| 시뮬레이션 | 백엔드가 없는 기능은 `$lib/data`의 목 mutation으로 **로컬 상태를 실제로 갱신**한다. 화면은 완성된 상태로 동작하고, 실제 API 연결은 함수 본문만 교체한다 |
| 미결정 기능 | 정책이 미결정인 기능(기간 필터·순위표·수동 결과 정정 등)은 **UI를 만들지 않는다**. 빈 카드·비활성 버튼으로 자리를 채우지 않는다 |
| 오류 | 페이지 전체 실패는 `+error`, 영역 실패는 `AsyncSection` |
| 제목 | `titles.ts` 형식. 브라우저 제목과 레일 문구는 같은 용어를 쓴다 |

미결정 정책은 [page-requirements.md §8](../page-requirements.md)을 그대로 유지한다. 이 문서는 그 정책을 결정하지 않는다.

## 2. `/` — 서비스 홈

**목적:** 방문자가 "무엇을 하는 서비스인지" 10초 안에 이해한다. 진입은 헤더의 서버 선택기가 담당한다(반복 금지).

```text
[Global header]
  MONKEYBOT                          (Jersey 10, 56px)
  내전 모집부터 전적 기록까지, 한 곳에서.   (body, muted, 42rem)

  01 ─────────── 02 ─────────── 03
  모집            팀 편성         기록
  Discord에서     직접 배정 /     ROFL 업로드로
  참가 신청       경매 입찰       자동 기록

  ─────────────────────────────────────────────
  세 가지 흐름이 하나의 기록으로 이어집니다. (짧은 문단)
[Footer]
```

| 구성 | 컴포넌트 | 비고 |
| --- | --- | --- |
| 히어로 | `PageHeader` 없이 직접 조립 | `h1`은 워드마크가 아니라 "내전 운영 콘솔" 제목. 서비스명은 헤더가 이미 표시하므로 h1에 중복 가능(브랜드 워드마크 제외) — **h1은 서비스 문장** |
| 3단계 | `<ol>` + `.numeric-display` 번호 | 클릭 가능한 단계로 만들지 않는다(목적지 중복) |
| 개발 바로가기 | `dev`일 때만 | 라우트 목록 + `/dev/components`·`/dev/error` |

- 상태: 없음(정적). 로딩·빈 상태를 만들지 않는다.
- 반응형: 3단계는 데스크톱 3열, 모바일 세로 번호 목록.
- 완료 기준: 운영 모드에서 빈 공간이 40% 이상 남지 않는다. 로그인·서버 선택·설치 버튼이 없다.

## 3. `/me` — 내 정보

**목적:** 참가에 필요한 Riot 계정을 연결하고 공개 범위를 관리한다.

```text
내 정보
  [본인 프로필]  표시명 · Discord ID          (정적, 편집 없음)

  연결한 Riot 계정                              [계정 연결]
    Riot ID            플랫폼    상태
    Hideonbush#KR1     KR        확인됨          [해제]
    (없음일 때) "연결된 Riot 계정이 없습니다."

  공개 범위
    [x] 프로필 공개          필요한 설명 한 줄
    [x] Riot ID 표시         필요한 설명 한 줄
    [ ] 외부 전적 검색 허용   (기능 채택 시에만 표시)
                          [변경 취소]  [공개 범위 저장]
```

| 데이터 | 필드 |
| --- | --- |
| `getViewerProfile()` | `viewer`, `riotAccounts: { id, gameName, tagLine, platform, verified }[]`, `privacy: { publicProfile, showRiotIds, allowExternalSearch }`, `capabilities: { canLink, canUnlink }` |

- 계정 연결은 `TaskDialog`(�atform: Riot ID 입력 → 조회 → 확인 → 연결)로 처리. 조회 성공을 소유권 확인으로 표시하지 않는다.
- 해제는 `ConfirmDialog` + "진행 중인 참가에 영향이 있을 수 있습니다" 1문장.
- 비로그인: 본문 대신 "로그인이 필요합니다" + 헤더 안내(버튼 없음). `viewer`가 없으면 라우트 로더에서 403.
- 완료 기준: 저장 없이 이탈 시 초안이 사라진다는 사실을 저장 버튼 옆에 한 번 표시한다. 저장 실패 시 입력 유지.

## 4. `/docs` · `/terms` · `/privacy` — 문서

`DocumentPage` 하나로 세 라우트를 처리한다. 42rem 한 열, 목차는 본문 상단 앵커.

```text
이용 문서
  목차: 모집 참여 · 팀 편성 · 대진 · 결과 등록
  ─────────────────────────────
  모집 참여
    절차 → 예외 → 다음 행동
```

- 약관·처리방침은 `appliedAt`이 실제 발행본일 때만 표시한다. 미작성 상태를 예시 조항으로 채우지 않는다.
- 완료 기준: 모바일에서 표가 있으면 표 컨테이너만 가로 스크롤, 문서 폭 유지.

## 5. `/backoffice` — 서비스 전체 관리

현재 확정된 업무가 없으므로 **구조만** 준비한다. 와이어프레임:

```text
백오피스
  (확정된 운영 업무가 없습니다)  ← 현재는 이 문장만, 카드·차트 없음
```

- 권한이 없으면 403. 첫 업무가 결정되면 이 페이지에 섹션을 추가한다.
- 완료 기준: 구현되지 않은 기능의 가짜 카드·통계·메뉴가 0개.

## 6. `/g/[guildId]` — 서버 홈 (운영 보드)

**목적:** "지금 이 서버에서 무엇이 진행 중이고, 어디로 들어가야 하는가".

```text
지금
┌──────────────────────────────────────────────────────────┐
│ ▍모집 중  30일 밤 내전 #12            10 / 10명 (미터)   │   ← 대표 내전: 링크 1개
│   오늘 20:00 · 경매 편성 · 하드 피어리스           내전 열기 →│
└──────────────────────────────────────────────────────────┘
  · 편성 중  주말 5v5 (직접)             10 / 10    대진 →
  · 진행 중  목요일 경매                 20 / 20    대진 →

최근 경기
  1팀 vs 2팀   2 : 1   종료   10/29 22:14     ← 행 1개 = 링크 1개
  3팀 vs 4팀   1 : 0   중도 종료 10/28 23:02
```

| 영역 | 컴포넌트 | 데이터 |
| --- | --- | --- |
| 대표 내전 | `ScrimRow` 변형(`promoted`) — 카드형, 링크 1개 | `activeScrims[0]` |
| 나머지 내전 | `ScrimRow` 목록 | `activeScrims[1..4]` |
| 최근 경기 | `MatchRow` 목록 | `recentMatches` |

- `activeScrims`가 비면 "진행 중인 내전이 없습니다." 한 문장. 모집 생성 버튼을 여기에 두지 않는다(내전 목록의 책임).
- `recentMatches`가 비면 "아직 등록된 경기가 없습니다."
- 두 영역은 **독립적으로** 실패할 수 있다(`AsyncSection` 2개).
- 데스크톱 ≥80rem: 오른쪽에 "서버 현황"(완료 경기·참여자·이번 주 경기) `MetricList` 3개. 좁은 화면에서는 생략(정보 중복 없음).
- 완료 기준: 첫 화면에 최소 1개의 실제 링크가 보인다. 요약과 목록에 같은 내전이 중복되지 않는다.

## 8. `/g/[guildId]/scrims/[scrimId]` — 내전 요약

**목적:** 내가 신청했는지, 지금 무엇을 해야 하는지, 누가 참가하는지.

```text
[header: Monkeybot / 서버명 ▾ / 내전명]   [rail: 요약 | 팀 편성 | 대진]

10인 · 경매 편성 · 하드 피어리스 · 10/29(목) 20:00     (ScrimContextBar)

● 선발 7/10 — 3명을 더 선발해야 편성을 시작할 수 있습니다.     (NowLine, operator)
● 신청할 수 있습니다.                          [참가 신청]     (NowLine, viewer)

참가자 (12)
  나          참가자 03   미드·서폿   선발    나
  참가자 01   탑          선발
  참가자 02   정글        대기
  참가자 04   —           신청
  …                                        (관리자: [관리])
```

| 상태(내전) | NowLine 문장(역할별) | 행동 |
| --- | --- | --- |
| recruit · 미신청 | "신청할 수 있습니다." | `참가 신청` |
| recruit · 신청함 | "신청 완료 · 선발 결과를 기다리는 중입니다." | 없음 |
| recruit · 대기 | "대기 중입니다. 선발 인원이 바뀌면 알려 드립니다." | 없음 |
| recruit · 운영자 | "선발 7/10 — 3명을 더 선발해야 편성을 시작할 수 있습니다." | `모집 마감`(선발 완료 시) |
| preparing · 방식 미정 | "편성 방식을 정해야 팀 편성을 시작할 수 있습니다." | `편성 방식 정하기` |
| preparing · 방식 결정 | "편성 방식이 경매로 정해졌습니다." | 없음 |
| ready | "편성이 완료되었습니다." | 없음 |
| in_progress | "경기가 진행 중입니다." | 없음 |
| completed / ended_early / cancelled | 상태 문구 | 없음 |

- `NowLine`의 행동은 **레일 목적지를 가리키지 않는다**(중복 금지). 편성으로의 이동은 레일이 담당한다.
- `RosterTable`: 본인 행 고정 + `aria-current`. 운영자는 행별 `관리`로 `OperationsPanel`을 연다(한 번에 하나).
- `RegistrationHistory`는 운영자에게만, 접기/펼치기로.
- 완료 기준: 신청 → 본인 행 상태 변화가 같은 화면에서 보인다. 정원 초과·마감 상태의 신청 시도는 버튼 비활성 + 이유 문장.

## 9. `/g/[guildId]/scrims/[scrimId]/teams` — 편성 진입점

```text
팀 편성
  편성 방식: 엔트리
  → (자동 이동: /teams/manual)
  방식 미정: "편성 방식을 정해야 합니다." + [방식 정하기]
```

| 조건 | 동작 |
| --- | --- |
| `formationMethod === 'manual'` | `redirect(302, '/teams/manual')` |
| `'auction'` | `/teams/auction`으로 리다이렉트 |
| `null` | 방식 선택 카드(엔트리/경매) 2개 → 선택 시 저장 후 해당 페이지 이동 |
| 선발 미완료 | "선발이 끝나야 편성할 수 있습니다" 문장 + 선택 비활성(이유 포함) |

방식 선택은 저장 후 이동하는 **유일한 전환 지점**이며, 상세 페이지에서 방식을 바꾸는 버튼을 만들지 않는다.

## 10. `/g/[guildId]/scrims/[scrimId]/teams/manual` — 엔트리 편성

```text
엔트리 편성                                          [편성 확정]
배치 7/10 · 저장되지 않은 변경 있음                [변경 되돌리기]

┌ 미배정 (3) ─────┐ ┌ 팀 A ─ 4/5 ──┐ ┌ 팀 B ─ 3/5 ──┐
│ ▸ 참가자 05     │ │ 탑  참가자01 │ │ 탑  + 배치    │
│   참가자 06     │ │ 정글 + 배치  │ │ 정글 참가자07 │
│   참가자 08     │ │ 미드 참가자02│ │ 미드 + 배치   │
└─────────────────┘ └──────────────┘ └───────────────┘
```

| 단계 | 동작 |
| --- | --- |
| 선택 | 참가자 카드(버튼) 클릭 → 선택 표시 + 안내 문장 1곳 |
| 배치 | 팀 슬롯(버튼) 클릭 → 로컬 초안에 반영. 이미 찬 슬롯이면 인라인 "교체할까요?" 1회 |
| 되돌리기 | 초안 되돌리기 1단(스택 없음, "변경 되돌리기"=마지막 저장 상태로) |
| 확정 | 검증(정원·중복·포지션) → 실패 시 첫 문제 슬롯 포커스 + 인라인 사유 |
| 저장 | 확정 시 `saveFormation()` 목 mutation 1회 호출 후 "저장됨" 표시 |

- 이 페이지는 **편집 1개 저장 1회**. 이동마다 서버를 호출하지 않는다(MSM1 P2).
- 모바일: 미배정 → 팀 A → 팀 B 세로. 선택된 참가자는 화면 하단 고정 안내줄(같은 DOM의 sticky)로 보여 준다.
- 완료 기준: 터치만으로 10명 배치가 가능하다. 키보드 Tab/Enter만으로도 동일하다.

## 18. `/dev/*` — 개발 화면

| 라우트 | 내용 |
| --- | --- |
| `/dev/components` | 실제 컴포넌트를 **실데이터 목**으로 렌더 + 시나리오 전환기(`?scenario=normal|empty|slow|error|partial`). 각 컴포넌트의 정상·빈·오류·처리 중·비활성 5상태를 한 화면에서 |

## 19. `+error.svelte`

```text
        404
  페이지를 찾을 수 없어요
  (문장 1개)
  [서버 홈으로]        ← 404
  [다시 시도]          ← 5xx만
```

| 상태 | 문장 | 행동 |
| --- | --- | --- |
| 403 | "이 서버를 볼 권한이 없습니다." | 서버 선택 안내(링크 없음, 헤더 사용) |
| 404 | "페이지를 찾을 수 없어요." | 문맥이 있으면 서버 홈 링크 1개 |
| 5xx | "페이지를 불러오지 못했어요." | `다시 시도` 1개 |

개발자용 메시지·`page.status` 숫자 노출은 유지하되, 사용자 문장이 우선이다. `page.error.message`는 우리 문장이 있을 때만 쓴다.

## 부록 B. 화면 완성 판정 (DoD)

각 라우트는 다음을 모두 만족해야 "완성"이다.

1. 첫 화면에 주 행동 또는 실제 데이터 링크가 있다.
2. 정상·로딩·빈·오류 상태가 `/dev/components` 시나리오로 재현된다.
3. 360·768·1280px, 라이트·다크에서 레이아웃 붕괴·가로 스크롤이 없다.
4. 키보드만으로 주 행동을 완료할 수 있고 포커스가 보인다.
5. 같은 화면에서 같은 목적지·같은 설명이 두 번 나오지 않는다(헤더·푸터·열린 패널 포함).
6. 브라우저 제목이 `titles.ts` 형식과 일치한다.
7. `pnpm check` 통과, `pnpm check:branding` 위반 없음.
