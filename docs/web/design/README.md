# 프론트엔드 디자인 전면 재작성 계획

작성일: 2026-10-29 · 브랜치: `design/frontend-rewrite` · 상태: **설계 확정, P0(기반·셸) 구현 완료**

이 디렉터리는 `apps/web` 프론트엔드를 **처음부터 다시 그리는 계획**이다. 기존 `docs/web/ui-plan.md`와
`docs/web/ui/*.md`의 배치안을 대체하며, 이번에는 배치도에 그치지 않고 **토큰·컴포넌트·페이지·코드 골격**까지 확정한다.

## 1. 왜 다시 쓰는가

[진단서](audit.md)의 결론: **서비스의 뼈대는 있는데 화면이 없다.**

- 18개 서비스 페이지 중 18개가 `<h1>` 한 줄이다. 운영 모드 홈은 워드마크 한 줄이 전부다.
- 앱 전체에서 STDF를 쓰는 곳은 `+error.svelte`의 `Button` **1곳**뿐이다. STDF 우선 원칙과 정면으로 어긋난다.
- 헤더는 190줄 중 54줄이 자체 CSS이고, 규칙 문서와 반대로 GitHub 링크를 1차 메뉴에 두며, 테마는 `localStorage`를
  컴포넌트가 직접 만진다.
- 프론트 목 데이터·데이터 로딩·로딩/빈/오류 상태가 전부 없다. 그래서 화면을 설계할 재료 자체가 없었다.

## 2. 무엇을 만드는가 — "Arena Console"

내전이 열리는 저녁, 운영자가 한 화면에서 모집·편성·대진·결과를 지휘하는 콘솔. 로고의 세 색(잉크·크림·시안)을
시스템 뼈대로 쓰고, 숫자를 주인공으로 세우고, 다크를 기본 시각 기준으로 삼는다. 자세한 시각 규칙은 [디자인 시스템](system.md).

| 지금 | 계획 |
| --- | --- |
| 워드마크 한 줄 홈 | 서비스 정체성 + 3단계 흐름 + 개발 도구 분리 |
| 헤더 1개(전역) | 전역 / 서버 / 내전 문맥 헤더 + 컨텍스트 레일(하나의 DOM) |
| `<h1>`만 있는 17개 페이지 | 운영 보드·참가 명단·편성 보드·경매 콘솔·대진·성적표·전적·통계 |
| STDF 1회 사용 | 버튼·입력·패널·다이얼로그·진행률·스켈레톤·로딩·페이지 이동·알림·바텀시트 네이티브 사용 |
| 상태 처리 0 | 모든 비동기 영역이 로딩·빈·오류·재시도 4상태 |
| 목 데이터 0 | `$lib/mocks` + `$lib/data` 계약(스키마 enum 1:1) |
| 색·타입 임의 값 | 브랜드 토큰 + 의미 토큰 + 타입 스케일 |

## 5. 구현 순서 (한눈에)

```text
P0 기반(토큰·셸·오류·개발)  → 디자인이 즉시 바뀐다
P1 데이터·상태 도구        → 모든 화면의 재료
P2 전역 페이지             → 첫인상
P3 서버 문맥               → 서버 홈·내전 목록·기록 목록·관리
P4 내전                    → 요약·참가·편성 진입
P5 편성                    → 엔트리 편성·경매·대진
P6 기록                    → 경기 상세·ROFL·전적·통계
P7 마감                    → 백오피스·접근성·성능
P8 실데이터 연결(별도)
```

세부 PR·검증 기준은 [delivery.md](delivery.md).

## 6. 이 계획이 결정하지 않는 것

- 업무 정책: 열람 범위, 변경 권한 부여, 계정 소유권, 운영 상태 전이, 경매 규칙, 결과 정정 절차
  ([page-requirements.md §8](../page-requirements.md) 유지).
- 백엔드 API 형태, 인증 구현, 실시간 전송 방식.
- 약관·개인정보 방침의 법적 본문.

정책이 정해지면 이 문서들의 **데이터 필드와 상태 표만** 갱신하면 되도록 경계를 분리했다.

## 7. 검토 체크리스트 (이 계획 자체를 볼 때)

- [ ] 화면마다 "지금 할 일"이 하나이고 주 행동이 명확한가.
- [ ] 헤더·레일·본문·푸터에서 같은 목적지·같은 설명이 두 번 나오지 않는가.
- [ ] 컴포넌트가 전부 STDF이거나, 아니면 §9 예외표에 근거가 있는가.
- [ ] 상태 4종과 권한별 화면이 페이지마다 정해져 있는가.
- [ ] 코드 골격이 설치판 `stdf@3.0.0`의 실제 API와 맞는가(§1.1).
- [ ] MSM1의 실패(P1~P15)가 계획에서 실제로 제거됐는가.
