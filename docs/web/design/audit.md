# 현재 프론트엔드 진단서

작성일: 2026-10-29. 대상: `main`의 `apps/web` 프론트엔드 전체.
기준 문서: [프로젝트 목적](../../purpose.md), [라우트 설계](../routing.md), [페이지 요구사항](../page-requirements.md), [프로젝트 규칙](../../../AGENTS.md).

이 문서는 새 디자인 계획([README](README.md))의 출발점이다. 감정적 비판이 아니라 **지금 브라우저에 실제로 뜨는 화면**과
**정한 규칙과 실제 코드의 간극**을 근거로 정리한다. 모든 근거는 파일 경로와 줄 번호로 확인한다.

## 1. 한 줄 결론

> 디자인 시스템을 쓰지 않고 손으로 다시 짠 HTML/CSS다. STDF는 앱 전체에서 `Button` 1개(!)에만 쓰였다.

## 2. 화면이 비어 있다 — 가장 큰 문제

### 2.1. 운영 모드의 홈 화면은 워드마크 한 줄이다

```svelte
<!-- routes/+page.svelte:37-72 -->
<h1 class="font-brand text-4xl ...">{SERVICE_NAME}</h1>
{#if dev}
  ...개발 바로가기...
{/if}
```

운영 배포에서는 `dev`가 false이므로 **로고 옆의 `Monkeybot` 한 줄이 전부**다. 방문자는 이 서비스가 무엇이고,
어디서 시작해야 하는지 알 수 없다. 상세 페이지 18개도 같은 형태다:

```svelte
<!-- routes/g/[guildId]/scrims/+page.svelte (그리고 17개 페이지가 동일) -->
<h1 class="text-2xl font-semibold">내전 목록</h1>
```

라우트 설계 문서가 정한 "서버 홈은 진행 중 내전과 최근 경기를 요약한다"([routing.md:42](../routing.md))는 계약은
화면에 존재하지 않는다. 페이지 요구사항도 24줄에서 "현재 페이지 대부분은 제목만 갖춘 상태"라고 자인한다.

### 2.2. 상태 설계가 물리적으로 불가능한 구조

문서는 정상·로딩·빈 데이터·오류·권한 부족을 요구하지만(AGENTS "Frontend Implementation"), 현재 코드에는
**비동기 지점이 없으므로 그 상태를 표현할 컴포넌트도 없다.** `Skeleton`, `Loading`, 빈 상태, 재시도 영역,
입력 오류, 작업 패널이 전부 미구현이며 `lib/mocks/`도 비어 있다. 데이터가 없어서 화면을 못 만든 게 아니라,
화면 설계가 데이터·상태를 전제하지 않았기 때문에 구현할 것이 남지 않았다.

### 2.3. "제목만 있는 페이지"는 디자인 실패가 아니라 정보 설계 실패다

17개 페이지가 모두 동일한 `h1` + 브라우저 제목이다. 사용자가 그 화면에서 **끝내야 하는 일**(예: 참가 신청, 선발 확정,
ROFL 업로드)이 화면에 하나도 없다. 이 상태는 CSS를 다듬어서 해결되지 않는다. 업무 단위 화면, 즉
*보드·표·스테이지·흐름*을 새로 설계해야 한다.

## 3. 유일한 UI인 헤더가 규칙과 어긋난다

### 3.1. STDF 우선 원칙 위반

`AppHeader.svelte`는 190줄 중 54줄이 자체 CSS이고(`:138-190`), `nav-link`·`nav-action`·`menu-summary` 같은
**자체 디자인 시스템 원형**을 만든다. STDF `NavBar`·`Button`·`Popup`·`ActionSheet`은 쓰지 않는다.
`Button`조차 쓰지 않으므로 크기·상태·포커스·다크 모드 처리가 서비스 전체에서 헤더와 본문 사이에 통일되지 않는다.

### 3.2. 문서와 코드가 정면으로 충돌하는 지점

| 항목 | 정한 규칙 | 실제 코드 | 영향 |
| --- | --- | --- | --- |
| GitHub 링크 | "GitHub 저장소 링크는 서비스 업무 메뉴에 포함하지 않는다" ([routing.md:117](../routing.md)) | 주 내비게이션 링크로 노출 (`AppHeader.svelte:44-52`) | 서비스와 무관한 외부 링크가 1차 메뉴를 차지 |
| 헤더 종류 | 전역·서버·내전 헤더 중 **하나만** 표시 ([ui-plan.md:99](../ui-plan.md)) | 항상 같은 전역 헤더 | 서버·내전 문맥 이동 수단이 없음 |
| 서버 선택 | 헤더 한 곳에서만 제공 | 구현 없음 | 서버 문맥에 진입할 방법이 없음 |
| 메뉴 중복 | 같은 목적지 조작은 화면 전체에서 하나 | GitHub 링크가 데스크톱 내비(`99-103`)와 모바일 메뉴(`123-131`)에 **각각 렌더링** | 같은 조작 2벌 관리, 수정 누락 위험 |
| 터치 대상 | 기본 조작 높이 약 44px ([ui-plan.md:194](../ui-plan.md)) | `min-height: 2.25rem` = 36px (`AppHeader.svelte:140`) | 모바일 오조작 |
| 홈 이동 | 헤더 로고 한 곳 | 로고(`88-97`)만 존재 | 규칙 자체는 준수, 다만 나머지가 없음 |

### 3.3. 텍스트 계층이 없는 "링크 모음"

헤더 오른쪽은 `GitHub`와 테마 버튼뿐이다. 현재 위치(활성 메뉴), 서버 이름, 사용자, 다음 행동이 모두 없다.
정보 구조상 헤더가 **문맥 표시 장치가 아니라 장식**이다.

## 4. 브랜드가 화면에 없다

| 요소 | 현재 | 문제 |
| --- | --- | --- |
| 색 | Slate 회색 계열만 사용 (`layout.css:15-62`) | 로고의 **잉크 네이비·크림·일렉트릭 시안**과 무관한 무채색 UI |
| 워드마크 | `font-brand` Jersey 10 (헤더·푸터·홈) | 유일한 브랜드 요소. 나머지 화면에 이어지는 시각 언어가 없음 |
| 강조색 | `--color-primary`가 회청색, 사용처는 오류 숫자(`+error.svelte:28`) | CTA·선택·포커스에 쓸 주색이 사실상 없음 |
| 상태색 | `--color-success/warning/error/info` 정의됨(`layout.css:55-58`), 사용처 0 | 승패·진행·경매 상태를 표현할 언어가 없음 |
| 축하/성취 | 없음 | 경기 결과·낙찰·우승 같은 도메인 이벤트가 감정 없이 처리됨 |

`stdf.dev`의 기본 테마를 그대로 쓰지 않은 것은 맞지만, **브랜드 팔레트를 STDF 테마에 재주입**하지도 않아
STDF 컴포넌트(시안/다크)와 자체 CSS(슬레이트)가 서로 다른 두 회사 같은 색을 쓴다.

## 5. 타이포그래피·숫자·표 — 게임 데이터 서비스인데 데이터가 안 읽힌다

이 서비스의 정보 대부분은 **숫자**다: 시리즈 점수, K/D/A, CS, 포인트 잔액, 승률, MMR, 인원 정원.
그런데:

- 탭ular 숫자(`tabular-nums`)가 어디에도 없다 → 표에서 열이 흔들린다.
- 숫자용 스케일이 없다 → `text-2xl`/`text-8xl` 같은 임의 값만 있다(`+error.svelte:28`).
- 표 컴포넌트가 없다. `ul/li` 링크 목록만 있는 계획([ui-records.md:26](../ui/records.md))이며 10인 성적표를 그릴 틀이 없다.
- Jersey 10은 워드마크에만 쓰인다. 이 폰트의 강점(군더더기 없는 디스플레이 숫자)은 점수·라운드 표기에 활용되지 않는다.

## 6. 테마·폰트·메타데이터의 기술 부채

| 항목 | 현재 구현 | 문제 |
| --- | --- | --- |
| 첫 방문 테마 | `app.html:7-17`가 `localStorage`만 확인, 기본 `data-mode="primary"` | OS 다크 모드 사용자도 항상 라이트로 시작, `prefers-color-scheme` 무시 |
| 화면 모드 저장 | `AppHeader.svelte:13-25`이 `localStorage` 직접 접근 | 상태 관리가 헤더 컴포넌트에 갇힘. 다른 곳에서 모드를 읽을 방법 없음 |
| 다크 변형 정의 | `layout.css:4`의 복잡한 `:not()` 체인 | STDF 다크 클래스와 결합 시 예측 어려움, 주석도 근거 부재 |
| 폰트 | `app.html:18-23` Google Fonts 외부 CSS 블로킹 로드 | 렌더 차단 + 한글 FOUT + 오프라인/프라이버시 의존. preload·fallback 메트릭 없음 |
| `meta` | `text-scale`(무의미), `application-name`만 있음 | `theme-color`, `color-scheme`, OG/Twitter 카드, manifest, apple-touch-icon 없음 → 링크 공유 시 미리보기 빈약 |
| 레이아웃 틀 | `.app-frame`이 본문·푸터에 좌우 1px 경계선(`layout.css:82-95`) | 게임 콘솔 느낌의 "창"이 아니라, 아무 기능 없는 액자. 모바일에서 4px 여백 계산으로 본문이 답답함 |
| 용어 | 브라우저 제목이 `길드 홈`·`매치 목록`·`내전 상세`·`참가자 전적` | 라우트 설계의 `서버 홈`·`경기 기록`·`요약`·`사용자 전적`과 불일치. 문서가 정한 사용자 용어를 화면이 어김 |

## 7. 상태·오류·피드백

`+error.svelte`는 유일하게 STDF를 쓴 화면이지만 `heightOut="0"` 같은 레이아웃 우회로 36px 버튼을 만들고(`:33`),
폭을 `w-36`으로 고정한다. 5xx에서만 재시도하는 규칙은 지켰으나, 403/404/500의 **다음 행동이 없다**
(로그인, 서버 선택, 목록으로). 서비스 전역에서 토스트/알림/작업 패널이 없어 "저장 중·실패·성공"을 표현할 수단이 전무하다.

## 8. 원인 분석 (왜 이렇게 됐나)

1. **문서는 "하지 말 것" 중심으로 발전했다.** 화면 중복 방지·장식 금지 규칙은 정당하지만, 대체 시각 언어(토큰·타입 스케일·
   밀도·상태 표현)를 함께 정의하지 않아 구현자는 "비우기"만 할 수 있었다. 실제로 `ui-plan.md` 전체가 배치도와 금지 목록이며
   색·타입·컴포넌트 코드가 없다.
2. **STDF를 데코레이션이 아니라 경계로만 다뤘다.** STDF는 모바일 우선 컴포넌트 라이브러리인데, 이 프로젝트는 데스크톱 표·링크
   중심으로 설계해 대부분을 native로 대체했다. 그 결과 STDF가 사실상 미사용이 되었고, "STDF 네이티브 우선" 규칙과 충돌한다.
3. **데이터 계약이 화면보다 뒤에 있다.** DB 스키마는 1,231줄인데 화면은 235줄이다. 화면이 쓸 뷰 모델·목 데이터·상태 전이가
   없으니 렌더할 것이 없었다.
4. **셸을 한 번만 만들었다.** 전역 헤더 하나로 설계했고, 나중에 문서 요구사항이 "전역·서버·내전 헤더"로 늘어나도
   구현은 따라가지 않았다.
5. **검증 기준이 문서 검토였다.** 실제 브라우저·뷰포트·상태를 확인하는 절차가 없어, "구현했다"는 판정이 문서에만 남았다.

## 9. 무엇을 새로 설계해야 하는가 (새 계획의 목표 요약)

| 목표 | 정량 기준 |
| --- | --- |
| 모든 라우트에 "그 화면에서 끝내는 일"이 보인다 | 18개 라우트 각각 첫 화면에 업무 영역 ≥ 1, 제목만 있는 화면 0개 |
| STDF 사용률 | 서비스 UI의 대화형 조작(버튼·입력·패널·알림·배지·진행률·페이지 이동·로딩·스켈레톤) 중 **80% 이상 STDF 네이티브**, 나머지는 문서화된 한정 예외 |
| 문맥 내비게이션 | 전역/서버/내전 헤더 중 항상 1개, 중복 목적지 0개 |
| 상태 커버리지 | 모든 비동기 영역에 로딩·빈·오류·재시도 3종 구현, 작업에 진행·실패·성공 피드백 1곳 |
| 브랜드 일관성 | 모든 서비스 화면이 3색(잉크·크림·시안) 토큰만으로 구성, 임의 색 지정 0개 |
| 접근성 | 44px 터치 대상, 가시 포커스, 키보드만으로 모든 작업 완료, 320px~1440px 무붕괴 |
| 성능 예산 | 첫 화면 LCP < 2.0s(모바일 4G), CLS < 0.05, 셸 JS < 180KB gz, 폰트 < 400KB |
