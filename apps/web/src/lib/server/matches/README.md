# 경기와 결과

소비자는 `/g/[guildId]/matches`, `/matches/[matchId]`와 경기 상세의 `confirmLineup`, `releaseLineup`, `upload`, `revertResult` action이다. 내전 대진과 서버 홈도 같은 Match·Game을 조회한다.

- `queries.ts`: 경기·채택 Game·실출전·피어리스·MMR 공개 조회. 없는 수치·실제 시각은 null이다.
- `operation-context.ts`: 경기 단위 출전 라인업, 다음 게임 번호, 운영 권한 힌트와 정정 차단 사유 조회.
- `service.ts`: 경기 전체의 라인업 저장·확정·해제. 양 팀 다섯 포지션과 서로 다른 열 명을 검증한다.
- `lineup-bootstrap.ts`: 수동 편성에서 이미 확정한 포지션을 Match 생성 시 복사·확정한다. 경매는 경기마다 한 번 확정한다. 진출한 팀의 직전 확정 포지션도 다음 경기로 복사하며, 경매는 복사된 초안을 확정한다. 같은 경기의 후속 Game은 그 라인업을 재사용한다.
- `results.ts`: ROFL 자동 등록, Game·실출전·MMR·경기 종료·승자 진출을 한 트랜잭션에서 처리한다. 마지막 결과 취소는 역분개와 다음 경기 복원을 함께 처리한다.
- `reversal.ts`: 후속 경기 작업·MMR 변경이 생긴 결과의 정정을 막는다.

열람은 공개다. 라인업 변경·결과 취소는 현재 서버 관리자만, 업로드는 현재 서버 관리자 또는 확정 출전자만 가능하다. 쓰기 전에 Discord REST로 소속을 갱신하고 트랜잭션 안에서 권한을 다시 검사한다. 취소된 결과까지 포함해 Game이 생긴 경기의 라인업은 변경하지 않는다.

업로드는 Match revision·다음 Game 번호·lineupId·이번 Game의 블루 팀을 받는다. ROFL 팀 번호 자체에 검증되지 않은 물리 진영 의미를 붙이지 않는다. 파일의 두 팀 구성을 확정한 서비스 팀과 대조한 후 업로드 문맥의 진영을 저장한다. 게임 내 밴픽이나 진행 입력은 추가하지 않는다.

ROFL Riot ID를 실제 ACCOUNT-V1로 조회한 PUUID와 서버별 계정 연결을 대조한다. 기존 연결 계정으로 두 팀의 대응을 확인하고, 파일에 명시된 `TEAM_POSITION`과 확정 라인업을 함께 사용해 실제 출전자를 연결한다. 미연결 부계정도 팀과 포지션으로 유일하게 확인되면 당시 사용 계정으로 기록하며, 서버 계정 연결이나 대표 계정을 자동 변경하지 않는다. 기존 소유자·포지션 충돌과 근거가 없는 팀·출전자 연결은 거절한다. 파일에 포지션이 없는 기존 연결 계정은 검증한 사용자와 이미 확정된 포지션을 사용한다. 배열 순서·희망 포지션·리플레이 원시 PUUID로 계정이나 포지션을 추정하지 않는다.

파싱과 Riot 호출은 잠금 밖에서 처리하고, 계정 조회는 공용 전송기 상한보다 작은 묶음으로 실행한다. 저장은 사용자 → 계정 → 서버 연결 → 시즌 → 내전 → Match → Game → MMR 순으로 잠근다. 파일 SHA-256과 선별 결과의 정규화 지문을 별도로 검사한다. 같은 성공 요청은 기존 Game을 반환하고, 다른 파일의 동일 결과·다른 경기 재사용·취소 후 늦은 재전송은 차단한다. 등록 실패는 계정 식별 행·ROFL 선별 자료·Game·MMR·게시 예약까지 모두 롤백한다.

마지막 결과 취소는 기존 Game을 `cancelled`로 남기고 출전·ROFL·MMR 역분개 이력을 보존한다. 같은 번호의 새 결과는 새 Game으로 등록한다. 자동 생성만 된 수동 다음 경기와 미확정 경매 초안은 안전하게 제거할 수 있지만, 관리자가 수정한 다음 경기·후속 결과·후속 MMR 변경이 있으면 취소를 거절한다.

원본 ROFL은 저장하지 않는다. P0~P2 선별 자료와 파일 지문·크기·버전·업로더·등록 시각만 저장한다. 실제 경기 시각은 모르면 null이다. 정상 파일은 별도 승인 없이 자동 등록하며 하드 피어리스는 안내만 제공한다. ROFL 서명 진위의 암호학적 검증을 구현한 것으로 취급하지 않는다.
